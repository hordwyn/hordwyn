## Must fix before commit

### OT2B-1 (high) A page refetch rebuilds an open log dialog; the new test retries around it

- Where: `web/src/item.rs:139-148` (the keyed `<For>` renders `ItemView` afresh on every
  refetch) and `web/src/item.rs:356-361` (both dialogs are mounted inside `ItemView`);
  `ui/src/dialog.rs:146-161` (the panel's effect starts from `prev = None` on the new mount);
  `web/src/funnel.rs:409-420`; the workaround: `src/web/tests/item.spec.ts:739-748` (the
  comment "a late refetch of the page ... renders the open dialog once more, so the
  measuring is repeated until it holds" and the `toPass`).
- Is the test change a workaround for an app race? Yes. The test failed because the app
  replaced the dialog's elements under it (`boundingBox()` of a field was null). The change
  makes the test focus the field again and measure again until one attempt falls between
  two renders. A person cannot do that. The added wait for "One play" in the bar is a
  legitimate wait on visible state, but it is not enough either: a save causes two
  refetches, the page's own (`refresh.run(())` in `save_play`, 300 ms later) and one more
  from the `entity.updated` event of the same save (`item.rs:96-103`; the 300 ms `pending`
  window only merges them when the event arrives inside it). HANDOFF section 0, Definition
  of Done: "no test workarounds for app races". The same class of defect was fixed in the
  app, not in the test, in ot2a (OT2A-4, OT2A-5: `item.spec.ts:431-439`, `:461-471`).
- Is it pre-existing? The mount point is (the same two lines at HEAD). It is still this
  package's to fix: DEC-564 handed the dialogs of the action bar to ot2b, the files are the
  package's own, the package made the effect worse (the body is now an inner scroller at
  every width, whose scroll position is lost with the element), and the package is where
  the test met it and was bent around it.
- What a person loses, read from the code:
  1. Focus. The old panel and its fields are removed; the new `Panel` effect runs with
     `prev = None`, takes `active_element()` as the opener (by then `body`, or the detached
     old field) and calls `focus_first`, which focuses the panel itself (neither log dialog
     passes `initial_focus`). Keys typed after that go nowhere; Tab starts again at the
     first control.
  2. The place in the form. `[data-dialog-body]` is a new element with `scrollTop = 0`:
     with ten players the person at "Score of Player 10" is back at the date chips.
  3. Text that lives in the DOM and not in `PlayState` / `WatchedState`: what was typed
     into "Add a person" and not yet entered.
  4. The return of focus. The opener recorded by the new effect is `body` or a detached
     node; `restore_focus` drops both, and the log dialogs pass no `return_to`. After Save,
     Cancel or Escape the focus stays on `body`. The package's criterion "return of focus
     ... as today" holds only while no refetch happened.
  5. A screen reader announces the dialog (name and description) again in the middle of
     the form, because focus moved to the `role="dialog"` element.
  6. Not accessibility, same cause: `funnel::sheet_flow` runs again with `prev = None`
     and counts a second "intent" for one opening.
- WCAG: 2.4.3 Focus Order is not met in this state (focus is moved, without any action of
  the person, to a place from which the sequence starts over, and is not returned to the
  opener on close). 3.2.2 On Input does not apply by its wording (nothing the person set
  causes it); the change of context is unrequested, which is the concern of 3.2.5 (AAA).
  2.4.3 is AA and binding here.
- Failure scenarios (each one is a normal use, not a test artefact):
  1. Search a board game in the palette and open it. The page shows "Loading details"
     (`item.state == "stub"`). Click "Log a play" at once (`AddBar` opens the dialog for an
     item without an entry, `item.rs:562-568`) and type a name into "Add a person". The
     enrichment finishes, `entity.updated` arrives, the page refetches: the typed name is
     gone, focus is on the panel, the next keys are lost.
  2. Game night, two rounds: save a play, click "Log a play" again within about a second
     (longer on a slow connection, and once more when the event's refetch arrives). This is
     what the test does.
  3. The dialog is open and another tab, device or the import changes the same item.
  4. Any of the above, then Save: focus is on `body`, a keyboard user starts from the top
     of the page.
- Suggested fix (app):
  1. Mount the two dialogs once, in `ItemPage`, outside the keyed `<For>` and the
     `Transition`, next to `TagEditor` and `ListPicker`, which already live there with their
     state in `ItemUi` (`item.rs:150-151`). Their state is already page-owned
     (`ui.watched`, `ui.play`); what they still take from one render is `ItemInfo`, the
     model and the play title. Put those into `ItemUi` as a signal that `ItemView` (or a
     memo over `data` and `kinds`) updates, compared with `PartialEq` so that an unchanged
     answer notifies nobody. The dialogs read the values that change with a refetch
     (`rating`, `note`, `finished`, `last_duration`) untracked when they open and when they
     save, as they do today through `StoredValue`. Key the mount on what is fixed for an
     item (item id, progress model, verb, board game, title), so a client-side navigation
     to another item builds new dialogs and a refetch of the same item does not.
     `FormDialog`'s `description` is a plain `String`; with the key above it can stay one.
  2. Deferring the refetch while a dialog is open is not enough: a fetch already under way
     when the dialog opens (scenario 2) still replaces the view when it answers.
  3. Test: take the `toPass` and its comment out of `inView` again. Add the regression test
     that states the rule: open the play dialog, focus a field in the lower part of the
     form, type into "Add a person" without entering, cause a refetch (`page.request` posts
     a change to the item and the test waits for the `/_fn/item_page` response, the pattern
     of `library.spec.ts:239-252`), then expect the same field focused, the typed text
     still there, the body's `scrollTop` unchanged, and after Escape and Discard the opener
     focused. It must be red on today's build for the right reason.
  4. Run the whole chromium project again afterwards. The log says it was not run after the
     test-only change, and that `target/site` predates the formatting.

### OT2B-2 (medium) In a low window the fields get no room: the body shrinks to nothing between header and footer

- Where: `ui/src/dialog.rs:101-115` (`FORM_PANEL` has a maximum height and no overflow,
  `FORM_HEADER` and `FORM_FOOTER` are `shrink-0`, `FORM_BODY` is `min-h-0 flex-1`);
  `web/src/log_sheet.rs:1088-1107` (the footer also carries the discard question and an
  error list of up to 6 rem). The render test pins it:
  `ui/tests/render.rs` `form_dialog_is_a_bottom_sheet_on_phones_and_centered_from_640`
  asserts that the panel has no `overflow-y-auto`.
- Problem: header and footer keep their height, the body takes what is left of
  `85dvh` (or `100dvh - 2rem`), and nothing scrolls except the body. When header plus
  footer reach the maximum height, the body has a height of zero and the fields cannot be
  seen or scrolled to; whatever does not fit is cut off below the window. The side sheet
  before this package scrolled as a whole (`max-h-[85dvh] overflow-y-auto` on the panel),
  so every part could be reached at any height. Read from the classes, not rendered.
- Failure scenario: a desktop window of 1280 x 1024 at 400 % zoom is 320 x 256 CSS px, the
  viewport WCAG 1.4.10 Reflow names. The bottom sheet may be 217 px high. The header takes
  about 84 px (24 + 18 + 6 + 20 + 16), the footer 77 px (1 + 16 + 44 + 16): 56 px are left
  for the body, 36 px of them for content, one input row. Press Escape on a changed form:
  the discard question (about 100 px with its gap) joins the footer and the body is gone;
  the person is asked whether to discard changes that can no longer be seen. A failed save
  (error list) or "You are offline" above the full-width Save does the same in part. A
  phone in landscape at or above 640 px wide (667 x 375) keeps about 190 px and is fine
  until question and errors are both shown.
- Suggested fix: let the panel scroll as a whole when it is too low, and only then: add
  `overflow-y-auto` to `FORM_PANEL` and give `FORM_BODY` a floor (`min-h-32` instead of
  `min-h-0`). In a window of normal height nothing changes (the body shrinks first and
  scrolls inside); below the floor the panel scrolls and the footer is no longer fixed,
  so it still covers nothing (2.4.11). Adjust the render test (the panel may scroll, the
  body has a minimum height) and add a Playwright step at 320 x 256: with the discard
  question shown, the first field can be scrolled into view and Save can be reached.

## May defer

### OT2B-3 (low) The error list in the footer scrolls but cannot be scrolled by keyboard

- Where: `web/src/log_sheet.rs:1092` (`max-h-24 overflow-y-auto` on the `ul role="alert"`).
- Problem: the list has no focusable content and no `tabindex`. `PlayForm::payload` pushes
  one error per player whose score is not a number (`web/src/log_form.rs:266-273`), plus
  date and duration.
- Failure scenario: ten players, the scores pasted with a unit ("42 pts"): twelve lines in
  a box of 96 px. A keyboard user in a browser that does not make scrollers focusable
  (Safari) cannot read past the fourth line (WCAG 2.1.1); an axe run in that state reports
  `scrollable-region-focusable`.
- Suggested fix: `tabindex="0"` and the focus ring on the list while it overflows, or one
  line per kind of error ("5 scores are not numbers") with `aria-invalid` on the fields,
  which also removes the need for the maximum height (see OT2B-2).

### OT2B-4 (low) The add bar is enabled again before the refetched page replaces it

- Where: `web/src/item.rs:588-589` (`adding.set(false)` on success, then `refresh.run(())`,
  which refetches 300 ms later). DEC-568 names this as not closed.
- Failure scenario: "Want to watch", the answer arrives, and within the 300 ms plus the
  fetch a click on "Mark as watched" still hits the old `AddBar`: `run_first_step` runs as
  for an item outside the library, the toast says "..., added to your library" a second
  time, and its Undo (DEC-561) takes the watch back, finds the entry Planned without
  events and removes it, although the person added it on purpose with the first button.
  The mirror case: `log_step` resets `busy` after a first log (`web/src/next_step.rs:268`)
  before the refetch arrives; "Want to watch" in that window answers "Added to your library
  as Planned" for an entry that is Completed (the second half of OT2A-8, now only inside
  this window).
- Suggested fix: a signal `done` in `AddBar`, set when either action succeeded and part of
  `either`; the bar is replaced by the refetched page, so it never needs to be cleared.
  `adding` and `busy` keep their meaning (the spinner), and `log_step`, which other callers
  share, stays as it is.

### OT2B-5 (low) DEC-568: the Undo of the add toast reads, then removes (two requests)

- Where: `web/src/next_step.rs:384-394` (`undo_add`).
- Judgement: acceptable to commit as it is. The window is one round trip between the
  answer of `item_page` and the arrival of `library_bulk`; the change must come from the
  same account in that time. OT2A-8 as reviewed (seconds between the toast and Undo) is
  closed, the test `item.spec.ts` "one add at a time ..." covers the keep path through the
  server, and `page.progress` includes the session events, so a play counts as a change.
- Failure scenario for what is left: on a slow mobile connection (round trip of a second or
  more) Undo is tapped and, before the removal is answered, "Mark as watched" is tapped on
  the still enabled bar: the watch is logged and the entry removed, in either order; the
  toast says "Undone". The history keeps a watch of an item that is not in the library.
- Suggested fix (later, with the next server change to the library): a use case "remove if
  untouched" in `app`, one request, the check inside the transaction; `undo_add` then only
  maps its three answers. Until then, disabling the action bar while an Undo runs would
  close the same-tab case.

### OT2B-6 (low) The new focus test does not reach the branch it names

- Where: `ui/tests/wasm.rs`, `form_dialog_traps_focus_over_body_and_footer_and_returns_it`:
  `key_with_shift(&el("w-fd-first"), "Tab")` with the message "Shift+Tab from the first
  control wraps to the last".
- Problem: the key event is dispatched on the first field, but `trap_tab` looks at
  `document.activeElement`, which is still the panel (asserted three lines above). The
  wrap happens through `at(panel)`, not `at(first)`. The later list of ids is the DOM order
  from `querySelectorAll` and says nothing about the Tab handling.
- Failure scenario: a change that breaks `at(first)` (Shift+Tab on the first field leaves
  the dialog and lands in the page behind it) keeps this test green.
- Suggested fix: `el("w-fd-first").focus()` before the Shift+Tab, and one more step that
  focuses `w-fd-save`, sends Tab and expects the close button not to be skipped (no wrap
  from a middle stop).

### OT2B-7 (low) The OD-01 assertions allow more than the DEC states

- Where: `src/web/tests/item.spec.ts`, in "the log dialogs are centered ...":
  `expect(await inputs(watched)).toBeLessThanOrEqual(5)` and the same for the play dialog.
- Problem: DEC-567 states 2 inputs for the watched dialog and 5 for a board game play with
  one player; the package text asks for "5 inputs as it opens". The test accepts anything
  up to 5 for both.
- Failure scenario: the rating moves out of "More" in the watched dialog (3 inputs, a
  change of the approved layout): green.
- Suggested fix: `toBe(2)` and `toBe(5)`.
