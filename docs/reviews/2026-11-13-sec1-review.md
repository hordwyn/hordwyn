## Must fix before commit

### SEC1-1 (medium) The one-off failure of item.spec.ts:333 is a race in the spec; two places have it

- Where: `src/web/tests/item.spec.ts:379-388` (the failure of the progress log) and the same
  pattern at `src/web/tests/item.spec.ts:1196-1197`.
- Problem: the spec holds `**/_fn/item_page*` in a route handler (`await pageHeld; await
  route.continue()`), then calls `show()` and at once `await page.unroute(...)`. `unroute`
  removes the last pattern of the page; the Playwright server then removes its interceptor
  and continues every route that handler still holds
  (`setNetworkInterceptionPatterns` -> `removeRequestInterceptor` ->
  `notifyRoutesInFlightAboutRemovedHandler` -> `Route.removeHandler` ->
  `continue({isFallback: true})`, which sets `_handled`). When the spec's own
  `route.continue()` for such a route reaches the server after that, `Route._startHandling`
  asserts "Route is already handled!". Which message arrives first is a matter of timing
  (and of whether a second `item_page` request is held or arrives at that moment).
- Answers to the questions asked: it is a test-harness race, not an application race (the
  server and the page do nothing wrong; the error is thrown by the test's own handler). The
  new fixture does not cause it: `fixtures.ts` registers no route, only a console listener,
  a binding and an init script; the racy lines are unchanged from HEAD. At most the fixture
  shifts timing a little.
- Failure scenario: the whole suite is the gate of every package; it failed once in three
  whole runs here (sec1-progress.md) and will again, on any package, with a message that
  points nowhere near the cause.
- Fix (test only, three lines each): use the pattern the same file already has at
  `item.spec.ts:988-991`: `const answered = page.waitForResponse((r) =>
  r.url().includes("/_fn/item_page")); show(); await answered; await page.unroute(...)`.
  Alternative: `await page.unrouteAll({ behavior: "wait" })`.
  Note: the lines are older than sec1; if the orchestrator wants the sec1 commit free of
  them, fix them in their own commit right before it. The progress log should say
  "explained" in place of "not explained".

## May defer

### SEC1-2 (medium) The Playwright guard has no standing proof that it still fires

- Where: `src/web/tests/fixtures.ts:61-85`, `src/web/tests/global.setup.ts:102-107`.
- Problem: the guard was seen red twice by hand (strict policies), but no test in the suite
  fails when the guard goes blind. It depends on details that an upgrade can change: the
  override of the built-in `context` fixture, the instance patch of `browser.newContext`
  (and that `browser.newPage()` calls it), the binding, the wording of Chromium's console
  message.
- Failure scenario: a Playwright upgrade creates the built-in context on another path or
  renames the console text; every spec stays green while a later package adds an inline
  script without nonce that only fails on the owner's instance.
- Fix: one canary test that must see a violation: open a context with
  `browser.newContext()`, `page.route` one URL and fulfil it with an HTML document whose
  header is `Content-Security-Policy: script-src 'none'` and which has an inline script,
  then `expect(policyViolations.length).toBeGreaterThan(0)` and empty the array
  (`policyViolations.length = 0`) so the teardown passes. A second canary for the built-in
  `page`.

### SEC1-3 (low) The check "every spec uses the shared fixtures" can be passed by accident

- Where: `src/web/tests/global.setup.ts:104-106`.
- Problem: the pattern is `from\s+"@playwright\/test"` on `*.spec.ts` and `*.setup.ts` only.
  A spec with single quotes, with `require("@playwright/test")`, or one that takes `test`
  from a helper module that re-exports the Playwright one is not found.
  `tests/helpers.ts` itself imports from the package (only `expect` and `request` today).
- Failure scenario: a formatter change or a new spec written with single quotes runs
  without the guard and nobody notices.
- Fix: match both quote kinds and `require(`/`import(`; include every `*.ts` under `tests/`
  except `fixtures.ts`, and for those allow type-only and `expect`/`request` imports only.
- Not a defect: a spec can ask for the `policyViolations` fixture and empty it. That is a
  visible, deliberate act (and what the canary of SEC1-2 needs).

### SEC1-4 (low) A missing file under /pkg answers the HTML 404 page with `no-cache`, not `no-store`

- Where: `src/rust/apps/server/src/lib.rs:949-960` (`pkg_no_cache` sets `no-cache` on every
  `/pkg` answer, also the 404 page), `src/rust/apps/server/src/security_headers.rs:183`
  (a directive that is already there is kept).
- Problem: DEC-658 says every `text/html` answer is `no-store`. This one is a page with a
  nonce and, for a signed-in visitor, the shell with their name; `no-cache` lets a cache
  keep it (it only has to ask before reuse).
  `tests/it/security_headers.rs:477-481` pins the `no-cache`.
- Failure scenario: a browser keeps the 404 page of `/pkg/app.<old hash>.js` after an
  upgrade, with the name of the person in it; history navigation may show it without
  asking the server, also after sign-out. Small: nobody navigates there on purpose.
- Fix: in `pkg_no_cache` set the directive only for a non-HTML answer (or only for 200 and
  304), so the header layer puts `no-store` on the 404 page; adjust the test.

### SEC1-5 (low) `style-src-attr 'unsafe-inline'`: accepted for now, but the reason in DEC-656 is too short

- Where: `security_headers.rs:136`; the four sources: `crates/ui/src/progress.rs:56`,
  `crates/ui/src/rating.rs:152`, `crates/web/src/widgets.rs:105-114`,
  `crates/web/src/admin/mod.rs:281-283`.
- What it allows someone who can inject markup: declarations on the injected element only.
  That is enough for an overlay (`position:fixed; inset:0`) that covers the page with a
  fake form or link, for hiding content, and for a request to any https host through
  `background:url(...)` (no more than `<img>` under `img-src https:`). It does not allow
  selectors, so no reading of attribute values through CSS (that needs a style sheet, and
  `<style>` needs the nonce, `<link>` this origin), and it runs no script. DEC-656 names
  only the last point.
- Is reworking the four places small enough to do now: no. The widths and placeholders are
  rendered on the server and again in the browser: after hydration `style:width` goes
  through the CSSOM (never blocked), but `style=...` strings and cloned templates go
  through the attribute, so all four components need another technique on both sides
  (`<progress>`/SVG `width` attributes for the bars and stars, an `<img src="data:...">`
  or a nonce'd rule per cover for the placeholder, classes for the swatches), with visual
  re-tests of 553 uses. That is its own small package.
- Failure scenario (why not to forget it): a later markup-injection bug in a title or a
  note gives a full-page phishing overlay on an internet-facing instance although scripts
  are blocked.
- Fix now: add the overlay case to DEC-656 and open a follow-up item. Fix later: the
  rework above, then drop the directive.
- References: https://www.w3.org/TR/CSP3/#directive-style-src-attr ,
  https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/style-src-attr

### SEC1-6 (low) The server trusts hash.txt without looking at the site root

- Where: `src/rust/apps/server/src/infra.rs:196-208`, `src/rust/apps/server/src/main.rs:135`.
- Problem: `bundle_hashes` answers "hashed" whenever the file exists, and never checks that
  the files it names are in `<site root>/pkg`.
- Failure scenario 1 (development, real today): `cargo leptos build --release` wipes
  `target/site` and writes `target/release/hash.txt`; Playwright then starts
  `target/debug/server`, which reads the older `target/debug/hash.txt`; every page names
  bundle files that are gone, nothing hydrates, the whole suite fails with timeouts.
  Scenario 2: the reversal DEC-659 describes (`hash-files = false`) leaves the old
  `hash.txt` in `target/`, same effect.
- Fix: at start, read the `js`, `wasm` and `css` lines and refuse to start (same message
  style) when `<site root>/pkg/<output name>.<hash>.<ext>` is missing. That also protects
  the image should the two build steps ever disagree.

### SEC1-7 (low) HSTS: the setting cannot take the header back, and the page does not say how

- Where: `security_headers.rs:84-86`, `docs/modules/ROOT/pages/reverse-proxy.adoc:70-74`,
  `config/.env.example` (HSTS key).
- Problem: `0` sends no header. A browser forgets the rule only when it receives
  `max-age=0` over https (RFC 6797 6.1.1); the application cannot send that.
- Failure scenario: the owner tries the instance under an https name with the default of
  one year, then wants the same host on plain http (or moves the name to another service
  without TLS): every browser that saw it refuses for a year, and setting `0` changes
  nothing.
- Fix: one sentence on the proxy page: to take it back, let the proxy send
  `Strict-Transport-Security: max-age=0` over https for a while (application setting `0`).
  Optional: a separate value that sends `max-age=0`.
- Reference: https://www.rfc-editor.org/rfc/rfc6797#section-6.1.1

### SEC1-8 (low) "The proxy sets none of them" leaves the proxy's own answers bare

- Where: `docs/modules/ROOT/pages/reverse-proxy.adoc:36-39` and the Caddy and nginx
  snippets.
- Assessment: the statement is safe and consistent for everything the application answers
  (the layer is the outermost of both routers, verified in `lib.rs:457-468` and
  `lib.rs:861-862`), and a second policy at the proxy would indeed break the pages. Not
  covered: what the proxy answers itself (502/504 while the container restarts, its own
  error pages) and the case that somebody takes the layer out again (the reversal of
  DEC-655).
- Failure scenario: during an upgrade the proxy's 502 page is the only answer for a while;
  it carries no `X-Frame-Options`, no `nosniff`, no HSTS. Harmless content, so low.
- Fix (docs only, optional): show the "only if the answer has none" form for Caddy
  (`header ?X-Content-Type-Options nosniff`, `header ?X-Frame-Options DENY`,
  `header ?Strict-Transport-Security "max-age=31536000"`), never for
  `Content-Security-Policy`; say that nginx has no such form and stays without.

## Checked, no finding

Policy (CSP Level 3, https://www.w3.org/TR/CSP3/ ; MDN
https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy ):

- Nonce: 16 bytes from `getrandom` (`crates/auth/src/lib.rs:272-276`, the OS CSPRNG),
  base64url, made in the layer once per request (`security_headers.rs:209-216`), never
  stored. Leptos first makes its own (`leptos_axum` `provide_contexts`), the page context
  replaces it afterwards (`lib.rs:805-813`), and the streamed chunks read it with
  `use_nonce()` (`leptos_integration_utils` lib.rs:169-181). The test
  `every_inline_script_and_style_carries_the_nonce_of_the_answer` reads the whole streamed
  body of six pages including the 404 page and can fail. Every HTML answer is `no-store`
  (exception: SEC1-4). https://www.w3.org/TR/CSP3/#security-nonces
- `'wasm-unsafe-eval'`: the right keyword for compiling WebAssembly without `eval`;
  justified by "Red 1" of the progress log; `'unsafe-eval'` is absent and a test says so.
  https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src#unsafe_webassembly_execution
- `script-src 'self'` next to the nonce: needed for the `import()` of the bundle and the
  preload. Uploads are served from this origin, but as pictures and with `nosniff`, so
  they do not load as scripts. The JSON config block needs no nonce (a data block is not
  run).
- `img-src 'self' data: https:`: as broad as DEC-640 and v1-plan P7/B9 ask; the price is
  that injected markup can call any https host (same as before the policy). `http:` is
  added only when `public_url` is not https (`security_headers.rs:79-90,120`), tested both
  ways. No `blob:` needed: no object URLs in `crates/web` or `crates/ui`.
- `connect-src 'self'`: all `fetch` and the `EventSource` use relative addresses
  (`rest.rs`, `events.rs`, `funnel.rs`). No `<audio>`, `<video>`, `<iframe>`, worker or
  service worker in the app, so the `default-src 'self'` fallbacks break nothing.
- `form-action`: `'self'` plus sanitised origins (`source_expression`, tested with a
  header-injection string); the list is filled at start (`install_env` -> `sync_hosts`,
  `lib.rs:754`) and on every provider change.
- `base-uri 'none'`, `object-src 'none'`, `frame-ancestors 'none'` plus
  `X-Frame-Options: DENY` (which also holds in report-only mode, where a browser ignores
  `frame-ancestors`): correct.
  https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors
- Report-only: same policy and nonce under the other header, closed policy on data
  answers too, the other headers stay; tested. No report endpoint (written down).
- The closed policy on non-HTML answers does not disturb the bundle, the stylesheet, the
  wasm file, fonts, pictures in `<img>` or the event stream (a policy on a subresource is
  not applied to the page that uses it). The sign-in interstitial
  (`crates/web/src/auth_redirect.rs`) has no inline script or style.

Coverage of the layer: outermost in `guarded`, applied to the base router and the page
router; one listener only (`main.rs:140-148`). Headers go on the answer head before the
body streams, so streaming pages and the event stream have them. Not covered by design:
answers hyper writes itself for a malformed request.

HSTS: only for an https `public_url`, age from the setting, no `includeSubDomains`, no
`preload`; a second header from a proxy is ignored by browsers (RFC 6797 8.1). Sound; see
SEC1-7 for the way back.

`Referrer-Policy: same-origin`: share, invitation and reset addresses no longer leave the
instance; the cross-site guard does not read `Referer` (`csrf.rs` has no such use) and
same-origin posts keep their `Origin`; the OIDC round trip does not depend on a referrer.
Cover hosts get no referrer, which the providers in use accept.

`no-store`: the offline queue is not touched (it lives in the page and posts to
`/api/v1/sync/commands`; there is no service worker and no HTTP-cache use). Known price,
acceptable and in line with DEC-658: browsers keep such a document out of the
back/forward cache, so "back" to a document from another site reloads it, and offline it
shows the browser's error page; in-app navigation is client-side and not affected.
(https://web.dev/articles/bfcache ) The public list page is `no-store` too; correct,
because a signed-in visitor's shell is in it. `/api/` has no picture or file route that
would now lose caching (`/assets` and `/brand/fonts` keep `immutable`). No permanent
redirects exist in the code.

Hashed bundle: would the image start? By the cargo-leptos v0.3.11 source: yes.
`--frontend-only` wipes the site, builds, runs `add_hashes_to_site`, which creates the
directory of the executable and writes `target/release/hash.txt`; `--server-only` neither
wipes the site nor hashes again. The Dockerfile copies the file next to
`/usr/local/bin/server`, where leptos looks (`current_exe().parent()`), and a missing
file fails the image build at `cp`, not at run time. Not run here. `immutable` goes only
to 200 answers whose name has 22 base64url characters between name and extension;
`snippets/` and unhashed names keep `no-cache`. The hash in the JS name is taken before
cargo-leptos rewrites the wasm name inside it; harmless, because the page passes the wasm
address to the bundle explicitly.

Rules: ASCII only in the new and changed lines; no brand string in code; DEC-655..660 are
the next free numbers and in the six-column format; no function over 100 lines found in
the diff; no change outside the package (the `allow` change in `crates/auth/src/oidc.rs`
belongs to the form targets). The server tests skip without `TEST_DATABASE_URL` (project
convention); with a database each of them can fail.
