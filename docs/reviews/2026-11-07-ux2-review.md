# UX phase 2: independent review of "why is nothing happening, and the admin area"

Date: 2026-11-07. Reviewer: a fresh session that did not produce any of the code. Scope:
`git diff add6203` (tag `ux1`) plus the uncommitted working tree (`git status`, `git diff`),
excluding the untracked `crates/testkit/fixtures/import/legacy/`, against `docs/HANDOFF.md`
sections 2 and 4, `docs/design/ux/design.md` section 9 "Phase 2" with 3.7, 4.1-4.4, 5.1,
5.2, 5.7, 6.1, 6.4, 6.10, 6.12-6.15, `docs/design/ux/addendum-1.md` 2.2-2.5 and 3.1-3.6, the
mockups `admin`, `sources`, `signup`, `palette`, and `docs/DECISIONS.md` DEC-243 to DEC-269.
Read-only: nothing was compiled or run (the orchestrator runs `cargo xtask ci`); evidence is
`path:line` relative to the repository root (`src/rust/` dropped for Rust paths).

Coverage note, so nobody over-reads this review: the security core (secrets envelope, key
loading, admin operations, wizard, re-auth, lock-out guards, REST and server-function
routes, DTOs, audit, Postgres admin store, middleware, CSRF) was read line by line, and the
test-to-behaviour map (UX2-12) was built from every phase 2 test file. Two fan-out audits
(the Leptos admin and settings pages for accessibility, reflow and Fluent dynamic keys; the
catalog-core, connector, notify and config secret flow) had not reported when this file had
to be written. Those areas are listed under "not independently checked" at the end; the e2e
specs' own axe and 360 px assertions were read, the rendered pages were not.

## Summary verdict

Phase 2 is substantially built and the hard parts are right. The envelope is the one the
addendum asked for: AES-256-GCM in both layers, a fresh DEK and fresh nonces per value, the
AAD `sb1|purpose|row|field` (`|dek` for the wrap), fixed offsets with the key version
readable without decrypting, a key file created with `create_new` and mode 0600, file before
env before generate, a refusal to start when encrypted rows exist and no key is found, re-wrap
that leaves the value ciphertext untouched, `Debug` that prints versions only, and a golden
vector (`crates/auth/src/secrets.rs`). Every sign-in related admin operation checks the fresh
proof server-side before it does anything (`update_settings` for gated keys, `set_role`,
`set_disabled`, `delete_user`, `totp_begin`), the window slides by 15 minutes and caps at 60
from the proof, `POST /auth/reauth` regenerates the session id and is throttled like
sign-in, recovery codes are argon2id and single-use. The lock-out guards refuse own role,
disable and delete changes and the last admin who can still sign in; disabling deletes the
sessions and sign-in refuses the account. The wizard is a real install lock: step 1 is 409
once any account exists, steps 2-4 are admin-only, every wizard call is 404 `setup_done`
after completion and the page renders `NotFound` with a 404 status, a signed-out visitor after
the first account sees "sign in first", and the 303 redirect spares `/_fn/`, `/pkg/`, dotted
paths, `/healthz` and the API. The CSRF guard wraps both the REST router and the Leptos
page and server-function routes. No DTO carries a secret value; members get the short
vocabulary with zeroed counters; per-user credentials are read only for the caller. ASCII,
the white-label grep, Fluent parity (1071/1071 web keys, 49/49 notify keys), the dependency
licences (`aes-gcm`, `zeroize`: Apache-2.0 OR MIT) and the commit messages are clean.

Two things should be fixed before tagging `ux2`: with Postgres and the `memory` asset
backend the server seals TOTP seeds and channel secrets with a throwaway key and empties the
plain column, so the next restart locks every authenticator out (UX2-1); and the "Ask admin"
notification, the one path a member has to the admin, links to a route that does not exist
(UX2-2). The rest is a handful of spec items that were cut without a DECISIONS line (hosting
mode after the wizard, the CLI escape hatches, audit client address), small correctness
nits, and the usual long view functions.

## Findings

### UX2-1 (major) A Postgres instance with the `memory` asset backend encrypts secrets with a throwaway key and empties the plain columns

Evidence: `apps/server/src/admin_wiring.rs:43` sets `ephemeral: config.storage.backend ==
assets::Backend::Memory && !explicit_file`; `crates/auth/src/secrets.rs:457-463` returns a
generated in-memory key when `ephemeral` is set, and that branch sits before the
`has_encrypted_rows` refusal at `:464-468`, so existing encrypted rows do not stop it. The
start-up then runs `seal_plaintext` (`apps/server/src/lib.rs:326`), which encrypts every
plain TOTP seed with that key and sets `totp_secret = NULL`
(`crates/auth/src/pg.rs:513-527`), and the same for channel secrets. After the next restart
a new throwaway key is generated, every row is `locked`, and every TOTP user gets "the
authenticator cannot be checked right now" for good; `has_encrypted_rows`
(`crates/auth/src/admin_pg.rs:79-88`) is never consulted on that path. The `memory` backend
is documented as "for tests and demos only" (`crates/assets/src/config.rs:279-280`) and is
listed as an ordinary option in `docs/modules/ROOT/pages/configuration.adoc:160`; the
ephemeral key is tied to where images are stored, not to whether the database persists.
DEC-244 says "in-memory storage without a key uses a temporary key" without naming this
consequence.

Recommendation: use the ephemeral key only when nothing persists: refuse to start (the
existing `MissingKey` message) when `has_encrypted_rows` is true or when any `SecretRows`
reports plain rows to seal, even with `memory` storage; or require an explicit
`APP__SECRETS__EPHEMERAL=true` for the test harness and keep the file-or-env rule for every
other start. Test: `load(&eph, true)` must fail, and `seal_plaintext` must not run with
`KeySource::Ephemeral`.

### UX2-2 (major) The "Ask admin" notification links to a page that does not exist

Evidence: `crates/api/src/admin/sources.rs:321` emits the `admin.source_requested`
notification with `.link("/settings/admin/sources")`; the routes are `/admin/sources`
(`crates/web/src/app.rs:200`, `crates/web/src/admin_state.rs:15`) and there is no
`/settings/admin/*` route. Design.md 4.4 makes this the member's only recourse ("Ask admin
emits the existing admin notification path"); the admin opens the inbox row and lands on the
404 page. No server test asserts the link (`apps/server/tests/admin.rs:542` checks the event
and the dedupe only).

Recommendation: `.link("/admin/sources")`, and assert the link in
`credentials_status_ask_admin_and_search_reasons`.

### UX2-3 (minor) The hosting mode cannot be changed after the wizard

Evidence: DEC-255 says "hosting mode stays in the setup wizard"; the wizard is 404 after
completion (`crates/api/src/admin/setup.rs:24-36`, `crates/web/src/setup.rs:62-74`); no
admin page sends `instance.hosting` (`rtk proxy grep -rn hosting crates/web/src/admin` is
empty), although `update_settings` accepts the key (`crates/api/src/admin/mod.rs:67-73,
540-601`). design.md 4.1 ("`config` gets one new setting and the admin UI edits it") and
addendum-1 3.4/3.5 ("the hosting switch is edited on Admin > Instance") expect a place for
it; a home install that becomes hosted later can only switch through the REST API or
`APP__INSTANCE__HOSTING`. DEC-255 records the split but not that the switch is gone.

Recommendation: a two-card radio (the wizard's `HostingCard`) on Overview next to the
hosting line, or on Security; or a DECISIONS line that says the mode is wizard-and-env only
until the Instance page of phase 3.

### UX2-4 (minor) The CLI escape hatches and the key-file reload are not built and not recorded

Evidence: addendum-1 3.3 lists `cli admin promote`, `cli admin reset-password`,
`cli admin disable-sso-only`, `cli secrets status`, `cli setup reopen`, and 2.2 lists
`cli secrets status | rotate | prune` and "sends SIGHUP; the key set is re-read on reload".
`apps/cli/src/main.rs:23-27` has no admin or secrets command; nothing in the tree handles
SIGHUP. `docs/HANDOFF.md:302` says the package "recorded ... CLI escape hatches ... left for
phase 3", but no entry in DEC-243 to DEC-269 mentions them (`rtk proxy grep -in 'cli
admin\|cli secrets\|setup reopen\|sighup' docs/DECISIONS.md` finds nothing). Without
`cli admin promote` the only recovery from a lost last admin is SQL.

Recommendation: one DECISIONS entry naming each command and the reload as phase 3, or build
`cli admin promote <username>` and `cli secrets status` now (both are a few lines over
`App::set_role_unchecked` and `secrets_status`).

### UX2-5 (minor) Audit rows never carry the client address or the request id

Evidence: `crates/api/src/admin/mod.rs:292-293` writes `client_addr: None, request_id:
None` for every row; the columns exist (`crates/store-pg/migrations/0016_admin.sql:115-116`)
and addendum-1 3.4 lists "client address, request id" in the audit row. DEC-253 is silent.
The CSV export (`mod.rs:969-987`) does not include them either.

Recommendation: carry `client_addr` (from `ConnectInfo` behind the trusted-proxy rule) and
the request id in `Caller`, fill them in `audit`, and add both columns to the CSV; or record
the omission in DEC-253.

### UX2-6 (minor) Wizard step 3 shows a rejected database key as "set by environment"

Evidence: `crates/api/src/admin/setup.rs:88-91` maps `CredentialState::Invalid` to
`"env"` for `SetupSourceDto.credential`; `Invalid` is reached by any key the provider
answered 401/403 to, from the environment or from the database (DEC-246). `read_only` at
`:122-125` then treats such a source as environment-set, so a wizard whose only typed key was
rejected can turn step 3 into the read-only summary (`crates/web/src/setup.rs:239-243`),
with the "no key" line when `env_var` is absent (`setup.rs:275-278`).

Recommendation: decide `"env"` by `a.config.source_env.contains_key(&info.id)` and map
`Invalid` to `"invalid"` (add the key family value), or keep the origin next to `Invalid` in
the registry.

### UX2-7 (minor) Long view functions and uncommented lint allows (KICKOFF 4, HANDOFF 8)

Evidence (counted from `fn` to its closing brace): `crates/web/src/admin/users.rs:329`
`UserRow` 109 lines, `crates/web/src/admin/sources.rs:180` `Credential` 101,
`crates/web/src/auth_pages.rs:463` `SignUpFields` 102 (grew with the `setup` prop),
`crates/web/src/shell.rs:397` `AccountMenu` 126 (grew with the settings and admin entries).
`Server::build` is 160 lines but carries a reasoned `#[allow(clippy::too_many_lines)]`
(`apps/server/src/lib.rs:198-200`). `#[allow(clippy::needless_pass_by_value)]` without a
comment at `apps/server/src/web_admin.rs:24`, `crates/auth/src/admin_pg.rs:19, 24`,
`crates/auth/src/pg.rs:28`, `crates/notify/src/pg.rs:43` (the same allow in
`crates/api/src/admin/mod.rs:231-232` has one). UX1-9 made the same point.

Recommendation: split `UserRow` (the row menu as its own component) and `AccountMenu` (the
two link groups), move the `setup` branch of `SignUpFields` into a helper, and give each
allow its one-line reason.

### UX2-8 (minor) Overview health is computed in the request; the probes table of addendum-1 3.4 is not recorded as cut

Evidence: `crates/api/src/admin/mod.rs:1428-1461` runs `store.ping()`, `budget.report()`,
`lane_counts()` and `secrets_status()` (which sums `version_counts` over three tables) on
every Overview request; addendum-1 3.4 says probes "run on the `background_refresh` lane
every 60 s and are read from a table, never computed in the request". The third-party rule
("pages never wait on third parties") holds, because `sources_row` reads the in-memory
counters; DEC-247 records the in-memory counters but not this.

Recommendation: accept for phase 2 and record it with DEC-247 (the identity-provider and
mail probes of phase 3 will need the table anyway).

### UX2-9 (nit) CSV export: formula injection and no download header

Evidence: `crates/api/src/admin/mod.rs:957-963` quotes commas, quotes and newlines only;
`actor_name`, `target_id` and `detail` go through unchanged, so a value starting with `=`,
`+`, `-` or `@` (a username may start with `-`, an invite note is free text in `detail`)
runs as a formula in Excel and LibreOffice. `admin_routes.rs:498` sets `text/csv` without
`Content-Disposition`.

Recommendation: prefix such fields with `'` (OWASP CSV injection), add
`Content-Disposition: attachment; filename="audit.csv"`.

### UX2-10 (nit) Locked rows ahead in id order can stop the re-wrap of rows behind them

Evidence: `crates/auth/src/admin_pg.rs:488-497` selects the first `limit` rows not on the
active version ordered by id, and `rewrap_all` (`crates/api/src/admin/mod.rs:1073-1082`)
stops a purpose as soon as a batch re-wraps nothing. A batch made of 100 locked rows (say,
after a restore with one old key missing) ends the loop with the re-wrappable rows after
them untouched, and `locked` counts the last batch only. The same shape in
`crates/auth/src/pg.rs:550-567`.

Recommendation: keyset paging (`WHERE id > $last`) until the select is empty, counting locked
rows once each.

### UX2-11 (nit) Small races and side effects

Evidence:

- `require_fresh` slides the window (`crates/auth/src/fresh.rs:110-111`) before the lock-out
  checks run, so a refused `self_role_change` or `last_admin` still extends the proof
  (`crates/api/src/admin/mod.rs:725-734`).
- `use_signup_invite` returns `Ok(())` when the invite is no longer open
  (`crates/auth/src/fresh.rs:290-296`) and `sign_up` has already created the account
  (`crates/auth/src/lib.rs:384-440`); two sign-ups racing on one single-use invite both
  succeed. The companion-invite path maps the conflict to `InvalidInvite`; this one does not.
- `setup_account` checks `user_count` and then calls `sign_up`
  (`crates/api/src/admin/setup.rs:158-174`); two racing first sign-ups both pass the count
  and the second becomes a member only because `sign_up` recounts (`lib.rs:393`), which is
  fine, but the wizard step is then written by both.

Recommendation: check the guards before `fresh`; make `use_signup_invite` a conditional
update (`WHERE used_at IS NULL AND revoked_at IS NULL`) that fails with `InvalidInvite` when
nothing was updated; a unique partial index on the first admin is not worth it.

### UX2-12 (minor) Behaviours without a test (rule 4)

Evidence (from the test-to-behaviour map; each exists in code, none has an assertion):

- `reauth_required` over HTTP is asserted for `auth.session_days` only
  (`apps/server/tests/admin.rs:351-363`); sign-up mode is `fixed_by_config` in that test

- The re-auth throttle (`crates/auth/src/fresh.rs:164, 183`) and a recovery code through
  `POST /auth/reauth` are untested; `shell.spec.ts` covers the sign-in lock-out only.
- The cron registration of `secrets.rewrap` and `admin.audit_retention`
  (`apps/server/src/handlers.rs` `schedule_admin_jobs`) and the two handlers; `POST
  /admin/secrets/rewrap` asserts only "not 401/403" (`admin.rs:220`).
- Server start with encrypted rows and no key, and the `seal_plaintext` wiring
  (`apps/server/src/lib.rs:326`): unit and store level only (`secrets.rs:654-662`,
  `crates/auth/tests/pg.rs:117-148`).
- Members: `GET`/`DELETE /me/credentials` over HTTP, "never visible to admins", the zeroed
  counters; a member calling `/setup/hosting|sources|complete` (the member loop at
  `admin.rs:204-240` omits `/setup/*`); the signed-out visitor at `/setup` after the first

- Settings: a change taking effect without restart (the tests read the DTO back, never sign

- Axe at 360 px on the eight admin pages: `admin.spec.ts:57-62` is reflow only (axe runs at
  the default viewport, `:46-55`); `/settings/*` has axe at 360 and no reflow check.
- The password-change flow through the server function, the privacy switch toggle, the

- `global.setup.ts:68-74` skips the wizard walk silently on a reused server, so the

Recommendation: a server test that calls each gated route with an aged session and expects
403 (one `psql` update of `reauth_at`, as the e2e spec does), the disable/delete variants of
`last_admin`, the member and signed-out variants of the wizard, and axe at 360 px in the
admin loop; the rest can ride along with the DECISIONS line for UX1-11.

## What was checked and holds

- Secrets envelope (addendum-1 2.2, DEC-244): format byte, version at bytes 1-2, wrap nonce,
  wrapped DEK with tag, data nonce, ciphertext and tag at fixed offsets
  (`crates/auth/src/secrets.rs:30-40, 257-298`); AAD per purpose, row and field with `|dek`
  for the wrap (`:111-113, 216, 240, 283`); fresh DEK and nonces from the OS per value
  (`:269-272`); decryption of another slot, an unknown version, a wrong key, a short blob
  and every flipped byte fails as `SecretLocked` (`:508-558`); rewrap keeps
  `blob[DATA_NONCE_AT..]` and proves readability on the active version (`:334-352`);
  `Debug` of the ring and the options prints no material (`:94-100, 380-388`); the key file
  is created with `create_new` and mode 0600 and never overwritten (`:398-414`), a readable
  file is warned about (`:416-427`); file wins over env with a log line, env next, generate
  last, refusal when rows exist (`:438-476`, except UX2-1); golden vector (`:625-639`).
  `has_encrypted_rows` covers `credentials.totp_secret_enc`, `notify_channels.secret` and
  `connector_credentials` (`crates/auth/src/admin_pg.rs:79-88`). The dev key lives in the
  git-ignored `.dev/` (`.gitignore:14-15`), `config/.env.example` names
  `APP__SECRETS__KEY_FILE`, `APP__SECRETS__KEYS` and `APP__INSTANCE__HOSTING` with empty
  values (rule 8).
- Re-authentication (DEC-249, DEC-191): window end is `min(last + 15 min, proof + 60 min)`
  (`crates/auth/src/fresh.rs:77-84`); `require_fresh` also refuses unknown and expired
  sessions and reads the role from the user row (`:99-116`); `reauth` is throttled by
  username, uses the dummy hash for password-less accounts, runs the TOTP or recovery step,
  and regenerates the session id while deleting the old one (`:134-188`); sign-in, sign-up
  and password change count as proofs (`crates/auth/src/lib.rs` `create_session(.., "password")`,
  `:733-734`). Server-side gates: `update_settings` when any key is gated
  (`crates/api/src/admin/mod.rs:564-566`), `set_role` (`:725`), `set_disabled` (`:761`),
  `delete_user` (`:798`), `totp_begin` (`crates/api/src/admin/setup.rs:326-328`, also the
  REST route `crates/api/src/routes.rs` `totp_begin`); `reauth_required` maps to 403
  (`crates/api/src/error.rs`). Recovery codes: 8 of 10 Crockford symbols, argon2id, used once
  through a conditional update (`fresh.rs:39-66, 217-245`), returned once from
  `totp_confirm`.
- Lock-out guards (DEC-250): `self_role_change`, `self_disable`, `self_delete`, `last_admin`
  counting only admins who are not disabled (`mod.rs:682-702, 713-818`),
  `secure_cookies_need_https` on the effective value (`:573-581`), `fixed_by_config` before
  any write (`:558-563`); disabling deletes the sessions (`fresh.rs:252-264`) and sign-in
  answers `account_disabled` (`lib.rs:557-558`); the password change signs out the other
  sessions and keeps the caller's.
- Setup wizard (DEC-252, DEC-266): `setup_state` needs no session only while no account
  exists, admin otherwise (`setup.rs:108-120`); `setup_account` 404 after completion and 409
  once any account exists (`:154-164`); hosting, sources and complete are admin-only and 404
  after completion (`:189-262`); the step is stored for resuming (`:177, 216, 233, 251`);
  completion is audited. The middleware redirects only page requests without a session while
  no user exists, inserts `SetupGate` for `/setup` (`crates/web/src/backend.rs:51-89`), and the
  page sets 404 from the gate and renders `NotFound`, `SignInFirst` on
  `unauthorized`/`forbidden` (`crates/web/src/setup.rs:62-104`); the setup gate degrades to
  "users exist, completed" on a storage error (`apps/server/src/web_backend.rs` `setup_gate`),

- Authorisation and CSRF: every admin operation starts with `require_admin` (`mod.rs`,
