## Must fix before commit

### OT2A-1 (medium) "Log a rewatch" on an entry completed by hand does not raise the count

- Where: `app/src/next_step.rs:137-150` (`counted.max(u32::from(completed))`),
  `web/src/item.rs:282` (`finished` for the dialog line), `web/src/item_words.rs:133`.
- Problem: a Completed entry without a finished event counts as 1, and the first logged
  finish also counts as 1 (`max(1, 1)`). The button, the dialog and the header then disagree
  about the same number: the step is "again" because the entry is Completed
  (`step_of`, `again: summary.finished > 0 || completed`), but the count ignores that.
- Failure scenario: a movie is set to Completed in the status select (or arrives Completed
  from an import without events). Header: "Watched once". The button says "Log a rewatch",
  the dialog is titled "Watched again" but shows no "This will be watch number 2" line
  (`finished` is 0). The person clicks "Log a rewatch": toast "Logged: Watched again", header
  still "Watched once, on <today>". The next dialog says "Watched once before. This will be
  watch number 2." although a rewatch was just logged. The same holds for every single,
  paged and timed kind and for a show completed by hand.
- Suggested fix: decide one rule and use it in all three places. Either (a) the hand-set
  completion is a pass of its own: count `finished + 1` when the first effective finished
  event carries no `status_change` to Completed (the entry was Completed before it), or (b)
  it is not: then the step of a Completed entry without a finish is not "again". Feed the
  dialog line from `ItemPageDto.times` instead of `summary.finished`, and add the case
  "completed by hand, then one finish" to `times_counts_whole_passes_per_model` (today the
  test only has `times(true, .., &[])` and `times(true, .., three)`).

### OT2A-2 (medium) A show that is only up to date reads "Watched once, finished on ..." under an "In progress" pill

- Where: `web/src/item_words.rs:103-117`, `app/src/next_step.rs:154-166` (`passes`).
- Problem: `fact_line` prints the count line as soon as `times > 0`, and for a show
  `times` is 1 as soon as every known regular episode has one view, whatever the status.
  ux-owner-test.md 1.2 (the table the owner approved with OT-5 a) has two different rows:
  "All watched, not completed: In progress, Up to date: 24 of 24 episodes" and "Completed:
  Watched once, finished on <date>". The first row cannot be reached any more when all
  episodes are watched; `item-fact-up-to-date` only shows for a show with gaps
  (`next_episode` looks at the last episode, `passes` at all of them). The unit test
  `the_fact_line_follows_the_progress_model` asserts the deviating text.
- Failure scenario: a season is still airing, six episodes are known, the person has watched
  all six. Pill: "In progress". Line: "Watched once, finished on 9 Nov 2026". The show is
  not finished and the app cannot know that it is (DEC-207, R-23). A week later episode 7
  is known and the line falls back to "6 of 7 episodes": the "once" is gone again.
- Suggested fix: pass the status (or `completed`) into `Facts`; for the episodic model use
  the count line only for a Completed entry, otherwise "Up to date: N of N episodes" on
  `caught_up` and the plain progress else. Keep `times` as the server computes it. Adjust
  the unit test to the two rows of the table.

### OT2A-3 (medium) Undo after "Mark as watched" on an item outside the library leaves it in the library as Planned

- Where: `web/src/item.rs:531-545` (`AddBar`, first button), `web/src/next_step.rs:186`
  (`run_step`), server: `app/src/library.rs:222` (the first log calls `add_to_library`),
  `undo_progress` reverts the status move only.
- Problem: the first log creates the entry as Planned and moves it to Completed in the same
  call. Undo takes the event and the status move back, not the entry. The toast says
  "Undone", the page then shows the pill "Planned" and "Added on <today>". Rule 2 of the
  model ("every add is confirmed and reversible") is met for "Want to watch" only: this add
  is neither said nor taken back.
- Failure scenario: the person opens a search hit, clicks "Mark as watched" by mistake,
  clicks Undo. The movie is now in the library as Planned and shows up in the Planned
  filter and counts; nothing on screen said that it was added.
- Suggested fix: in `AddBar` remember that the entry did not exist and give the toast an
  Undo that undoes the event and then removes the entry (the `library_bulk` "remove" that
  `toast_added` uses), or say so in the toast ("Logged: Watched. Added to your library.").
  Add the step to `item.spec.ts` "an item outside the library ...", which today tests Undo
  for "Want to watch" only. If it stays as it is, record it in DEC-554.

### OT2A-4 (medium) The "Log these N again?" question loses the focus on Cancel and takes it back on every refetch

- Where: `web/src/episode_list.rs:530-573` (`AskAgain`), lines 556 and 567.
- Problem 1 (2.4.3): the question moves the focus to its first button. "Cancel" and "Log N
  again" set `ui.again` to `None`, which removes the group with the focused button; nothing
  returns the focus. `AskPrevious` has no Cancel, so this path is new.
- Failure scenario 1: keyboard user, "Mark season watched" on a watched season, focus lands
  on "Log 10 again", Tab, Enter on "Cancel": the group is gone and the focus is on the
  document; the next Tab starts at the top of the page.
- Problem 2: the effect at line 533 focuses the first button whenever the component is
  built while `ui.again` is set. `EpisodeList` is rebuilt by every refetch of the page (the
  `For` key in `item.rs` carries the version), and `ui.again` lives outside it.
- Failure scenario 2: the question is open; the person first sets a rating (the rating
  refetches the page, `item.rs:725`) or picks "Spread over a date range" and a tag change
  or an `entity.updated` event arrives: the focus jumps from where they are to "Log 10
  again". Enter then logs ten rewatches that were not meant.
- Suggested fix: keep the element that asked (the button or the row menu trigger; a
  `data-` marker and `keyboard::focus` are enough) and focus it on Cancel; after "Log N
  again" focus the season's mark button once the list is back. Focus the question only when
  `ui.again` is set by `bulk()` (a one-shot flag next to the signal), not on a rebuild.
  Extend the browser test: after Cancel the trigger is focused.

### OT2A-5 (medium) A browser test was routed around an app race

- Where: `src/web/tests/item.spec.ts:432-436`; the package log, "Final state", item (c).
- Problem: the last part of the bulk test used the row menu ("More for S1 E1", "Mark up to
  here"). After "Log 10 again" the page refetches once per logged event and the open menu
  was detached, so the test failed. The test now uses "Mark season watched", "a button
  that survives the re-render". The app behaviour was not changed. The brief does not allow
  test workarounds for app races, and the removed step was the only place where the
  question is raised from the row menu after a bulk log.
- Failure scenario: a person logs a season again and opens the menu of a row right after
  the toast: the menu closes under the pointer when the next of the ten refetches lands; a
  click aimed at a menu item goes to whatever is below it.
- Suggested fix: fix the cause (one refetch after a bulk log instead of one per event: the
  page already refetches in `log_episodes` when the loop ends, so the `entity.updated`
  refetches of the own events can be held while `ui.busy` is set), then restore the row
  menu step. If the orchestrator decides to keep the race for now, restore the row menu
  step behind an explicit wait for the settled page and record the race with an owner in
  the handoff; do not leave the swap as a silent change.

### OT2A-6 (medium) The video game test cannot fail on "scores are behind More as the dialog opens"

- Where: `src/web/tests/item.spec.ts:297`.
- Problem: `if ((await more.getAttribute("aria-expanded")) === "true") await more.click();`
  closes "More" when it is open and only then asserts that the score field is hidden and
  that there is one text box. The acceptance criterion is that the dialog opens with three
  inputs (DEC-557, OD-01). The board game test eleven lines of logic earlier asserts
  `aria-expanded="false"` directly (`item.spec.ts:251`).
- Failure scenario: a change makes the disclosure of a non-board game start open (or mounts
  `Scores` outside it): the dialog opens with scores and winner visible, the test closes
  "More" itself and passes.
- Suggested fix: replace the conditional by
  `await expect(more).toHaveAttribute("aria-expanded", "false")` (a fresh account has no
  stored disclosure state), keep the rest.

## May defer

### OT2A-7 (low) The date of the count line is the newest event, not the pass it names

- Where: `web/src/item_words.rs:106-116` (`summary.last_at`).
- Failure scenario: a show was completed on 1 Oct; on 9 Nov the person watches S1 E1 again
  with "Again". Line: "Watched once, finished on 9 Nov 2026". Same for a book completed by
  hand that is being read again: "Read once, on <day of the last page log>".
- Suggested fix: send the day with the count (`times_last_at`: the newest finished event,
  or for a show the day the last pass became whole), or drop the date when it cannot be
  attributed. Fits ot2e, which has to compute passes per run anyway.

### OT2A-8 (low) Two adds or an add and a log can overlap, and the add toast's Undo then removes more than the add

- Where: `web/src/item.rs:526-570` (two independent `busy` / `adding` signals),
  `web/src/next_step.rs:307-336` (Undo is "remove the entry").
- Failure scenario: "Want to watch", then within the 10 s of the toast "Mark as watched"
  (the bar is the normal action bar by then), then Undo on the first toast: the entry is
  removed together with its status and a rating set meanwhile; the watch stays in the
  history and the page offers "Log a rewatch" for an item that is not in the library. Also:
  a click on both `AddBar` buttons before the first answer arrives shows "Added to your
  library as Planned" for an entry that is Completed.
- Suggested fix: disable both `AddBar` buttons while either runs; let the Undo of the add
  toast remove the entry only while it is still Planned without events (else say that it
  can no longer be undone).

### OT2A-10 (low) "Log N again" with "On release dates" logs the rewatch on the first-run dates; a refused date choice drops the question

- Where: `web/src/episode_list.rs:554-558`, `258-266`. DEC-556 chooses "the date choice of

### OT2A-13 (low) `button_classes.rs` can skip a file's literals, and knows one button look only

- Where: `web/tests/button_classes.rs:32` (`src.split('"').skip(1).step_by(2)`).
- Problem: a char literal `'"'`, an odd number of `\"` or a raw string with quotes flips
  which segments count as literals for the rest of the file. `web/src/auth_redirect.rs:17`
  has `.replace('"', "&quot;")`: every class list after that line of that file is not
  looked at. The detector also needs `rounded-md`, `font-medium`, `px-N` and `bg-primary`
  or `border-input` together; a hand-written button with `border-border` or `bg-secondary`
  passes.
- Failure scenario: someone adds `<a class="... rounded-md bg-primary px-4 font-medium">`
  below line 17 of `auth_redirect.rs`: the test stays green.
- Suggested fix: skip `'"'` and `\"` before splitting (or scan with a small state machine),
  and add a detector case for a file that contains a quote char literal.

### OT2A-14 (low) "0" is a valid duration

- Where: `web/src/log_form.rs:176`; the test asserts `parse_duration("0") == Ok(Some(0))`.
- Failure scenario: "0" (or "0:00") typed to clear a prefilled duration is stored as
  `duration_minutes: 0`; the History row and the later hours of ot2c/ot2f count a play of
  zero minutes instead of a play without a duration.
- Suggested fix: map 0 to `None`.
