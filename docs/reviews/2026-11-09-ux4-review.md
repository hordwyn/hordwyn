## Summary verdict

The shape of phase 4 is right and most of it holds up under reading. The statistics cache is
one migration with statement-level triggers over transition tables, a per-user zone stamp
and a lazy recompute under `FOR UPDATE`, and its incremental statement is the full statement
restricted to the dirty items (same predicates, same window partitions, same bucketing); the
cache test walks every step the plan asked for. Activity reads sessions in keyset windows,
library pages are keyset-paged with a sort-checked opaque cursor and every statement still
filters on the caller, the fair-share gate orders by lane, round, arrival, remove-from-library
deletes the entry and its tags only, the bulk API fails per id without leaking, the undo token
can only write into the caller's own library, the offline queue reuses the online op ids and
after DEC-455 carries queue-time stamps so another device's later change wins, the funnel's
beacon and table have no user, item or free-text column and every word is allow-listed, goals
are private with "N of M in YYYY" and nothing on Home, game groups check the owner and follow
merges, the probes are read from a table, source counters are additive across processes, the
emailed link is hashed, bound to the asking browser's ticket and single use, the admin menu is
gated, audited in the transaction and notifies the person, the TMDB season endpoint and fields
are what the doc records with terms 1.C and 1.D quoted, the catalog race is closed in the
database with a test that really races, and UX3-25 was reproduced by the new guard, explained
from the leptos sources and fixed. ASCII, white-label, Fluent parity (1831/1831, 57/57),
licences and commit messages are clean, and DEC-399 to DEC-459 say where the test came after
the code and what was cut.

What should be fixed before tagging `ux4`: a dirty mark can be lost when a write's trigger
runs before the reader's `DELETE ... RETURNING` and commits after the recompute, leaving the
statistics silently stale (UX4-1); fair share lets a steady stream of single requests from
other users starve a burst's queued tail (UX4-2) and the gate still leaks a permit when a
waiter is cancelled after it was handed one (UX4-3); the UX3-25 panic guard runs only under
`cargo xtask e2e`, not in the CI job, and deletes the log even when it found a panic (UX4-4);
undoing any bulk op rewrites status, rating, notes and tags with fresh stamps, so an "Add tag"
undo reverts every change made in between (UX4-5); sign-out leaves the offline queue in
`localStorage` unsent and unannounced (UX4-6); every bulk Remove is counted as an abandoned
funnel flow, which skews the numbers the four-week review depends on (UX4-7); and the final
load record (UX4-8) is one release run with search at 290 ms and a writer count that fell
from 1262 to 326 without comment. The rest is spec deviations without a DECISIONS line, minors
in the admin menu, the emailed link, the undo token, the retention policy and the keyboard
layer, and the usual long functions and untested branches.

## Findings

### UX4-1 (major) A dirty mark can be lost between a writer's trigger and the reader's recompute

Evidence: every marking trigger inserts with `ON CONFLICT DO NOTHING`
(`crates/store-pg/migrations/0023_stats_cache.sql:73-80, 91-98, 109-113, 126-131, 151-154`).
The reader takes the dirty set with `DELETE ... RETURNING` (`crates/store-pg/src/repos/stats_cache.rs:104-110`)
and recomputes in later statements of the same READ COMMITTED transaction (`:156`,
`insert_item_months`). Sequence: pair (u, i) is already marked and committed; writer T_w
inserts an event, its trigger finds the committed row and does nothing (DO NOTHING takes no
row lock and only waits when the conflicting row is uncommitted or being deleted at that
moment); reader R deletes the row and recomputes while T_w is still uncommitted, so the new
event is not in the snapshot; both commit; no mark remains. DEC-400's "a write committing
later stays marked" holds only when the trigger runs after the DELETE. The window is the
writer's transaction (`crates/store-pg/src/repos/library.rs:465-502`, audit); two writers at
20/s against readers that refresh on every stats read (load run (d)) make it reachable, and
the result is persistent and invisible until the next write on that item or a zone change.

Recommendation: `ON CONFLICT (user_id, item_id) DO UPDATE SET item_id = EXCLUDED.item_id` in
the five trigger functions (the update locks the row for T_w's life, so R's DELETE waits until
T_w commits and the recompute then sees the event; if R deleted first, T_w waits and inserts).
A two-connection test in `phase1.rs`: open T_w, insert an event, run a stats read on another
connection, commit T_w, assert the next read equals `month_amounts_full`.

### UX4-2 (major) Fair share: rounds restart at 0 for every idle user, so a burst's queued tail can starve

Evidence: `crates/catalog-core/src/gate.rs:95-104` sets `round` to one above the user's
currently queued interactive waiters, else 0; the heap orders by lane, round, arrival
(`:36-42`). A search fans out one request per connector for one user at rounds 0..N-1
(`crates/catalog-core/src/search.rs:161-162`, audit). Any other user whose previous request
has already been served arrives at round 0 and is placed before every queued waiter with
round >= 1. With a steady stream of single requests from other users, user A's round 1..N-1
waiters, and so A's whole search, wait until the heap holds no round-0 waiter. DEC-402 says
"served in turn" and tests one arrival pattern only (`gate.rs:197-228`: A x5, then B x1).

Recommendation: keep a per-lane "current round" (the round of the last waiter popped in
`release`, or the heap's minimum) and assign `round = max(own_last_round + 1, current_round)`;
test B issuing one request at a time while A has five queued and assert A's fifth is served
by position <= 10.

### UX4-3 (major, pre-existing) The gate leaks a permit when a waiter is cancelled after it was handed one

Evidence: `crates/catalog-core/src/gate.rs:118` (`let _ = rx.await;`) and `:124-129`
(`release` pops waiters and returns as soon as `tx.send(())` succeeds; `available` is not
incremented). If the handler future is dropped between the send and its next poll (client
disconnect, axum cancellation), the permit travels into the dropped receiver and the lane is
one permit smaller for the life of the process. `cancelled_waiter_does_not_leak_the_permit`
(`:175-187`) aborts before `release`, not in this window. The shape predates ux3 (the diff adds
`round` and `user` only), but WP4-1 rebuilt `acquire_for` and the hosted mode now routes every
member's search through it.

Recommendation: a guard around `rx` whose `Drop` does `try_recv()` and calls `gate.release()`
on `Ok(())`; a test that holds the permit, queues a waiter, drops the permit and aborts the
waiter at once, then asserts `acquire` succeeds within a timeout.

### UX4-4 (major) The UX3-25 panic guard does not run in CI, and the log is deleted even when it found a panic

Evidence: `.gitlab-ci.yml:140` runs `CI=1 npx playwright test` directly;
`src/web/playwright.config.ts` redirects the server's stdout and stderr only when
`E2E_SERVER_LOG` is set (`const serverLog = process.env.E2E_SERVER_LOG` and the
`command: serverLog ? ... : serverCmd` ternary in the diff), and only `cargo xtask e2e` sets
and scans it (`xtask/src/main.rs:207-236`). In the CI job a `panicked at` line is discarded
and the run passes. `main.rs:220` removes the file before the panics are reported, so a
reproduced panic leaves nothing to attach. Plan WP4-8 asked that "e2e captures the server log
... and fails the run"; DEC-456 describes the xtask path only and does not say CI is uncovered.

Recommendation: run `cargo xtask e2e` in the job (or set `E2E_SERVER_LOG` there and scan with
`xtask::e2e_log::panics`), keep the file when a panic was found and add it to the
`on_failure` artifacts; say in DEC-456 which runner has the guard.

### UX4-5 (major) Undoing any bulk op rewrites status, rating, notes and the whole tag set with fresh stamps

Evidence: `crates/app/src/bulk.rs:362-371` (`restored` builds `status`, `rating` and `notes`
as `Lww::new(.., self.stamp(None))` and replaces the tags with the snapshot's), `:316-317`
(`write_many`), and `crates/store-pg/src/repos/library_page.rs:30-33` (the upsert sets all
three fields). The snapshot (`bulk.rs:384-393`) always carries every field. Undoing an "Add
tag" on 500 rows therefore reverts every status, rating and note changed in between (the item
page, another device's sync, an import) and drops tags added in between, last writer wins
without a check. DEC-417 documents this only for the status undo ("also re-stamps rating and
note"). No test changes something between the op and its undo.

Recommendation: record in `EntrySnapshot` which fields the op touched and have `restored`
write only those (tags for Add/RemoveTag, status for SetStatus, all for Remove), keeping the
old stamps elsewhere; or refuse the undo when the current `*_hlc` is newer than the snapshot's.
Test "change in between, then undo" per op.

### UX4-6 (major) Sign-out leaves the offline queue in `localStorage`, unsent and unannounced

Evidence: sign-out is a plain form POST (`crates/web/src/shell.rs:235` and the form at
`:611-612`, audit); nothing calls `Offline::flush` or clears the key.
`crates/web/src/offline.rs:316-325` keeps the record under `app-offline-<username>` (`:220-222`)
whenever items exist, and the shell only provides the queue for a signed-in person
(`shell.rs:350-353`). Pending changes stay on the device until the same username signs in on
that browser (from the person's view the changes are lost), and on a shared browser the next
person can read the previous person's queue (titles, statuses, ratings) in devtools. Design.md
5.4 and DEC-432 do not mention sign-out.

Recommendation: in the sign-out submit handler, flush first when online and clear the key
after the push settles; when offline or still non-empty, a confirm "N changes are not synced
yet" that lets the person stay; a test in `offline.spec.ts`.

### UX4-7 (major) Every bulk Remove is counted as an abandoned funnel flow

Evidence: `crates/web/src/bulk.rs:294-295` clears `selection.ids` before `run_bulk` is called;
`bulk_flow` (`bulk.rs:213-224`) fires `abandoned_if(Flow::Bulk)` when the count drops to 0 and
again in `on_cleanup` (the `<Show>` at `crates/web/src/library.rs:1141-1142` unmounts the bar
at that moment, audit); `Funnel::finish` ends only the active flow
(`crates/web/src/funnel.rs:254-262`), so the later `logged_if(Flow::Bulk)` after the request
(`bulk.rs:43`) is a no-op. DEC-435 says "a bulk edit -> logged"; the four-week review
(HANDOFF 6) would read every removal as abandonment.

Recommendation: end the flow in the `remove` callback before clearing the selection (or clear
the selection in `run_bulk`'s `Ok` arm through `on_done`); assert the beacon's outcome in
`library.spec.ts` for one remove.

### UX4-8 (major) The final load record is one release run with search at 290 ms and an unexplained fall in writer throughput

Evidence: DEC-459 (`docs/DECISIONS.md:463`): release, 8 clients + 2 writers, search p95 290
ms, Home 207, query first 250, History person 233, against a 300 ms budget that is asserted;
"one run each"; "the 8-client numbers are 10 to 70 percent above the earlier runs on every
endpoint alike ... taken as run-to-run variation of the shared host, not a regression; ...
this is not proven". DEC-404 run (d) recorded "1262 writes", DEC-459 run (d) "326 writes",
while the client phase that the writers run alongside (`apps/server/tests/load.rs:407-424`,
50 ms per write at `:310`, audit) was longer, not shorter; the DEC records writer p95 (80 ms)
but not `n` or `max` (the harness prints them, `load.rs:83-89`). A 4x drop in writes with
longer reads points at blocking, and UX4-1's sibling effect is a candidate: a writer's
`ON CONFLICT DO NOTHING` does wait while a reader's refresh is deleting the same `stats_dirty`
row (`stats_cache.rs:104-173`, up to a full rebuild), and every stats read with writers active
starts a refresh. Honest in the record: the zone-change rebuild at 770 ms debug / 767 release
(target 500) is named in DEC-404, DEC-459 and HANDOFF 3 with its EXPLAIN cause and a reason not
to fix now; "library query, first 100" (250 ms) is explained (full scan for the count) with
the levers listed. Neither has an ID or owner beyond prose in the alternatives column.

Recommendation: before tagging, one more release run of (d) after UX4-1's trigger change,
recording writer `n` and `max`; if search stays near 290 ms, say so and split the search
budget from the page budget (the governed fan-out is provider-bound); give the zone-change
rebuild and the query count follow-ups an entry in HANDOFF 6 or a DEC-pending line; assert
the zone-change read under 1000 ms in the harness so a regression to seconds is caught.

### UX4-9 (major) Retention: TMDB title and year are kept past six months by a judgement not on the owner's list, and unowned items are refreshed forever

Evidence: `crates/store-pg/src/repos/catalog.rs:224-242` (`purge_provider_data` clears
description, original title, attributes, cover, provenance, episodes and stamps; `title`,
`year` and `external_ids` stay). DEC-453 calls this "a judgement left for the owner", but
HANDOFF section 6 "Still open for the owner" (`docs/HANDOFF.md:709-722`) does not list it and
`docs/connectors/tmdb.md` "Caching" presents it as settled; terms 1.C covers "any information
obtained through or from TMDB". Separately, `crates/catalog-core/src/retention.rs:72-93`
queues a refresh (and the server handler a cover re-download, `apps/server/src/handlers.rs:268-283`,
audit) for every stale `tmdb` item while a key is usable, including items in nobody's library
(search results, removed items); library membership (`App::item_in_any_library`,
`crates/app/src/catalog.rs:220-222`, audit) is not consulted, so an unowned, unviewed item costs
one TMDB call and one image download every ~150 days indefinitely instead of being purged.

Recommendation: add the title/year question to HANDOFF 6 and the connector doc (alternative:
copy title and year into the library entry at purge time and blank the catalog row); purge,
not refresh, items with no library entry; a `retention.rs` test for an unowned item.

### UX4-10 (minor) Admin reset-totp and unlink: no self or last-admin guard; "last method" counts identities of disabled providers

Evidence: `crates/api/src/admin/user_menu.rs:42-57` and `:78-101` call `require_admin`,
`target_user` (any id, including the caller's) and `fresh`; unlike `set_role`
(`crates/api/src/admin/mod.rs:929-934`, audit) nothing refuses the caller's own row or the
last admin, only the web hides the menu on self rows (`crates/web/src/admin/users.rs:354-357`,
audit). In `auto` mode the precondition "an admin with password and authenticator"
(`crates/api/src/admin/oidc.rs:598-601`, audit) can be broken silently by resetting that
admin's TOTP through the API. `other_method` (`oidc.rs:686-701`) counts every other
`oidc_identities` row regardless of whether its provider is enabled or still exists, so a
password-less person with identities A (enabled) and B (provider disabled) can have A unlinked
and is locked out.

Recommendation: 409 `self_change` for the caller's own id; re-check the auto-mode precondition
after a reset (refuse or warn in the audit detail); count only identities whose `provider_id`
is an enabled provider; tests for both.

### UX4-11 (minor) Emailed link: the confirm does not re-check the offer conditions, burns the code before the ticket, and link, session and audit are separate writes

Evidence: `crates/auth/src/oidc/email_link.rs:117` discards `has_password`
(`let (t, user, provider, _)`), so a link asked for while password-less still links after a
password was set, although the offer exists only for accounts without one (`:54-56`,
DEC-413). Order at `:119-144`: `claim_sign_in_link` first, then the disabled check, then the
ticket's `claim_once`; a ticket already used burns the code too. `:150-160` `link_identity`
and `create_session_from` are separate calls, and the `auth.link_emailed` /
`auth.link_confirmed` rows are written after the fact (`crates/api/src/oidc_routes.rs:402-409,
452-459`, audit), unlike the WP4-2 admin actions that pass the audit row into the transaction.
The throttle is 3 per account per 15 minutes per process in memory (`email_link.rs:23-25`), so
N web processes allow 3N and a restart clears it; the ticket requirement bounds abuse.

Recommendation: re-check `can_email` in `confirm_email_link` and answer `NoEmail`; claim the
ticket first (or both in one transaction); pass the audit entry into `link_identity` as
`unlink_identity` does; count open `oidc_link` rows in the window instead of memory.

### UX4-12 (minor) The undo token is unsigned client-held JSON with unvalidated `notes`, `added_at` and `entry_id`, can exceed the body limit, and the list half is not atomic

Evidence: `crates/app/src/bulk.rs:97-106` (URL-safe base64 of serde JSON, no MAC); `:369`
copies `notes` without a length check (no notes limit exists, cf.
`crates/app/src/library.rs:156-171`); `:370` takes `added_at` from the token for a new entry;
`:311` uses the client-chosen `entry_id` as the primary key when free. Binding to the caller is
right (`:364`), so no cross-user write, but a forged token creates entries with any
`added_at` and unbounded notes. The 500-row snapshot carries every note
(`:384-393`) and `JSON_BODY_LIMIT = 2 << 20` (`crates/api/src/routes.rs:28`), so an undo can
fail with 413 after the change succeeded, shown as `error-generic`
(`crates/web/src/bulk.rs:67-73`). `:256-260` sets `undo.list` even when nothing was added, and
`undo_bulk` (`:325-333`) errors `NotFound` on a deleted list after the entries were already
written (`:316-317`). `:306-315` runs one `get_by_id` per removed entry (up to 500 round trips).

Recommendation: either store snapshots server-side keyed by id and user with an expiry
(DEC-417's alternative) or HMAC the token with a key from the ring and include user id and
issued-at; clamp `added_at <= now` and add a notes limit; set `undo.list` only when
`list_items` is non-empty and treat a missing list as nothing to undo; batch the id lookup.

### UX4-13 (minor) Offline queue: no cap, the drop toast does not say what was lost, the clock record dies with the queue, and Undo during a flush lies

Evidence: `crates/web/src/offline.rs:173-181` (`push` unbounded; a bulk episode mark is one
command per episode, `crates/web/src/episode_list.rs:120-128`, audit); `:362-368` the
destructive toast is `offline-dropped` plus the title only (not "status Paused"). `:320-324`
removes the whole record when `items` is empty, so `node` and `last` are lost after every
successful flush and `:301-306` mints a new node next time, while DEC-433 says the last stamp
"is kept with the queue so a reload continues it". `save_offline`'s Undo (`:439-452`) removes
the op from the queue, but a flush that already snapshotted the batch (`:354-368`) applies it
anyway and the toast says "Undone".

Recommendation: cap the queue (e.g. 500) with a toast when full; name the command kind in the
drop toast; keep `node` and `last` and empty `items` only (and correct DEC-433 if not);
disable Undo while `flushing` or check `remove`'s `false`.

### UX4-14 (minor) Usage funnel: subjects are free text within a charset, the Privacy line names "settings sections" only, and settings are read per beacon

Evidence: `crates/api/src/usage.rs:85-95` accepts any `a-z-` words of 1..32 characters on each
side of `/`; with 30 beacons per minute (`:32`) of 50 events (`crates/contracts/src/usage.rs:25`,
audit) one signed-in person can create 1500 new primary-key rows per minute
(`0025_usage_funnel.sql:14`, audit) that land in the admin report and CSV (formula injection is
not possible: charset plus `csv_field`, `:225`). `crates/web/locales/en.ftl:2007` says "how
often the settings sections are opened" and `:2012` "each settings section", but disclosures
are measured on the item page (`crates/web/src/log_sheet.rs:315, 644`), the Library
(`library.rs:515`), Stats (`stats_extras.rs:258`) and the gallery (`gallery.rs:560`); "shown"
and "open at a save" are not mentioned. `record` reads the instance settings from the store on
every beacon (`usage.rs:166` -> `:68-79`).

Recommendation: allow-list the subjects from one shared constant (eleven keys exist today) or
cap distinct subjects per day; reword the Privacy line to "how often collapsible sections
(for example the item page's More or the Library filters) are shown, opened and open when you
save"; cache the setting for a minute next to the limiter.

### UX4-15 (minor) Keyboard and layout: bulk bar reflow asserted at desktop width only, the sticky bar can cover the focused row, IME composition ignored, signed-out visitors see signed-in commands

Evidence: `src/web/tests/library.spec.ts:348` says "reflows at 320 CSS px" but no
`setViewportSize` precedes `expectReflow(page, "bulk bar")` at `:356`; the 360 px block at
`:390-393` never opens the bar (plan WP4-3: "axe and reflow with the bar"). The bar is
`sticky bottom-[calc(var(--tab-bar-height)+0.5rem)]` with `flex-wrap`
(`crates/web/src/bulk.rs:304`) and only the item page's `[data-sticky-action]` raises
`scroll-padding-bottom` (`src/web/style/input.css:179-189`, audit), so at 360 px the bar can
sit on the focused row (design.md 8, WCAG 2.4.11). `plain_key` (`crates/web/src/keyboard.rs:98-102`)
does not check `is_composing()`. The empty palette offers "Go to Lists", "New list", "Import a
file" without a `signed_in` check (`crates/web/src/palette.rs:339-346, 606-612`, audit), and
`help_sections` is static (`keyboard.rs:253-268`), so `?` lists `N` and the chords for a
signed-out visitor although `shell.rs:296-300, 328` run them signed in only.

Recommendation: select rows at 360x640 and run `expectReflow` and axe there in both themes;
a `data-sticky-bar` attribute with a matching `scroll-padding-bottom` rule (or non-sticky
below 47.5rem); `&& !ev.is_composing()`; pass `signed_in` into `idle_items` and
`help_sections`.

### UX4-16 (minor) Activity windows: a "watched with" pair can differ from the big read near a page boundary, and the equivalence test compares the new code with itself

Evidence (audit): `crates/app/src/activity.rs:379-386` reads the `above` events and sessions
within `PAIR_SECS` of `before` only; `pair_of` (`:488-503`) takes the newest unused session
within +/-120 s and only `above` events pre-consume sessions (`:515-520`). An event at
`before + 130 s` is outside `above` but would, in one big read, consume a session at
`before + 10 s`; here that session stays free for a window event at `before - 50 s`. Needs two
sessions and two events of one item within about four minutes across a boundary; the test
spaces rows 19 days apart (`crates/app/tests/activity.rs:466`). `activity.rs:490-500` compares
pages against `activity_feed(limit: 100)` of the same implementation, not the ux3 feed, and
the only Postgres coverage of `by_owner_window`/`with_participants_window`/`recent` is one
default page (`crates/store-pg/tests/phase1.rs:278-287`); the keyset comparison
`(s.started_at, s.id) < ($2, $3)` (`crates/store-pg/src/repos/sessions.rs:199, 231`) has no
paging test with equal timestamps.

Recommendation: read `above` with `since = before - PAIR_SECS` and `before = before +
2 * PAIR_SECS` (or document the bound); a test with three rows inside four minutes split by a
page of 1; a `phase1.rs` walk in pages of 1..3 over rows sharing `started_at` compared with
`by_owner` plus `by_user`.

### UX4-17 (minor) The People page reads every session of the owner twice per view; a foreign companion id answers 403 where a foreign group answers 404

Evidence: `crates/app/src/game_groups.rs:67-75` (`sessions.by_owner` to count plays per group
and find the last), called for every People page (`PeoplePageDto.groups`, DEC-442) and again
after each group create or update (`crates/api/src/goals.rs:189-195`, audit); `companion_stats`
(`crates/app/src/people.rs:186`) already does a full read on the same page, and DEC-441 admits
"linear in the caller's sessions; not in the load harness", while DEC-401 removed exactly this
pattern from the activity feed (20 000 sessions in the (b) data set). `game_groups.rs:128-131`
