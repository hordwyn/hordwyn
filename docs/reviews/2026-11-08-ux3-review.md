## Summary verdict

The hard part of phase 3 is right. The multi-provider OIDC flow is PKCE S256 on every
request, the pending state travels in an HMAC-signed cookie derived by HKDF from the live key
ring, is verified against every loaded key, carries a kind so a login value never passes for a
link ticket, expires after 10 minutes and is spent once in a server-side table
(`crates/auth/src/oidc/cookie.rs`, `oidc.rs:729-749`). The callback checks `state`, then the
RFC 9207 `iss` (required when advertised), then lets `openidconnect` verify signature, issuer,
audience, nonce and expiry, refreshing the JWKS once on a signature miss
(`oidc.rs:751-871`). Resolution follows addendum-1 4.2 to the letter: known identity, link mode
bound to the signed-in session and a fresh proof, a verified email leads to "Is this your
account?" with the account's own password and never to an automatic link, then creation with
the sanitised `preferred_username` (`oidc/resolve.rs`). Group rules refuse before resolution,
provider-managed roles are recomputed per sign-in but the last admin is never demoted and a
rule that would demote the acting admin is refused (`resolve.rs:214-250`,
`crates/api/src/admin/oidc.rs:227-244`). Back-channel logout refuses symmetric and `none`
algorithms, checks `typ`, `iss`+`aud` against an enabled provider, the signature with the
provider's keys, `exp`, `iat`, the logout event, the absence of `nonce`, `sub` or `sid`, and
replays of `jti`, and ends sessions by `sid` else by identity (`oidc/sso.rs:581-671`). Sign-out
is local first, then RP-initiated with `id_token_hint` from an encrypted per-session row that
dies with the session (`sso.rs:326-351`, `0019_sso_sessions.sql`). The `auto` mode checks its
three preconditions on the server, exempts `/signed-out`, `/sign-in/local`, `/sign-in/link`,
the wizard, one-time links and shared lists, and the break-glass path admits admins only and
audits and notifies every use (`admin/oidc.rs:544-586`, `sso_routes.rs:90-142, 331-340`).
Return paths are validated once, server side (`cookie.rs:226-239`), and nothing in the
browser trusts an unvalidated `next`. Client secrets, the SMTP password, ID tokens and pending
actions are sealed in the envelope format, registered for re-wrap and never returned by any
DTO (`OidcProviderDto` carries `secret_set`/`secret_locked` only). ASCII, white-label, Fluent
parity (1636/1636), licences and commit messages are clean, and DEC-297 to DEC-366 name their
cuts honestly, including the two items the orchestrator flagged ((b) and (c)).

What should be fixed before tagging `ux3`: `cli secrets prune` does not count OIDC client
secrets or session secrets and can drop a key version that still protects them (UX3-1); the
lock-out hatch `cli admin disable-sso-only` reports success while the environment keeps
`auto` (UX3-2); the History stream really does render the previous page's result under the new
address and remounts on "Load more" (UX3-3, the spec change in WP3-4 hid a bug); the remembered
webhook body misses common secret spellings and token-shaped values (UX3-4); the CSV export has
the formula-injection hole that UX2-9 closed for the audit CSV (UX3-5); and two WCAG 2.2
failures on the new pages (UX3-6, UX3-7). The rest is a handful of spec deviations without a
DECISIONS line, correctness minors in the importers and lists, and the usual long functions
and untested branches.

## Findings

### UX3-1 (major) `cli secrets prune` and `secrets status` do not see OIDC client secrets or session secrets, so prune can drop a key version in use

Evidence: `apps/server/src/escape.rs:108-113` builds the `SecretRows` list from the auth
store, `PgNotifyStore`, `PgAdminStore` and `PgMailSecret` only; the server's list at
`apps/server/src/lib.rs` (`Server::build`, the `secret_rows` vector in the diff) also has
`auth::pg::PgSessionSecrets` (`session_secrets.value`) and `auth::oidc::PgProviderStore`
(`oidc_providers.client_secret`). `secrets_prune` (`escape.rs:336-349`) takes `in_use` from
`self.counts()` over the short list and `prune_key_file` drops every other version
(`crates/auth/src/secrets.rs:546-560`, audit). A version that only an OIDC client secret or a
kept ID token uses is pruned; the next restart loads the pruned file and those rows are
`locked` (the SIGHUP path would have refused: `reload_keys` uses the server's full list,
`crates/api/src/admin/mod.rs` diff). DEC-301 says prune "drops versions that are neither
active nor used by any stored value", which is not true for two of the six purposes.

Recommendation: one `fn secret_rows(pool, cipher) -> Vec<Arc<dyn SecretRows>>` in
`apps/server/src/lib.rs` (or `admin_wiring.rs`) used by `Server::build` and `Escape::open`;
a `cli.rs` test that stores a client secret under v1, rotates, prunes and asserts v1 stays.

### UX3-2 (major) `cli admin disable-sso-only` reports success while the environment still forces `auto`

Evidence: `apps/server/src/escape.rs:222-240` reads and writes the database row only
(`self.admin.settings()` / `put_settings`); the doc comment at `:222-223` promises the error
"The configuration sets the mode (change it there)", but nothing checks the config origin of
`auth.sign_in_mode`. `effective()` lets env and file win (`crates/api/src/admin/mod.rs:575-586`
`sign_in_auto`), so with `APP__AUTH__SIGN_IN_MODE=auto` the hatch prints that the mode is
`page` again and changes nothing. This is the lock-out escape of addendum-1 3.3 and the one
DEC-301 names for an SSO outage.

Recommendation: keep the setting's origin in `Escape` (the config's `origin("auth.sign_in_mode")`)
and bail with the variable name or file path when it is fixed; test it in `cli.rs`.

### UX3-3 (major) The History stream renders the previous page under the new address and remounts on every change (known item (a): a real bug, not a test race)

Evidence: `crates/web/src/history.rs:560-574`: the `<For>` source `each` reads `h.first`,
`h.state` and `h.shown()` and calls `fresh(renders)` on every run
(`crates/web/src/pages.rs:66-69` increments a counter), so every reactive change yields a new
key and remounts the whole `Days`/`NoRows` subtree. On Back the URL state changes first while
`first.get()` still returns the previous page's value (the `<Transition>` keeps the stale
resource), so the previous result ("Nothing logged in this view") is rendered under the new
address with the new `filtered` flag and replaced only when the fetch lands; the transition
holds the old keyed child while the new one mounts, which is the "both in the DOM" the spec
saw. `src/web/tests/home.spec.ts:171-172` now waits for the old text to go, and DEC-337 records
it as "a test race, the view settles". Side effect (audit): "Load more" updates `more`, which
remounts the list and destroys the focused Load more button, a focus loss on every page of
rows.

Recommendation: key the `<For>` on the data identity (the address the page belongs to plus a
fetch generation), gate the empty state on the resource not being pending, append `more.rows`
without remounting; then revert `home.spec.ts:171-172` and correct DEC-337.

### UX3-4 (major) The remembered webhook body misses common secret spellings and token-shaped values

Evidence: `crates/integrations/src/call.rs:15-29`: `is_secret_key` matches `auth` and `key`
exactly and the parts `token|secret|password|passwd|apikey|api_key|authorization|credential`.
Not matched: `x-api-key` (contains `api-key`, neither spelling), `bearer`, `pass`, `pwd`,
`session`, `cookie`. There is no value-based redaction, so an `itk_...` token or a JWT under an
innocent key (`extra`, `url`, `note`) is stored verbatim in `last_payload` and shown on the
sender's card (rule 8; design.md 6.9 "secrets redacted"). DEC-339 lists the parts as the whole
rule.

Recommendation: add `api-key`, `bearer`, `pwd`, `pass`, `session`, `cookie` to the parts;
in `redact` also replace string values that start with `itk_`, `whsec_`, `Bearer ` or look
like a JWT (`eyJ...` with two dots) with `HIDDEN`; extend the unit test at `call.rs:164` and
DEC-339.

### UX3-5 (major) The CSV export has no formula-injection guard

Evidence: `crates/importers/src/generic.rs:160-193` (`csv_text`) writes `title`, `notes`,
`status`, list names and `source_id` as they are; the `csv` crate quotes `,`, `"` and
newlines only. A title or note beginning with `=`, `+`, `-`, `@`, tab or CR (an imported Trakt
note, `crates/importers/src/trakt.rs:179`, or a user's own note) runs as a formula when
`library-export.csv` is opened in Excel or LibreOffice. UX2-9 raised the same for the audit CSV
and that one is now guarded (`crates/api/src/admin/mod.rs:1148-1159`, audit); the new writer
was not.

Recommendation: a `safe_cell()` that prefixes such cells with `'` applied to every free-text
column in `csv_text` (the reader at `generic.rs:76-82` trims, so a leading space would also
round-trip); a test with a title `=HYPERLINK(...)`.

### UX3-6 (major) Keyboard reorder loses focus when a row reaches either end (WCAG 2.4.3)

Evidence: `crates/web/src/lists.rs:412-418` focuses the moved row's own arrow button after
the refetch; `:475-482` renders that button `disabled=first` / `disabled=last`, so after the
move that puts a row first or last the target is disabled, `focus()` is a no-op and focus falls
to `body`. `src/web/tests/lists.spec.ts:67-68` asserts focus after the first move only and not
after the second, where it would fail.

Recommendation: when `index == 0` or `index + 1 >= count` after the move, focus the other
arrow (or the row's title link); assert it in the spec.

### UX3-7 (major) The import file picker has no visible focus indicator (WCAG 2.4.7)

Evidence: `crates/web/src/imports.rs:201-203`: `<input type="file" class="sr-only">` stays in
the tab order and the `<label class=LINK_BUTTON>` beside it gets no ring when the input is
focused; a keyboard user tabbing through the format cards sees nothing move.

Recommendation: `peer` on the input and `peer-focus-visible:ring-2 peer-focus-visible:ring-ring`
on the label (or make the label the button and trigger the input from it).

### UX3-8 (major) Two addendum-1 3.4 requirements for Sign-in and SSO are not built and not recorded

Evidence: (1) the provider table has Provider, Issuer, Status and an actions column
(`crates/web/src/admin/sso.rs:146-155`); addendum-1 3.4's table row for "Sign-in and SSO" lists
"linked accounts" per provider. (2) addendum-1 3.4 "Mobile" asks for admin tables to become
"stacked cards with the same four fields" below the breakpoint; `crates/ui/src/table.rs:22`
is a horizontal scroll wrapper, used by `sso.rs:146`, the Users table, the rules matrix
(`crates/web/src/notify_rules_view.rs:198`) and the delivery log (`crates/web/src/notifications.rs:308`,
audit). The provider detail form sits in a `td colspan=4` inside that wrapper
(`sso.rs:191-195`), so at 360 px the form itself needs two-dimensional scrolling (WCAG 1.4.10
exempts data tables, not the form inside one). DEC-329, DEC-336 and DEC-337 do not list either
deviation.

Recommendation: render the detail form outside the table (a panel under the table or a
sheet), add the linked-accounts count (one `COUNT` over `oidc_identities` per provider in
`oidc_admin`), and record the scroll-wrapper choice for the other tables in a DEC with the
reversal ("stacked cards below 47.5rem").

### UX3-9 (minor) A client behind a trusted proxy can hide its address with one malformed `X-Forwarded-For` entry

Evidence: `crates/api/src/request_meta.rs:109-129`: the chain is parsed with
`.collect::<Option<Vec<_>>>()?`, so one entry that is not an address makes the whole header
`None`, and `of()` (`:134-145`) then records the peer, i.e. the proxy's own address, as
`client_addr`. Proxies append rather than replace, so a client sending `X-Forwarded-For: x`
yields `x, <client>` and the audit row shows the proxy. Also, when every entry is trusted the
leftmost (most client-controlled) one is taken (`:126`); DEC-299 describes neither case.

Recommendation: walk from the right and stop at the first entry that is not a trusted proxy;
when it does not parse, record `None` (or the raw text truncated) rather than the peer; when
all are trusted, record the peer. Unit tests for both.

### UX3-10 (minor) Test of a disabled provider always fails: its issuer host is not on the allowlist

Evidence: `crates/auth/src/oidc.rs:393-421` builds the runtime allowlist from
`providers.iter().filter(|p| p.enabled)` (`:410`), and `discover()` calls `sync_hosts()` before
the fetch (`:512`). `test_provider` (`crates/api/src/admin/oidc.rs:473-527`) runs
`rediscover` on any provider, enabled or not, so an admin who switches a provider off to test
it before enabling gets "failed: oidc_unavailable" from the governed client's host refusal
(`crates/catalog-core/src/http.rs:487`). No test covers a disabled provider's Test.

Recommendation: include the provider being discovered in `allow()` (pass `p` as `extra` like
the document) or let Test add its issuer host for the call; one assertion in
`admin_api_secret_reauth_audit_and_test`.

### UX3-11 (minor) The public back-channel endpoint forces a discovery and JWKS fetch for every token that does not verify

Evidence: `crates/auth/src/oidc/sso.rs:654-669` loops `for force in [false, true]` and calls
`discover(p, true)` whenever no key verifies; the provider is found from the public `iss` and
`client_id` (`:609-617`), so anyone can post a garbage JWS with those two values and make the
instance fetch the provider's discovery document and JWKS twice, up to the 60/min budget
(`:53`, `:121-133`). DEC-319 says "one forced discovery on a miss" without a cooldown.

Recommendation: at most one forced discovery per provider per minute (a timestamp next to
the cache entry), as key rotation never needs more.

### UX3-12 (minor) Password reset: not atomic after the claim, earlier links stay open, rows never pruned

Evidence (audit): `crates/auth/src/recovery.rs:52-62` claims the token with the conditional
update (`crates/auth/src/pg.rs` `claim_password_reset`), then writes the credentials and
deletes the sessions as separate statements, so a storage error after the claim burns the link
without changing the password; `recovery.rs:22-39` creates a new link without invalidating an
earlier open one for the same user; `password_resets` rows are never deleted
(`crates/store-pg/migrations/0017_phase3_instance.sql:29-37`; the retention job covers
`admin_audit` only).

Recommendation: claim and credential update in one transaction (one `AuthStore` method),
revoke other open resets of the user on create, delete expired rows in the retention job.

### UX3-13 (minor) Legacy op ids are position-based, so re-importing a newer export logs every earlier view again

Evidence: `crates/importers/src/legacy.rs:290-294` sets `event_id: None`, and
`crates/importers/src/lib.rs:419-423` then keys the op id by the event's index within the row.
`seen_history` is newest first (`legacy.rs:15`), so one new view at the top shifts every index.
The "second run creates nothing" tests use the identical file
(`crates/importers/tests/legacy.rs:283-290`); DEC-356 claims the stable-id benefit for Trakt
only, but the Imports page offers "Try again" and a new upload for the legacy format too.

Recommendation: derive `event_id` in `legacy::history` from date, progress and the occurrence
count of that pair within the row; a test that prepends one entry to a show and asserts the
old op ids are unchanged.

### UX3-14 (minor) Matching a row while the import is still running loses the match

Evidence (audit): `crates/importers/src/runner.rs:186-223` (`match_row`) checks owner and
`dry_run` but not `state.is_final()`; the running runner holds its own copy of the record and
saves it at every checkpoint (`runner.rs:284, 293`), overwriting the removal from `unmatched`
and the counters, so the row shows as unmatched again although `set_item_for` mapped it.

Recommendation: 409 `import_running` while `!r.state.is_final()` (the shape of `cancel`'s
`import_finished`, `runner.rs:171`); a test with `run_rows(id, Some(n))`.

### UX3-15 (minor) Uploaded import files are kept forever and count against the user's quota

Evidence (audit): `crates/importers/src/runner.rs:79-81` stores the upload at
`up/{user}/imports/{id}` through the budgeted store; nothing in `crates/importers/src` calls
`blobs.delete`, so each file (up to 64 MiB, `crates/api/src/routes.rs:30`) stays until the
quota refuses further uploads.

Recommendation: delete the blob when a real run reaches a final state and no record still
references its `source_key` (a dry run's file is needed for `rerun`), or a retention job;
answer 409 `import_file_gone` for a rerun after that.

### UX3-16 (minor) Known items (b) and (c): recorded honestly, both cheap to close

Evidence: (b) `crates/app/src/activity.rs:375-381` keeps a row for the person filter only when
a participant's `companion_id == p`; entries merged into the person are not matched. DEC-353
records it verbatim. (c) `crates/web/src/lists.rs:540-552` renders `SharedMissing` in the
`Err` arm inside a `<Transition>` and never touches `leptos_axum::ResponseOptions`; the route
is a plain `<Route>` (`crates/web/src/app.rs:209`, default out-of-order streaming), so a status
set inside the resource would arrive after the headers. DEC-351 records the 200. Neither is a
spec breach once recorded, but (c) means a crawler or a link checker keeps a revoked list as
alive.

Recommendation: (b) resolve `p` once per query to `{p} + {c.id | c.merged_into chain reaches p}`
from `companions.by_owner` and test membership against the set (the person page shares the
filter). (c) give `/shared/lists/:token` `SsrMode::Async` (or `PartiallyBlocked` with
`Resource::new_blocking`) and set 404 in the `Err` arm under `cfg(feature = "ssr")`, as
`crates/web/src/setup.rs:62-74` does for the wizard; assert the status in `sharing.spec.ts`.

### UX3-17 (minor) Removing or unlinking a linked person leaves the other side linked

Evidence (audit): `crates/app/src/companions.rs:147-155` ("delete keeps history") demotes the
removed companion only (`crates/domain/src/companion.rs:89-93` clears `linked_user` on that
row); the other user's companion that stands for the actor keeps its `linked_user`, so
`linked_people` (both directions, DEC-349) still treats the two as linked and the other side's
"Shared with me" and `shared_sessions` keep flowing one way. `unlink` at `companions.rs:313-317`
has the same one-sided shape, so this matches DEC-348's "as for unlink", but neither DEC says
the link survives on the other side.

Recommendation: demote the counterpart in both (`companions.linked_to(linked)` filtered to
the row whose `linked_user` is the actor), or say in DEC-348/349 that a link ends only for the
side that acted.

### UX3-18 (minor) Mail settings: the test bypasses the re-auth dialog and a broken transport is accepted silently

Evidence (audit): `crates/web/src/admin/instance.rs:205-219, 244-273` call
`update_admin_settings` and `PUT /admin/mail/password` directly, not through `reauth::gated`,
so a `reauth_required` answer (the hosting radios on the same page are gated) shows as an error
line instead of opening the dialog; `crates/api/src/admin/mail.rs:137-144` `rebuild` only logs
a warning when `configure` fails, so `PUT /admin/settings` answers 200 and mail is off until
someone presses "send a test".

Recommendation: wrap `save_and_test` in `gated`; return the configure error as a `warnings`
entry (or 422) when a `mail.*` key is in the patch.

### UX3-19 (minor) Two local-path checks missing in the browser

Evidence: `crates/web/src/reauth.rs:326-330` and `:344-349` navigate to the `path` returned
by `GET /auth/reauth/pending` without `local_path()`; the value was `here()` when stored, and
`location.pathname` of `https://host//evil/x` is `//evil/x`, so a victim parked on such an
address is sent off-site after confirming (low exploitability, the router 404s such paths,
but every other `next` in the crate is checked). `crates/web/src/lists.rs:576` builds the
shared-list sign-in CTA's `next` without encoding the token (harmless today, the token is
URL-safe; use `sign_in::encode`).

Recommendation: `local_path(&path)` before `go`; `encode` the token.

### UX3-20 (minor) Small WP3-1 inconsistencies

Evidence (audit):

- `apps/server/src/escape.rs:338-345` counts rows, then prunes; a process that has not yet
  received SIGHUP still seals with its old active version, and the CLI says "send SIGHUP"
  after prune (`apps/cli/src/main.rs:352`), not before.
- Every hatch changes first and audits second (`escape.rs:176-183, 189-203, 210-217, 324-330,
  336-349`); an audit failure returns `Err`, so the operator sees an error although the
  promotion or rotation happened. DEC-298 lists them as "after" honestly; the message does not.
- `crates/config/src/lib.rs` (diff, `is_network`) accepts `::ffff:10.0.0.0/104`, while
  `crates/api/src/request_meta.rs:50-61` folds to IPv4 first and rejects a prefix over 32, so
  config validation passes and `Server::build` fails.
- `crates/store-pg/migrations/0017_phase3_instance.sql:39` says NULL "follows the brand
  default, then UTC"; DEC-306 and `crates/app/src/time_zone.rs:20-25` say UTC only.
- `crates/app/src/stats.rs` (diff) passes `zone.name()` into `AT TIME ZONE` (`crates/store-pg/src/repos/library.rs:527`);
  a name chrono-tz knows and the server's Postgres tzdata does not is a 500 on Stats.

Recommendation: refuse prune until `secrets_keys` shows the file's active version was loaded
and say "SIGHUP every process first"; print "<done>; the audit row could not be written" and
exit non-zero; make config call `TrustedProxies::parse`; fix the comment; validate the zone
against `pg_timezone_names` in `set_time_zone` or fall back to UTC on the SQL error.

### UX3-21 (minor) Error mapping and i18n fallbacks

Evidence (audit):

- `crates/web/src/integrations.rs:276` maps every `Err` of "Create sender" (401, 429, 500) to
  `integrations-name-invalid`.
- `crates/web/src/imports.rs:406` renders `t(&format!("status-{v}"))` with `v` from the file
  (`crates/importers/src/row.rs:52-54` does not validate generic statuses), so an unknown
  status shows the raw key `status-foo`.
- `App::unmerge_companion` through a merge chain answers 422 (`DomainError::NotAllowed` ->
  `crates/api/src/error.rs:83-86`), while the route promises 409
  (`crates/api/src/people_routes.rs:79`) and the direct "not merged" case is 409.
- Raw server words as fallbacks (`crates/web/src/admin/sso.rs:89-97`, `imports.rs:458`,
  `notifications.rs:95-105`): every value the server emits today is covered, so forward
  compatibility only.

Recommendation: map by `e.code`; fall back to the raw word for statuses as `event_label`
does; map `ensure_active` to `AppError::Conflict`.

### UX3-22 (minor) E2E: the item seed is racy under lane load (known item (d)); one fixed wait

Evidence (audit): `src/web/tests/item.spec.ts:33-57` runs a real import on the `user_import`
lane (strict lane order, `crates/jobs/src/lib.rs:5`), polls `expect.poll(...).toBe("done")` for
30 s (a `failed` state keeps polling to the timeout), then polls the `background_refresh`
catalog fetch for `seasons` for another 30 s; `src/web/playwright.config.ts:12` is
`fullyParallel: true`, so `people.spec.ts:16-27`, `lists.spec.ts` and `imports.spec.ts` import
at the same time. The seed waits for the row (not a toast) and the titles are per user, so the
flake is lane load, not naming. `src/web/tests/signin.spec.ts:166` asserts "no auto-redirect"
with `waitForTimeout(1500)`.

Recommendation: poll for any terminal state and assert `done`, raise the caps or serialise the
import-seeding specs (`test.describe.configure({ mode: "serial" })` or a dedicated project);
replace the fixed wait with an assertion that the mock's authorize endpoint was not hit.

### UX3-23 (minor) Functions over 100 lines and one uncommented allow (KICKOFF 4, HANDOFF 8)
