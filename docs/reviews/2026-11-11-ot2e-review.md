# Review ot2e (rewatch run), 2026-11-11

Reviewed: the uncommitted working tree against HEAD f565218 (27 changed files, 3 new),
DEC-587 to DEC-589, docs/fable/round2/ot2e-progress.md. Read-only: nothing was built or
run; every statement below comes from reading the code. Paths are relative to `src/rust/`
unless they start with `docs/` or `src/web/`.

Counts: high 0, medium 3, low 11.

## Summary

The package does what the spec asks. The trace in DEC-587 matches the code in all points
but one sentence (OT2E-2 b). No high finding. Two things should be settled before the
commit: a view logged with an earlier date during a run silently falls out of the run
(OT2E-1, reachable from the normal "Watched with..." dialog), and the stop of a run leaves
nothing in the history, so a stopped run comes back to life and keeps collecting views
(OT2E-2); the second is a data-model question that cannot be repaired from stored data
later. The rest may be deferred with a DEC entry.

Load run: not needed (see "Load run verdict").

## Must fix before commit

### OT2E-1 (medium) A view dated before the start of the run is logged but not counted

- Where: `crates/domain/src/rewatch.rs:58-62` (membership by `(occurred_at, id)`),
  `crates/web/src/log_sheet.rs:382` and `:404` (the dialog's date chips, `save_watched`),
  `crates/web/src/episode_plan.rs:65-83` (`season_rows_in`),
  `crates/web/src/episode_list.rs:543` (only the bulk date choice is hidden in a run).
- Problem: the bulk date choice is hidden while a run runs because "a backfilled view sorts
  before the start and would not count" (DEC-589 (2)). The "Watched with..." dialog of the
  action bar and of an episode row still offers "Yesterday" and "Pick a date". The progress
  log lists this under "noticed, not built"; no DEC records it.
- Failure: the person watched S1 E1 last night. Today: "Start a rewatch", then "Watched
  with...", "Yesterday", Save. The toast says "Logged: S1 E1 watched". The header stays at
  "Rewatch: 0 of 24 episodes", the row still reads "Mark S1 E1 watched", the next step does
  not move. Saving again adds a second view that is not counted either. The run can never
  be finished with such views. This is the most likely first use of the feature.
- Same cause, rarer: a start queued offline carries the client's time
  (`web/src/next_step.rs:286`, `offline::now_rfc3339`), the episode logged online right
  after the flush carries the server's time. With the client clock ahead by more than the
  gap between the two (the server allows up to `CLOCK_SKEW_MINUTES`,
  `crates/api/src/ops.rs:425`) the episode sorts before the start and is not the run's.
- Fix (one of): (a) in the dialog, while `summary.rewatch.running`, refuse a date before
  the day of the start with an inline message naming that day (the start event is in
  `page.progress`); (b) let the person move the start: when a view of a running run is
  dated before the start, log it and say in the toast that it is not part of the rewatch.
  (a) is smaller. Add an app test next to `what_is_not_a_run` and a web test for the
  message. For the skew case: when the server logs an episode on an entry whose run is
  running and `occurred_at` was not sent, use `max(now, start.occurred_at + 1 ms)`.

### OT2E-2 (medium) A stop leaves no trace: a stopped run revives, and later views join it

- Where: `crates/domain/src/rewatch.rs:71-78` (every regular episode after the start is the
  run's until a finish), `:99-108` (`phase`: unfinished + In progress = Running),
  `crates/app/src/next_step.rs:148` (`running`), `:190` (`rewatch`), `:219`
  (`completes_run`); DEC-587 (3) "stop = the existing status write".
- Problem: the history cannot tell where a stopped run ended. Three consequences:
  - (a) Revival. Run stopped after 5 of 24 (or started by mistake and stopped at 0). Months
    later a new season arrives and the person sets "In progress" in the status select.
    The header reads "Rewatch: 5 of 34 episodes. Watched once before.", the Episodes tab
    shows 5 watched and 29 open, the next step is S1 E6 instead of S3 E1, the bulk date
    choice is gone. The only way out is Completed; there is no In progress without the old
    run (the start can be undone for 24 hours only). DEC-587 (5) wants "a later In progress
    runs" for the LWW case; this case was not considered.
  - (b) Views after the stop count as the run's. Stopped after 5; one "Again" on a
    favourite episode next week makes the header say "rewatch stopped after 6 of 24
    episodes"; ten first views of a new season make it "15 of 34". The same happens after
    a start whose move lost LWW (it reads as a stopped run with 0 episodes and is the
    newest run from then on). DEC-587 (4), (8) and the new section of
    `docs/modules/ROOT/pages/sync.adoc` say such logs "stay plain extra views"; they do not
    once any run exists. If such views ever cover every known episode the run counts as a
    pass (`over`, `run_passes`) without having been finished.
  - (c) Export and import. Stops are not in the file. Two stopped runs in a row come back
    as one (the second start is replayed on an In progress entry and carries no move,
    `crates/importers/src/runner.rs:565-590`), with the episodes of both.
- Why before the commit: once histories without a stop marker exist, no later change can
  tell where their runs ended.
- Fix (owner decision between two): (1) the stop writes a marker, for example the web
  logs `{"type": "rewatch", "end": true}` (serde default false) before or instead of the
  status write, carrying In progress -> Completed like the finishing episode does; `runs`
  closes the run there; a status write without the marker (old client, select) keeps
  today's behaviour. (2) No new data: a run is Running only while the entry still carries
  the start's status write (`StatusChange::carried`, already there for DEC-588); any
  status chosen by hand ends it for good. That removes (a), costs "pause and resume a
  rewatch", and leaves (b) and (c) as recorded limits. Either way correct the sentence in
  DEC-587 (4) and sync.adoc, and add a domain test "a stopped run does not come back with
  In progress" or, if the revival is kept on purpose, a test that pins it plus a line in
  DEC-589 under the limits.

## May defer (record in a DEC)

### OT2E-3 (medium) Completions in stats and goals now count show rewatches, and only those

- Where: `crates/app/src/library.rs:236-251`, `crates/store-pg/src/repos/library.rs:413`,
  `goals_groups.rs:235`, `stats_cache.rs:257`, `crates/app/src/stats.rs:130-134`,
  `crates/app/src/goals.rs:61`; DEC-587 (9).
- Answer to the question asked: a run does not double-count. One completion per finished
  run (the finishing episode), none for a stopped one, none for the start; undo events
  carry a move since DEC-588 but all three statements filter `x.undoes IS NULL`, and
  `contributions` gets effective events only.
- Problem: a show completed for the first time is completed by hand, which writes no
  event, so it was never a completion in the stats. A finished rewatch is one now. A movie
  watched again is not (`finished` on a Completed entry carries no move).
- Failure: goal "Completions, shows, 2026". Five shows completed this year by status: 0.
  One old show rewatched: 1. The stats measure "Completions" shows the same.
- Fix: decide what the measure means. Smallest: say in DEC-587 (9) that it is accepted
  and open a follow-up for "a status set to Completed by hand counts as a completion".
  Not a blocker: the count for first runs was 0 before this package too.

### OT2E-4 (low) An undo inside a finished run leaves the run finished

- Where: `crates/domain/src/rewatch.rs:75-84`, `crates/app/src/next_step.rs:144` (`over`:
  `finished.is_some()` is enough).
- Failure: 3 episodes, "Log 3 again" (run finished, "Watched 2 times"). In History, undo
  the row of E2. The run still has its finishing event: "Watched 2 times" stays, the entry
  stays Completed, the completion stays in the stats, with E2 seen once. Undoing the start
  row alone does the same to the stats (the finishing episode keeps `to = completed` in
  the effective history).
- Fix: record it as a limit in DEC-589. A check in `over` against the episodes known
  today would be wrong the other way (a finished run would stop counting when a new
  season arrives).

### OT2E-5 (low) Undo chains outside a run behave differently since DEC-588, untested

- Where: `crates/domain/src/progress.rs:109-131` (`carried`),
  `crates/app/src/library.rs:346-371`.
- Change: before, an undo reverted a status move only when the entry's stamp was exactly
  that move's. Now also when a later undo restored it. Example without a run: a book,
  first page log (Planned -> In progress), "Mark as finished" (-> Completed), undo the
  finish, undo the page log. Before: In progress with nothing logged. Now: Planned. The
  new result is the better one, and legacy events (no `from_stamp`) keep the old rule,
  but DEC-588 names only the run and no test outside `app/tests/rewatch.rs` pins it.
- Fix: one test in `crates/app/tests/undo.rs` for the book case and one line in DEC-588.

### OT2E-6 (low) `StatusChange::carried` has no unit test; one domain test checks its own helper

### OT2E-12 (low) A start that starts nothing is still stored

- Where: `crates/domain/src/rewatch.rs:126`, `crates/app/src/library.rs:243-251`.
- Failure: a start queued on the phone reaches an entry that another device already set
  to In progress. It carries no move and starts nothing (as designed), but it is a row
  "Started again from the beginning" in the History and one more event in the stats. The
  API also takes `occurred_at` on a start; a start dated before the first-run views makes

- Fix: do not store a start that carries no move (answer with the entry unchanged, `ok`
  for the queue), and ignore `occurred_at` on a start (or refuse one before the newest
  view).

### OT2E-14 (low) The extra history read per episode log

- Where: `crates/app/src/library.rs:236-242`.
- Cost: one `ProgressRepo::for_item` (the statement the item page already runs, index on
  user and item) for every episode logged on an In progress entry, plus two in-memory
  passes when a run exists. Interactive use: negligible. Import: a show that the file
  says is In progress replays n episodes with n reads of up to n rows; 3000 logged
  podcast episodes are about 4.5 million rows read in the import job.
- Fix: none needed now. If imports of long In progress shows turn out slow, read the
  history once per row in `runner.rs` or skip the check for logs with an `occurred_at`
  in the past of an entry without a start.

## Checked, no finding

- Sync push and pull of `Progress::Rewatch`: `api/src/sync.rs:88-106` parses the domain
  type, no new command; the offline queue keeps its stamps (`offline_log`, `log_command`);
  the start's and the finishing episode's moves go through `Lww::set` with the queued
  stamp; replay is a no-op by op id. Same-millisecond `occurred_at` of a queued start and
  its episodes is ordered by the server's v7 ids in replay order.
- Clients that do not know the type: nothing deserializes into a closed enum on the
  client side. A server binary from before ot2e cannot read stored starts (DEC-587,
  reversal column, says so).
- Importers: `crates/importers` untouched; Trakt and legacy rows never contain a start.
- State machine: start only on Completed; finish exactly once (`run.finished` closes the
  run, later views are ignored); stop and start again; a movie refuses the start and a
  second `finished` moves nothing; Paused or Dropped during a run hides it and no episode
  finishes it; two logs at once: both miss the finish, pages treat the covered run as
  over, the status stays In progress (DEC-589, accepted; the web logs sequentially).
- Undo: of a start (Completed back, run gone), of a finishing episode (run reopens), of
  a whole bulk run in the toast's order (DEC-588 chain holds: each finishing move records
  the start's stamp), a hand status in between stays. A stop has no Undo in its toast
  (plain status toast); setting In progress again resumes the run (see OT2E-2 a).
- `times` and `times_at`: a run counts once in every combination tried on paper (logged
  first pass, hand-completed with partial views, stopped then finished run, extra views
  before a run). `times_at` follows the pass, not the newest view.
- DTO changes: additive except OT2E-9.
- WCAG: the new menu items are plain items of the existing menu with text labels; the
  toasts use the existing `role=status` region and Undo action; the Playwright test runs
  axe in light and dark while a run runs. Nothing new to object to.
- Rules: ASCII in all changed files except `de.ftl`; no brand string; no attribution; no
  migration, no SQL change; DEC-587 to 589 in the required format. No out-of-scope code
  change found (`stats.rs`, `log_sheet.rs`, `widgets.rs` are one-line consequences).
  `crates/web/src/offline.rs`, named in the spec, needed no change.

## Load run verdict

Not needed before the commit, and a run before tagging would not measure this change:
the load harness (`apps/server/tests/it/load.rs`) seeds movies, a book and board games;
its writers post `paged` progress to a book. The new read happens only for an `Episode`
on an In progress entry (`library.rs:236`), which the harness never sends, and the list
paths short-circuit on the progress model (`step_in`, `rewatch`). No SQL changed. If a
number is wanted, time `POST /items/{id}/progress` by hand on a show with about 1000
events once the host is free; expected cost is one indexed read of that history.
