# UX phase 1: independent review of "where am I, what is next"

Date: 2026-11-07. Reviewer: a fresh session that did not produce any of the code. Scope:
`git diff e7df532` plus the untracked phase 1 files (the whole uncommitted working tree except
`crates/testkit/fixtures/import/legacy/` and `docs/research/anime-manga-sources.md`) against
`docs/HANDOFF.md` sections 2 and 4, `docs/design/ux/design.md` section 9 "Phase 1" with 3.1-3.6,
5.3-5.5, 6.1-6.3, 6.6, 7.2-7.4 and 8, `docs/design/ux/addendum-1.md` 1.2 and 1.3, the mockups
`home`, `library`, `item`, `history`, `mobile`, and `docs/DECISIONS.md` DEC-204 to DEC-212 and
DEC-222 to DEC-233 (DEC-213 to DEC-221 are the anime research, out of scope). Read-only:
nothing was compiled or run (the orchestrator runs `cargo xtask ci` and `e2e`); evidence is
`path:line` relative to the repository root (`src/rust/` dropped for Rust paths).

## Summary verdict

Phase 1 is done, and done with care. Every bullet of design.md section 9 "Phase 1" is either
in the tree or named in a DECISIONS entry that says what was cut and why: kind groups live in
the domain and in every built-in module (DEC-204); the Library page has the group switcher,
kind chips with counts, status tabs, the one Filters button with tags and the kind's facets,
the `/` filter box, sort, grid/list and "Load more", with the whole state in the URL and the
back button undoing one change at a time (DEC-205, 222-225); the next step is derived in `app`
per progress model and rendered as one-click buttons, pills and quick menus (DEC-207, 226);
Home has Continue, Up next with next-in-series, five activity rows and the all-time status
totals per group as hand-built SVG bar lists with a sentence as the image name and the
numbers as a list (DEC-212, 229); `/stats` has a tab per group plus All, month or year
columns, and a table behind "Show as a table" per chart; the log sheets (watched, play) have
date chips, people chips with inline create, rating and note behind "More", a discard
question inside the sheet, Ctrl+Enter, and every save toasts "Logged: ..." with a 10-second
Undo that appends a compensating event (DEC-208, 232, 233); the item page has the facts card,
the action bar per model (inline pages and positions), rating/tags/lists, Episodes with
"Mark season", "Mark up to here" and the ask-once question remembered per show (DEC-231),
About, History and the private note (DEC-209); History groups by day with the filters behind
one disclosure, pages with the feed's cursor, tints shared rows with "Copy to my log" and
offers Undo on own rows (DEC-210, 230).

The hard parts are right. Undo is append-only, own events only (404 for anyone else), inside
24 hours (409), idempotent (the compensating event has a derived client op id), refuses to
undo an undo, restores the status move only while the entry still carries that exact stamp,
deletes the session of an undone play, and `LogProgress` refuses the undo type through
`validate_for`. `log_play` checks that every player is the caller's own companion (403), that
the kind has the sessions model (422), validates co-op and scores, and answers the event so
Undo works. Tags are normalised, bounded, case-insensitive and reach no shared DTO. The
library SQL is one static statement with every filter as a parameter. Sheets trap and return
focus, chips carry `aria-pressed`, tabs carry `aria-controls`, charts never rely on colour.
Every new string is in both Fluent catalogues with plurals, the three new dynamic key
families are registered in the locale test, and axe runs in both themes at 1280 and 360 px on
Library (grid, list, quick menu, no-match), the item page with both sheets open, Home, Stats
and History. Rules hold: ASCII only, no `kithkeep` outside the brand and docs, no new icons
(so none outside the vendored set), `deny(unsafe_code)` untouched, no `anyhow` outside the
apps, no AI attribution, no GPL material, no secrets.

Three things need a decision before tagging `ux1`: Home does work proportional to the whole
library on every request, and the M17 load test was not extended to any phase 1 endpoint
(UX1-1); the Library, Home and History pages still rebuild their rows in place, the very
pattern the item package had to replace with a keyed render after it left stale click
handlers behind, and no test clicks a card twice across a refetch (UX1-2); a replayed
`client_op_id` on `log_play` stores a second session row, which the DTO documents as an
idempotency key (UX1-3). The rest is low: a few spec items missing without a DECISIONS line,
server-side input bounds, UTC days, URL junk, chart typography, two long functions, and test
gaps. Recommendation: fix UX1-1 to UX1-3 (or record them) before tagging; the low findings
can ride along or go into phase 2 with a DECISIONS line each.

## Findings

### UX1-1 (medium) Home and the Library query do work proportional to the whole library per request; the M17 load test covers none of the phase 1 endpoints

Evidence: `GET /home` (`crates/api/src/browse.rs:557-590`) calls `library_counts`,
`continue_rows`, `up_next`, `activity_feed` and `stats_totals` in sequence. `up_next`
(`crates/app/src/browse.rs:315-349`) first loads up to `MAX_PAGE` planned rows fully built
(catalog items, tags, every progress event of each, `rows()` at `:249-294`) to keep six, then
`finished_series` (`:352-376`) runs the library query with `limit: u32::MAX` over every
Completed entry and `get_many` over every one of their catalog items (two statements plus the
external ids, `crates/store-pg/src/repos/catalog.rs:149-183`) to find book series. For the
M17 profile in `apps/server/tests/load.rs:89-112` (50 000 completed movies) that is 50 000
entries through the LATERAL statement plus 50 000 catalog rows on every Home visit, for a
feature only book-like kinds use (`series_of`, `browse.rs:505-514`). `stats_totals`
(`crates/app/src/stats.rs:164-199, 206-245`) reads every progress event, every catalog item
with an event and every session of the user per request; `activity_feed`
(`crates/app/src/activity.rs:136-141`) reads every own and shared session per request
(DEC-210 says "fine at today's sizes"). The Library query (`crates/store-pg/src/repos/
library.rs:313-395`) evaluates a LATERAL aggregate over `progress_events` per entry, a
`COUNT(*) OVER ()`, and sorts the whole match set through `CASE` keys before `OFFSET/LIMIT`,
so no index serves the default `last_activity` order. `load.rs:143-181` requests only
`/api/v1/search` and the old `/api/v1/library` (the untouched `LibraryRepo::list`), so the
300 ms p95 budget says nothing about `/library/query`, `/home`, `/stats/*` or `/activity`.
DEC-211 and DEC-210 record "per request, no stored aggregates" but not a size at which that
stops being fine.

Recommendation: (1) `finished_series`: ask the repository only for completed entries whose
item has series data (a `LibraryFilter` on the book-like kinds from the registry, or a
predicate `c.attributes ? 'series'`), and read only `id`, `attributes->'series'`,
`attributes->'series_position'`; (2) `up_next`: fetch a bounded candidate set (for example the
60 most recently added planned entries plus the planned entries of the series found in (1))
instead of `MAX_PAGE` full rows; (3) extend `load.rs` with `/api/v1/home`,
`/api/v1/library/query` (default sort, first page and `offset = n - 100`),
`/api/v1/stats/totals` and `/api/v1/activity` under the same budget, seeded with a few
thousand progress events, and record the numbers in DECISIONS; (4) if the deep page of
`/library/query` misses the budget, add `(user_id, added_at DESC, id DESC)` on
`library_entries` and compute `last_activity` from a maintained column or a materialised
`max(occurred_at)` per `(user_id, item_id)` (the LATERAL then becomes a join).

### UX1-2 (medium) Library, Home and History rebuild their rows in place, the pattern the item page had to key after it kept stale click handlers

Evidence: the item page explains its own fix at `crates/web/src/item.rs:57-62`: "rebuilding
the old view in place kept event handlers of the previous render, whose state was already
disposed", and renders each load under `<For ... key=version>` (`item.rs:106`) so a refetch
replaces the subtree. The three other data pages use the unkeyed form: Library `Results`
renders `move || lib.rows.get().map(|r| ... <Grid rows=page.rows/> ...)` inside `Transition`
(`crates/web/src/library.rs:715-756`), each `PosterCard` and `QuickMenu` capturing its
`row`, `busy` and `error` signals and `LoggedStep` in `on:click` closures
(`crates/web/src/widgets.rs:152-157, 225-241`, `next_step.rs:244-266`); Home does the same for
`HomeSections` and `ContinueCard` (`crates/web/src/home.rs:84-99, 192-219`); History for the
day groups and `ActivityRow` (`crates/web/src/history.rs:521-575, 88-111`). Every one of these
refetches on `entity.updated` and after each action (`library.rs:141-166`, `home.rs:66-74`,
`history.rs:239-250`). The e2e tests never click a card a second time after that refetch:
`src/web/tests/library.spec.ts:134-141` and `home.spec.ts:78-86` click the step once, then
Undo in the toast; the item test is the only one that marks repeatedly across refetches
(`item.spec.ts:181-200`), which is where the defect showed. If the item page's diagnosis is
right, a second "Watched S1 E3" click on a Library or Home card can log S1 E2 again, or
nothing, because the handler belongs to the disposed render.

Recommendation: key the row views the way the item page does (a `version` bumped on each
refetch around `Results`, `HomeSections` and the day groups, or `<For>` keyed by
`(entry.id, last_activity, status)` so a changed row is replaced, not patched), and extend the
two e2e tests with a second click: after "Watched S1 E3" appears, click it and expect
"Logged: Watched S1 E3" and then "Watched S1 E4". If the second click turns out to work
without the key, keep the test and record in DECISIONS why the item page needed it and the
others do not.

### UX1-3 (medium) A replayed `client_op_id` on `POST /items/{id}/plays` stores a second session row

Evidence: `log_session_event` inserts the session first (`crates/app/src/sessions.rs:100-101`)
and only then appends the progress event with the client op id (`:102-113`); the append is
the only deduplication (`crates/store-pg/src/repos/library.rs:449-493`), and `sessions` has no
op id column (`crates/store-pg/migrations/0001_core.sql:142-153`). So a retry with the same
`client_op_id` (the field is documented as the "Idempotency key" in
`crates/contracts/src/browse.rs:395-396`; design.md 5.4 says offline retries reuse it) yields
two sessions, two "plays" in the counts (`query_page` counts session events, so the count
stays one, but `/sessions`, History and the play sheet's "last group" see two), and the
toast's Undo removes only the one the returned event names. DEC-232 records it as a known
limit "as the existing watched-with path does"; neither `crates/api/tests/rest.rs`
(`a_play_with_players_scores_and_a_winner`) nor the e2e play test replays the id.

Recommendation: generate the session id first, append the event (with
`Progress::Session { session_id }` and the op id) before inserting the session, and when the
stored event is not the new one, return the session it names (`sessions.get`) without
inserting; the "watched with" path can take the same order. Test: two POSTs with the same
`client_op_id` answer the same event id and `GET /sessions` has one row.

### UX1-5 (low) The server accepts any `occurred_at` / `started_at`, including the future, and unbounded play fields

Evidence: `crates/api/src/ops.rs:273-279` and `:322-329` parse RFC 3339 and nothing else;
`Session::validate` checks participants and finite scores only (`crates/domain/src/
session.rs:63-80`); `NewPlayDto.duration_minutes` is any `u32`, `location` and `notes` any
length (`crates/contracts/src/browse.rs:385-397`; `set_note` by contrast caps at 20 000
characters, `crates/api/src/browse.rs:363-373`). The web client refuses a future day
(`crates/web/src/log_form.rs:61-66`), the REST and sync paths do not. A future `occurred_at`
becomes the entry's `last_activity` (first in the default sort), a future month on `/stats`,
and a row above "Today" in History.

Recommendation: in `ops::log_progress` and `ops::log_play`, reject timestamps more than a few
minutes after the server clock with 422 `invalid` (`occurred_at`), cap `notes` and `location`
like the note, and `duration_minutes` at a sane maximum (a week); REST tests for each.

### UX1-6 (low) Days, "Today" and times are UTC for everyone

Evidence: `crates/web/src/history_state.rs:1-4` ("there is no per-user time zone yet"),
`history.rs:27-37` (Today from `ClientConfig.today`, the server's UTC day), `:55-59` (times
rendered as "HH:MM UTC"), `stats.rs:156-161` (UTC buckets). DEC-211 and DEC-230 record the
choice. For a user in UTC+10 an episode logged at 08:00 local lands under "Yesterday", and
the Stats month boundary moves by hours; the owner's i18n ruling asks for "locale-aware dates".

Recommendation: accept for phase 1 (it is recorded), and put the per-user time zone on the
phase 3 settings page (account: language, theme, time zone), carried in `ClientConfig` so
server and browser group alike; then drop the "UTC" marker from History and Home. Until then
the markers are the honest choice.

### UX1-7 (low) Junk in a shared URL shows an error with a useless Retry instead of being ignored

Evidence: `LibraryState::from_lookup` keeps any `group` except "all" and any `facet` pair
(`crates/web/src/library_state.rs:105-116`), `HistoryState` keeps any `person`
(`history_state.rs:36-38`); the server answers 400 for an unknown group (`crates/api/src/
browse.rs:32-37`) and 422 for an attribute that is not a facet (`crates/app/src/
browse.rs:138-150`); the pages render that as a destructive Alert with "Try again"
(`library.rs:721-729`, `history.rs:527-532`). `/library?group=foo` therefore says "Your
library could not be loaded" and Retry can never help. design.md 6.2: "empty filter result
names the active filters and offers Clear filters".

Recommendation: validate `group` against the five known ids in `from_lookup` (drop unknown
values, unit test `group=foo` -> `None`), and on a 400/422 from the rows resource render the
no-match empty state with "Clear filters" instead of the Alert (the Alert stays for 5xx and
network errors).

### UX1-8 (low) Chart typography and wording: axis labels below the type floor, an odd summary for empty series, sentences composed in code

Evidence: `crates/web/src/charts.rs:262` and `:274` set tick and axis labels at
`text-[0.6875rem]` (11 px); design.md 2.8 floors body text at 0.8 rem and captions at
0.72 rem (11.5 px); UX0-7 was the same point. `home.rs:484-507` builds "most in { $peak }"
from `max_by_key`, so an all-zero series says "0 in total, most in <last month>".
`home.rs:258-264` composes "Watch: 2 planned, 1 in progress, ..." with `format!` and
`to_lowercase()` on translated status words (German nouns lose their capital), and
`charts.rs:222`, `home.rs:513-517` compose "{label}: {value}" tooltips; the locale scan only
sees `view!` bodies, so these sentences live outside Fluent (HANDOFF 4.1 "every
user-visible string in the locale files").

Recommendation: `text-caption` for the tick and axis labels; a `stats-chart-summary-empty`
key when `total == 0`; Fluent keys `stats-totals-summary` (`{ $group }: { $parts }`) and
`chart-value` (`{ $label }: { $value }`) with the status words untouched (they are already
lower-case in the sentence position for English if the keys say so, and German can keep its
capitals).

### UX1-9 (low) Two phase 1 functions pass 100 lines under the crate-wide `too_many_lines` allow

Evidence: `crates/web/src/lib.rs:9-13` allows `clippy::too_many_lines` crate-wide with a
two-line comment, `crates/ui/src/lib.rs:11` likewise; both predate phase 1 (M06, commit
334f682), so the rule "allow-list individual lints only with a comment" (KICKOFF 4) is met
formally. HANDOFF 8 says "functions at most 100 lines"; phase 1 adds `history::Filters` at
170 lines (`crates/web/src/history.rs:273-442`, six near-identical `bind` calls plus the
view) and `widgets::TagEditor` at 113 (`widgets.rs:302-414`). The new test files allow the
lint per file with a one-line reason (`crates/app/tests/undo.rs:3-4` and siblings), which
is fine.

Recommendation: split `Filters` (a table of `(signal, from_state, to_state)` for the five
selects and a `FilterFields` component for the panel) and `TagEditor` (the dialog body as its
own component), then either narrow the crate-wide allow to per-function allows with a reason
or record the crate-wide exception for `view!`-heavy crates in DECISIONS so HANDOFF 8 and the
code agree.

### UX1-10 (low) Small correctness and cost nits

Evidence:

- A failing search backend turns the text filter into "Nothing matches these filters":
  `text_matches` logs a warning and returns an empty list (`crates/api/src/browse.rs:123-143`),
  which the page shows as the no-match state (`library.rs:730`) with no way to tell.
- The play sheet's prefill loads every session of the user to find the last play of one item
  (`crates/web/src/log_sheet.rs:486-496`, `api::sessions(false)`); the page already has the
  item's effective history (`page.progress`) whose last `session` event names the session.
- The item page reads the entry and the item's history three times per request: `item_page`
  (`crates/api/src/ops.rs:49-53`) loads entry and history, then `item_state`
  (`browse.rs:298-312`) loads the entry again and `library_row` (`crates/app/src/
  browse.rs:227-246`) loads the history again and runs `rows()` for one row.
- `ItemRow`'s rating change does not refresh the facts card (`item.rs:421-428` calls
  `api::rate` and nothing else), so "Your rating" in the card lags until an
  `entity.updated` event arrives (it does, so this is a flicker, not a bug).

Recommendation: answer 503 `search_unavailable` from `library_query` when the port fails (the
page then shows Retry); derive the last group from `page.progress`; let `item_page` build the
row from the entry and history it already holds; run `refresh` after a rating.

Evidence (each exists in code, none has an assertion):

  `log_form.rs`, the wiring is not).
- The play sheet's discard question and the remembered "More" state (`log_sheet.rs:526-530,
  553-556`); only the watched sheet's discard is tested (`item.spec.ts:131-140`).
- The German locale on any phase 1 page: `src/web/tests/i18n.spec.ts` is unchanged; the
  catalogue parity is tested, the rendered German (length of "Als abgeschlossen markieren"

- `activity` with `person`, `type` and `shared` filters through the UI: `home.spec.ts:141-160`

`/stats` asserting a few strings and `html[lang=de]`.

## What was checked and holds

- Kind groups (3.1, DEC-204): `KindGroup` with stable ids, unknown ids read as `Other`,
  `group()` on `KindModule` defaulting to `Other`, each built-in module in its group with a
  test (`crates/domain/src/kind.rs:128-190, 241-258`; `crates/kinds/tests/builtins.rs:105`);
  `other` listed only when non-empty (`crates/api/src/browse.rs:59-73`).
- Library query (3.5, DEC-205): one static statement, every filter a parameter, facets as a
  jsonb array matched by text, tags by key with "carries all", text through the search port
  intersected by `items`, sorts by `CASE` with missing years and ratings last, ties by id,
  total past the end recomputed (`crates/store-pg/src/repos/library.rs:170-178, 313-395`);
  the facet attribute must belong to a selected kind, else 422 (`crates/app/src/
  browse.rs:138-150`). Tested on the in-memory store and on Postgres
  (`crates/app/tests/browse.rs`, `crates/store-pg/tests/phase1.rs:42`).
- Tags (DEC-206): trimmed, inner spaces collapsed, 1-50 chars, no control characters, 50 per
  entry, case-insensitive identity with the typed form kept, rename-onto-existing merges,
  every change recorded for sync (`crates/domain/src/tag.rs`, `crates/app/src/
  browse.rs:380-501`, `store-pg library.rs:200-268`). Privacy: tags appear in
  `LibraryRowDto`, `ItemPageDto` and `/tags` only, all behind `Authed` and scoped to the
  actor's entries; nothing in `lists.rs`, `sharing.rs` or the session DTOs carries them.
- Undo (5.4, DEC-208): `Progress::Undo` is never valid as logged progress
  (`crates/domain/src/progress.rs:50-66`), `effective()` drops both sides, the status move is
  stored on the event and restored only while `status.stamp` is unchanged
  (`crates/app/src/library.rs:176-191, 226-300`); own events only (`NotFound` for others),
  24 h window (`Conflict`), undo of an undo refused, repeat returns the first compensating
  event, a play's session is deleted and republished; migration adds `undoes` with a partial
  unique index and `status_change` (`0014_phase1.sql`). Tested at `crates/app/tests/undo.rs`
  (all four rules), on Postgres (`phase1.rs:209`), through REST (`rest.rs`), the server
  function (`library_page.rs:273`) and e2e on Library, Home, History and the item page.
- `log_play` (DEC-232): players must be the caller's active companions (`check_participants`
  -> `Forbidden`, `crates/app/src/sessions.rs:167-181`), kinds without the sessions model are
  a model mismatch (422), co-op only `won`/`lost`, RFC 3339 `started_at`, empty players
  means the self companion, scores finite; the item's cover is pinned; the event is
  answered for Undo (`crates/api/src/ops.rs:312-353`); REST test with scores, winner, undo
  and the movie 422 (`rest.rs` `a_play_with_players_scores_and_a_winner`); e2e verifies the
  decimal comma and the derived winner (`item.spec.ts:143-170`).
- Next step (3.4, DEC-207): single/episodic/paged/timed/sessions, specials ignored, rewatches
  of older episodes do not move it, season rollover, `caught_up`, `episode_count` as one
  season, labels chosen in `api` with Watch/Listen/board-game wording
  (`crates/app/src/next_step.rs`, `crates/api/src/browse.rs:201-252`; `crates/app/tests/
  next_step.rs`). The pill is a button only while Planned or In progress (DEC-226,
  `widgets.rs:152-160`); the one-click set is exactly finish and episode (`next_step.rs:26-36`

## Test quality

Strong where the behaviour is a function or a use-case: the URL state of both pages, the
log-form rules, the chart maths, the next step, the progress summary, undo, the feed, the
stats and the library query all have focused tests, most of them in both the in-memory store
and Postgres, and the REST layer has a scenario per endpoint family plus the play endpoint.
The server-rendered page tests assert real markup (counts, labels, tab order, the next
episode after an undo), and the e2e suite covers the owner's "where am I, what is next"
story end to end: URL state and the back button, one-click steps with Undo on three pages,
both sheets including focus trapping and the discard question, inline create of a person,
the episode question with memory, the bulk undo, Stats tables, History paging and filters,
and axe in both themes at two widths on every new page. Weak where the orchestrator already
suspected it: the Library page's interactive parts (facets, `/`, debounce, Load more, a
second click after a refetch) rest on one e2e test; the inline page and position loggers
and the play sheet's discard are rendered but never driven; no German page is rendered in
e2e; the idempotency the DTO promises is not exercised (UX1-3, UX1-11). Test-first cannot be
verified from an uncommitted tree; the packages' own account (partly kept) is the record.
