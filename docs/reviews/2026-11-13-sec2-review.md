## Must fix before merge

### SEC2-1 (high) The second factor can be guessed without a bound per account

- Where: `src/rust/crates/auth/src/throttle.rs:349-353` (the only account count is the pair
  of name and exact address), `src/rust/crates/auth/src/lib.rs:553-555` and `:587-611`
  (`sign_in` -> `second_factor` -> `check_totp` / `use_recovery`), LA-1.
- Problem: before this package a name had 10 failures per 15 minutes in all, whatever the
  address (960 a day). Now a failure is counted for (name, address) and for the address
  only. Nothing counts wrong one-time codes for the account across addresses, and there is
  no other lock on TOTP failures (`totp_locked` is about an unreadable secret). A 6-digit
  code has 10^6 values, of which one to three are right at any time.
- Scenario: someone has a member's or the owner's password (phishing, reuse) and the
  account has TOTP. From each address they get 30 checked guesses per 15 minutes (3 free
  per pair, the address budget is what stops them). With an IPv6 /48 (65 536 budgets of
  one /64 each, free from a tunnel broker) or a rented pool of IPv4 addresses the only
  bound left is the verification cap (8 argon2 runs at once): tens of thousands of codes
  per 15 minutes, so a right code is expected within hours. With 100 IPv4 addresses it is
  288 000 guesses a day. The old lock made the same attack take years. LA-1 accepts
  spread-out guessing because "the password length rule, TOTP where enrolled" bound it;
  for the TOTP step itself nothing does.
- Why the lock-out argument does not forbid a fix: a wrong one-time code can only be
  produced by someone who already sent the right password, so a count per account for the
  second factor cannot be used by a stranger to keep the owner out of break-glass.
- Suggested fix: a third count, per account alone (key `t|<name>`), added only on
  `AuthError::InvalidTotp` (TOTP and recovery code, in `sign_in`, `reauth`,
  `totp_confirm`), with the same progressive wait and checked in `begin` only when a code
  is supplied (or checked right before `second_factor`). Clear it on a right code. Add a
  test with a fake clock: right password, wrong codes from 40 different addresses, the wait
  grows; wrong passwords from elsewhere do not touch it. Consider an admin notification
  after N such failures (the password is known to someone).

### SEC2-2 (medium) The head timeout is dodged by sending nothing, or by speaking HTTP/2

- Where: `src/rust/apps/server/src/serve.rs:39-44` and `:72-74` (hyper-util `auto::Builder`,
  `serve_connection_with_upgrades`); test
  `src/rust/apps/server/tests/it/read_timeout.rs:221-236`.
- Problem: the auto builder first reads up to 24 bytes to tell HTTP/1 from the HTTP/2
  preface (`hyper-util-0.1.21/src/server/conn/auto/mod.rs:339-378`, `ReadVersion`). That
  read has no timer; hyper's `header_read_timeout` starts only once the connection was
  handed to the HTTP/1 state machine. And an HTTP/2 connection has no head timeout at all
  (LA-11 says so, with "a proxy speaks HTTP/1.1 to the application", but a client that
  reaches the port directly chooses the protocol itself).
- Scenario (the one the package was to close, SEC-5 "many connections"): a client opens
  thousands of connections and sends zero bytes, or the first bytes of `PRI * HTTP/2.0`,
  or the whole preface and then nothing. Each holds a socket and a task for ever, as with
  `axum::serve` before. The new test passes because its half head starts with `GET`, which
  leaves the version read at once.
- Suggested fix: serve HTTP/1 only. Nothing needs h2c (pages, REST, SSE all work on 1.1,
  and the documented proxies speak 1.1 upstream): either `builder.http1_only()` (the auto
  builder then skips the version read, `auto/mod.rs:231-237`) or hyper's
  `server::conn::http1::Builder` with `.with_upgrades()`. If HTTP/2 must stay: wrap the
  connection in a timeout until the first request arrives and set the HTTP/2 keep-alive
  interval and timeout. Extend the test: a connection that sends nothing, and one that
  sends the HTTP/2 preface, are closed within the limit.

### SEC2-3 (medium) `outbound.allow_private_hosts` does not do what the docs say for sign-in providers given as an address, and the mail host has no allowlist at all

- Where: `src/rust/crates/auth/src/oidc.rs:263-272` (`private_literal`), `:455-457`
  (host list), `:497-503` (the openidconnect client), `:540-542` (`fetch`);
  `src/rust/crates/notify/src/channels/email.rs:104-121`;
  `src/rust/apps/server/src/lib.rs:176-187` (`private_targets`) and `:192-208`
  (`private_hosts`, handed to the governed client only); docs
  `docs/modules/ROOT/pages/operations.adoc:626-630`, `config/.env.example` (the example
  entry `10.0.0.5:8443`), `crates/config/src/lib.rs` `OutboundConfig` ("a sign-in provider
  in the local network of a hosted instance").
- Problem: the operator's list is consulted in `GovernedHttp::client_for` only. `auth::oidc`
  refuses every IP literal in a private range by itself whenever `private_targets()` is
  false, without looking at the list, and drops such hosts from the connector's host list.
  The mail transport asks `private_targets()` only. So the per-host exception works for a
  provider with a name and for nothing else.
- Scenarios: (a) hosted instance, provider at `https://10.0.0.5:8443`, operator sets
  `APP__OUTBOUND__ALLOW_PRIVATE_HOSTS=["10.0.0.5:8443"]` exactly as the example shows:
  discovery still fails with `oidc_blocked_target`. (b) hosted instance (or a home instance
  whose config has `notify.allow_private_targets = false`, which was the documented default
  value until now and may be written out in an existing file) with a mail relay on the
  compose network or on `localhost:25`: mail is refused (`private_target`), password-reset
  and emailed-link mails stop, and the only switch is `notify.allow_private_targets = true`,
  which also lets every member point a webhook at the operator's network. The task brief
  asks for an allowlist that makes a LAN OIDC or mail host work (SEC-4a); for mail there is
  none.
- Suggested fix: one predicate "may this host be private" = `private_targets()` or the host
  (with port) is on `outbound.allow_private_hosts`; hand it to `OidcParts` (taking the URL)
  and to `Mailer::with_private_rule` (taking host and port) in place of the bare
  `Fn() -> bool`. Consider treating a mail host that comes from file or environment like a
  connector `base_url` (the operator named it). Tests: hosted mode, IP-literal issuer on
  the list is fetched; hosted mode, mail host on the list is used; and the upgrade note for
  an explicit `allow_private_targets = false`.

## May defer

### SEC2-4 (medium) A reverse proxy missing from `server.trusted_proxies` now means: 30 wrong guesses by anyone refuse every sign-in, break-glass included

- Where: `src/rust/crates/auth/src/throttle.rs:354-364` (address budget, fixed window, no
  refill on success), `src/rust/crates/api/src/request_meta.rs:177-200` (one warning per
  process, level warn, only when the request carries `X-Forwarded-For`), default of
  `trusted_proxies`: none.
- Problem: until now a missing `trusted_proxies` entry only made audit rows show the proxy.
  With the budget per address, all visitors behind an unlisted proxy are one address. The
  same holds for people who really share an address (a family behind one IPv4, an office,
  carrier-grade NAT), where 30 failures per 15 minutes is a shared hard refusal.
- Scenario: home instance behind Caddy on the same host, `APP__SERVER__TRUSTED_PROXIES`
  empty. A stranger sends 30 wrong sign-ins in 15 minutes and repeats that every window:
  nobody can sign in, re-authenticate, change a password or use `/sign-in/local`, for as
  long as they keep it up. This is the hard lock DEC-535 removed, for the whole instance.
  The spoofing direction is fine: without a trusted proxy the header is ignored, so it can
  neither reset nor dodge a budget (checked in `request_meta::of` and by the `it` test).
- Suggested fix: before merge, the owner checks the home deployment has the proxy listed.
  Then: show the condition where an admin looks (the health probes of Admin > Instance:
  "requests with X-Forwarded-For arrive from <peer>, which is not a trusted proxy"), repeat
  the warning (once per hour, not once per process), and put the point into the upgrade
  notes. Optionally let a right password from an address still pass when only the address
  budget (not the pair wait) is exhausted and the pair has no failures of its own: a
  holder of the password is not guessing.

### SEC2-5 (medium) Counter keys keep whatever name was sent: up to 20 000 keys of up to 2 MiB

- Where: `src/rust/crates/auth/src/lib.rs:553` (`normalize_username` only trims and
  lowercases), `src/rust/crates/auth/src/throttle.rs:349-353` and `:227`
  (`key.to_string()`), `CAPACITY` at `:180`.
- Problem: the pair key contains the submitted name unbounded; the JSON body limit is
  2 MiB. The count of keys is bounded, their size is not.
- Scenario: each address can add 30 keys per window, so about 670 addresses (670 /64
  networks out of one /48) fill the map with 20 000 names of, say, 200 KiB each: 4 GB held
  by the process until the entries age out, on a 4 to 16 GB home server. (Not new: the old
  map had the same shape and no address budget. Still open.)
- Suggested fix: a name longer than `USERNAME_MAX_LEN` cannot be an account; key it as a
  fixed placeholder (`p|<too long>|<ip>`) or hash the name into the key. Same place as the
  SEC2-1 key. Test: 31 over-long names from one address create a bounded number of bytes.

### SEC2-6 (low) Eviction at capacity hands budgets and waits back

- Where: `src/rust/crates/auth/src/throttle.rs:210-221`.
- Problem: at 20 000 keys the stalest key is dropped, whatever it is: an address budget
  that is exhausted, or a pair in its wait. The `retain` before it uses the window of the
  key being added with `Restart::AfterLast` for all keys; the comment says "the longer of
  their windows", the code passes the caller's (for an address key the shorter one when
  `delay_max_secs` is above `window_minutes`).
- Scenario: an attacker with many networks (see SEC2-5) keeps the map full; the oldest of
  their own exhausted budgets is evicted and can be used again before its window ends.
  They had that many addresses anyway, so the gain is small.
- Suggested fix: pass `s.pair_window().max(s.window())` to the purge; evict pair keys with
  the fewest failures before address keys; or refuse new pair keys at capacity and count
  the address only.

### SEC2-7 (low) The import upload has no total time: a trickle holds 64 MiB for ever

- Where: `src/rust/apps/server/src/read_timeout.rs:46-48` and `:116`.
- Problem: `POST /api/v1/imports` only has the idle limit. One byte every 29 s never trips
  it. Not verified here whether the route rejects an unauthenticated request before it
  reads the body; if it does, this needs an account.
- Scenario: a member (or anyone, if the body is read first) opens 50 uploads that trickle:
  up to 3.2 GB buffered and 50 tasks, with no end.
- Suggested fix: a generous total for this path instead of none (64 MiB at 0.3 Mbit/s is
  about 30 minutes), as a fourth setting or a fixed multiple of `body_read_timeout_secs`;
  a test that an unauthenticated upload is refused with nothing read.

### SEC2-8 (low) `is_private_ip` leaves ranges out that the new filters now rely on

- Where: `src/rust/crates/domain/src/net.rs:8-28` (unchanged, now behind the governed
  client, OIDC and mail too).
- Missing: `0.0.0.0/8` beyond the one address, `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4`,
  multicast (`224.0.0.0/4`, `ff00::/8`), and IPv6 forms that carry an IPv4 address:
  NAT64 `64:ff9b::/96`, IPv4-compatible `::a.b.c.d`, 6to4 `2002::/16`, also site-local
  `fec0::/10`. Covered and checked: RFC 1918, loopback, `169.254.0.0/16` (the metadata
  address), `100.64.0.0/10`, `fc00::/7` (includes `fd00:ec2::254`), `fe80::/10`,
  IPv4-mapped `::ffff:a.b.c.d`.
- Scenario: on a network with NAT64, `https://[64:ff9b::a9fe:a9fe]/` or a name with that
  AAAA record passes the filter and is translated to `169.254.169.254` by the gateway.
- Suggested fix: add the ranges and extend the table test; for the embedded forms, extract
  the IPv4 part and classify it.

### SEC2-9 (low) Proxy environment variables switch the name check off

- Where: `src/rust/crates/catalog-core/src/http.rs:316-327`,
  `src/rust/crates/catalog-core/src/plain.rs:22-32` (no `.no_proxy()`).
- Problem (reqwest's documented default, not executed): a client built without
  `no_proxy()` uses `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` from the environment. Then the
  resolver is asked for the proxy's name, the target name is resolved by the proxy, and
  `PublicOnly` never sees it. Host lists and literal checks still apply.
- Scenario: an operator runs the container with `HTTPS_PROXY` set; a member's webhook to a
  name that resolves to `10.0.0.5` is sent through the proxy and reaches the internal host
  if the proxy can.
- Suggested fix: `.no_proxy()` on the three clients, or a documented setting for an
  outbound proxy together with the statement that the proxy must do the filtering.

### SEC2-10 (low) Mail where private addresses are refused: only the first address is tried

- Where: `src/rust/crates/notify/src/channels/email.rs:109-120`.
- Problem: the checked path builds a transport to `addresses.first()`. The normal path
  lets lettre try every address of the host. A new transport (and pool) is built per send.
- Scenario: hosted instance without IPv6 routing, provider whose first answer is an AAAA
  record: every mail fails with a connection error although the A record would work.
- Suggested fix: try the checked addresses in order until one connects (all of them passed
  the check), or prefer the family the host can route.

### SEC2-11 (low) `outbound.allow_private_hosts` entries are compared as written

- Where: `src/rust/crates/config/src/lib.rs` `is_host` (accepts upper case and a leading
  dot), `src/rust/crates/catalog-core/src/http.rs:159-176` (`host_matches`, exact
  comparison with the lower-cased URL host; a leading dot means "all subdomains").
- Scenario: `["IdP.lan"]` passes validation and never matches, the provider stays refused
  with no hint; `[".lan"]` passes and silently allows every `*.lan` host, which the
  setting's text does not offer.
- Suggested fix: lower-case entries when the config is read; reject a leading dot here (or
  document it).

### SEC2-14 (low) Small things in the throttle

- `src/rust/crates/auth/src/throttle.rs:66`: `self.free_failures + 1` overflows for
  `free_failures = 4294967295` (panic in a debug build, in release the wait then starts at
  the first failure). The config check does not bound the value. Use `saturating_add`.
- `throttle.rs:365-375`: the pair wait is checked before the verification and counted
  after it, so a burst of parallel guesses at one pair all pass the wait. They are bounded
  by the address budget including attempts in flight (30), so one address still gets 30
  per window and no more; worth one sentence in LA-1.
- `oidc.rs:531-566`: `oidc_blocked_target` against `oidc_unavailable` tells a hosted admin
  whether a name resolves to a private address. A category, as DEC-534 asks; no port or
  response detail leaks. Recorded so it is a decision and not an accident.

## Checked and found in order

- Every check of a secret goes through `Auth::attempt`: password and TOTP/recovery code at
  `sign_in` (both doors, and "Is this your account?" through `confirm_link` -> `sign_in`),
  `reauth`, `change_password`, `totp_confirm`, `reset_password` (address budget only),
  `confirm_email_link`. No `verify_password` call is left outside `Auth::verify` (the cap).
  Invite tokens and bearer tokens are not counted (random tokens; the lane lists invites).
- Spoofed `X-Forwarded-For`: ignored unless the peer is a trusted proxy; with one, the walk
  from the right stops at the first untrusted entry, so entries the client added are never
  used. IPv4-mapped peers are made canonical; IPv6 is budgeted per /64.
- The wait is a refusal with `Retry-After`, never a lock: a pair starts again after a quiet
  window, the address window is fixed from its first failure. Guesses from elsewhere do not
  slow the owner at their own address (unit and `it` test); break-glass keeps its audit row
  and notification.
- Unknown names are counted, delayed and verified (dummy hash) like known ones.
- The client address reaches `auth` in server functions too: leptos_axum 0.8.10 runs the
  server function inside the handler's task (`handle_server_fns_inner`, no spawn), so the
  task-local of `request_meta::layer` is visible.
- Outgoing clients: only `GovernedHttp`, `PlainHttp` and lettre exist in the workspace.
  Governed: no automatic redirects; each hop re-checked against the connector's list and
  the private rule; no https to http; caller headers and validators only to the first
  origin; refused hops are not retried and do not trip the breaker. Names are resolved by
  `PublicOnly` and the connection goes to the checked addresses (no second lookup); one
  private answer refuses the name. Plain client: no redirects, same resolver. Mail:
  resolved, checked, connected by address with the certificate checked against the name.
- Timeouts: the body layer sits outside `body_limit`, so the collecting for `/_fn/` is
  timed; requests without a body (SSE, pages) are not wrapped, so streams are not cut;
  only the import route has the 64 MiB limit, every other body is at most 2 MiB, for which
  60 s is ample. Defaults (150/30/60 s; 3, 1 s, 300 s, 15 min, 30, 8) are sane and zero
  values are rejected.
- Error texts: mail test answers a category, the transport text goes to the log; 408, 429
  and 413 use the common error shape. No non-ASCII in the new Rust and doc files (the
  German locale file aside), no leftover debug switches in the sources.
