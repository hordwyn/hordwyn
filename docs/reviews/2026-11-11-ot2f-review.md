What holds (checked, no finding):

- Migration 0032 only replaces the column check of `sessions.coop_outcome` by one that also
  allows `none`. The dropped name `sessions_coop_outcome_check` is the name Postgres gives the
  unnamed column check of `0001_core.sql:150`; the table was never renamed (the only other
  "sessions" table is `auth_sessions`). Existing rows (`won`, `lost`, NULL) satisfy the new
  check, so the validating scan cannot fail. No data is rewritten. Both statements run in the
  one transaction of the migration.
- The new `.sqlx` file matches the statement in `store-pg/src/repos/sessions.rs` (same text,
  three parameters uuid / uuid[] / uuid, five columns). No other stored query changes: the
  outcome column is still read and written as text. The file is untracked and must be in the
  commit together with the migration and the three new source files.
- `CoopOutcome::as_str` / `parse` are the one mapping for the store (`conv.rs`), the API
  (`ops.rs`, `browse.rs`) and serde. The outcome reaches clients only as a string
  (`ActivityPlayDto.coop`, `NewPlayDto.coop`); no client deserialises the domain enum. An old
  web client (cached bundle) that reads `coop: "none"` shows the row without a result line
  (its match knows `won`, `lost` and falls through), it does not fail. The two new DTO fields
  are `serde(default)`; no contract type involved has `deny_unknown_fields`.
- Sync (`api/src/sync.rs`), the legacy and Trakt importers and `crates/integrations` do not
  read or write a session or a co-op outcome (no reference in those crates); nothing to change
  there. The realtime event of a session carries only its id. "Copy to my log" of a shared
  session copies the outcome as the enum (`app/src/sessions.rs:291`).
- The SQL of `play_totals` and `Session::result_for` state the same rule (co-op `won`/`lost`
  decide alone, `none` decides nothing, else any winner mark; a result needs one of the
  person's entries at the table). Each lateral subquery is an aggregate without GROUP BY, so
  it returns exactly one row and cannot multiply sessions. The Postgres test compares the
  statement with the rule for four sets of entries and three scopes and also asserts absolute
  numbers.
- Undo: `App::undo` deletes the session row of an undone play (`app/src/library.rs:427-431`),
  so the totals follow an undo; a replayed play that was undone stores nothing.
- Merged people: `own_entries` follows merge chains to the self entry; tested.
- People cards: `Acc::add` now uses `Session::decided`, and `won` treats `NoResult` as no win;
  for every play in the owner's log a person's card and the person's own rate use the same
  rule (ties: a win for each winner; co-op win: everyone's). The one difference is OT2F-8.
- Game groups: not touched; `group_plays` does not read the outcome.
- Play group and sessions model are the same three built-in kinds (`kinds/src/builtin/play.rs`),
  so the totals row of the Stats Play tab and `App::play_totals` cover the same kinds.
- Container queries: the build uses Tailwind CSS 4 (`flake.nix`), where `@container` and
  `@2xl:` are built in. A browser without container queries keeps two columns (the base
  class), nothing breaks. The parents of the block on Home and Stats are block or column
  flex items, so the inline-size container has a definite width.
- `ui/src/table.rs`: the added selector `.. tbody tr:last-child` (specificity 0,2,2, inside
  the 47.5 rem media query) beats `TableBody`'s `[&_tr:last-child]:border-0` (0,2,1) only in a
  stacked table below 47.5 rem. Effect on Admin Users, SSO and the notification log: the last
  card has the same border as the others. Above 47.5 rem nothing changes.
- Fluent: 43 new keys each in en and de with the same names and variables; the two removed
  keys are removed in both. The German words follow the existing ones ("Partien",
  "Mitspielende", "Gemeinsam gewonnen/verloren"). `plays-rate-value` in de uses a no-break
  space, allowed in a non-English .ftl.
- ASCII outside de.ftl, no brand string, no attribution in the diff.

## Must fix before commit

### OT2F-1 (medium) Score table: element ids come from the row index, which goes stale

- Where: `src/rust/crates/web/src/log_sheet.rs:891` (`<For each=rows key=|(_, id)| id.clone()>`),
  `:914` (`format!("play-score-{n}")`), `:932` (`format!("play-won-{n}")`).
- Problem: rows are keyed by the companion id, so a row that stays is not rendered again and
  keeps the index it was created with. After a player before it is removed and another is
  added, two rows carry the same `n`, so `play-score-{n}` and `play-won-{n}` exist twice. The
  label of the radio has `for=play-won-{n}`; a `for` attribute wins over the nested input.
  The duplicate score id existed before this package; the radio and its 36 px label are new.
- Failure scenario: board game dialog, players You, Ben, Cleo (n = 0, 1, 2). Deselect Ben in
  the picker (Cleo keeps n = 2), select Dana (new row, n = 2). A click on the padding of
  Dana's 36 px "won" target (the part that exists for WCAG 2.5.8) checks Cleo's radio: the
  play is saved with Cleo as the winner and counts as a loss in the person's win rate. For a
  screen reader Cleo's score field is named by both labels and Dana's by none (WCAG 1.3.1,
  4.1.2; duplicate ids). Shorter path: You, Ben; deselect You; select Cleo.
- Fix: build both ids from the companion id (`play-score-{id}`, `play-won-{id}`), and drop the
  index from the row. Add a browser assertion: remove a middle player, add one, the ids in
  the table are unique and each radio is checked by its own label.

### OT2F-2 (medium) The Plays tab counts session rows, the header, History and the tiles count session events

- Where: `src/rust/crates/web/src/item.rs:984` (tab count from `play_totals.plays`), `:963`
  (`default_tab`), `src/rust/crates/web/src/plays_tab.rs:151-154` ("No plays logged yet."),
  `src/rust/crates/web/src/stats_extras.rs` `PlayResults` (`stats-play-open`),
  `src/rust/crates/store-pg/src/repos/sessions.rs:199` (`play_totals` reads `sessions`).
- Problem: "Played N times" (`app::times`), the History tab count, the totals row and the
  games tile (`app/src/stats.rs:157`, `a.plays = 1` per event) count `session` progress
  events. The new numbers count rows of `sessions`. The two differ whenever an event has no
  session row, and that state is produced by the product itself: the generic export writes
  every history event (`api/src/ops.rs:640-647`, the progress as stored, including
  `{"type":"session","session_id":..}`) but no sessions, and the importer replays the event
  as it is (`importers/src/runner.rs:575-594`).
- Failure scenario: export an account with a game played three times, import the file into
  another account (the round trip `export_then_import_*` tests). The game page there says
  "Played 3 times, last on ...", History shows 3 rows, the Home tile says "3 plays"; the new
  tab reads "Plays 0", the page opens on About, and the panel says "No plays logged yet.".
  On the Stats Play tab the totals row says "Plays 3" and "Your results" is missing; with a
  fourth play logged after the import it says "One play is not counted" under "Plays 4".
- Fix (smallest, in scope): take the tab count and the "is there a play" test from the same
  source as the header (the `session` events of `page.progress`, or `page.times`), and when
  events exist without a readable play say so ("3 plays without details") instead of "No
  plays logged yet."; in `PlayResults` do not derive "not counted" from a number the totals
  row above contradicts (or name the base: "of 1 play with details"). Out of scope, to be
  recorded: the export carries no plays (players, scores, outcome, duration are lost in a
  round trip, so `none` is lost too); that needs sessions in the export format.

### OT2F-3 (medium) "Use the highest score" removes itself and drops the keyboard focus

- Where: `src/rust/crates/web/src/log_sheet.rs:896-902` (`<Show when=.. s.winner .. !is_empty()>`
  around the button whose click clears `s.winner`).
- Problem: the button is unmounted by its own activation. The focused element leaves the
  DOM, focus falls back to the document (in the modal dialog: its start).
- Failure scenario: keyboard or screen-reader user picks "Play Tester won" by hand, tabs to
  "Use the highest score", presses Enter. The button is gone, nothing is announced, the next
  Tab starts at the top of the dialog (close button, When, Duration, ...) instead of the
  table or Save (WCAG 2.4.3 Focus Order; the binding rule is WCAG 2.2 AA everywhere,
  HANDOFF 4.1). The browser test clicks the button with the mouse and does not look at focus.
- Fix: after the reset move focus to the checked radio (or to the first radio when the
  scores tie), or keep the button mounted and `aria-disabled` while nothing is chosen by
  hand. Assert `toBeFocused()` in `item.spec.ts` after pressing Enter on the button.

## May defer

### OT2F-4 (medium) A scored solo play is always a win, and a scored play cannot be saved without a winner

- Where: `src/rust/crates/web/src/log_form.rs:278-300` (`PlayForm::winner`: the one highest
  score wins, also when it is the only score), `src/rust/crates/web/src/log_sheet.rs:948-950`
  (a radio cannot be unchecked; "Use the highest score" only returns to the automatic mark).
- Problem: the rule is older than this package, but until now the mark was only a word in a
  History row. Since ot2f it feeds a rate.
- Failure scenario: a person plays a solo board game or a score-attack video game ten times
  and types the score each time. Every play is sent with `winner: true` for themselves; the
  Plays tab and the Stats Play tab say "100%", "10 of 10 plays with a result", although no
  play had an opponent and some were lost. There is no way in the dialog to say "nobody won"
  once a single highest score exists (only the co-op switch with "We lost").
- Fix: do not derive a winner from the highest score when fewer than two players have a
  score; give the table a way to clear the mark ("No winner"). Owner question: is a solo
  play ever a result. Record the choice in DECISIONS.md.
