## Must fix before commit

### OT1A-1 (medium) Stale results of the previous query stay selectable, unfiltered

- Where: `src/rust/crates/web/src/palette.rs:716` (`filter`), `:698` (`shown`), `:471`
  (failed search); `src/rust/crates/ui/src/command.rs:160`.
- Problem: `filter` is off as soon as the field holds two characters. `items` is replaced
  only when the next search answers (250 ms debounce plus the round trip) and is not touched
  when the search fails. Before this change the old list was filtered by the new text at
  once, so rows that did not hold the typed text disappeared; now the whole list of the
  previous query stays on screen and the first row is active (the query change resets the
  chosen row to the first).
- Failure scenario: type "dune", wait for the results (first row "Dune (2021)"), go on
  typing " messiah" and press Enter, or Ctrl+Enter, before the new answer is there. The
  palette opens "Dune (2021)", or with Ctrl+Enter adds it to the library as Planned
  (DEC-426), although the field says "dune messiah". On HEAD the list was empty at that
  moment and Enter did nothing. Second case: the new search fails (offline, 5xx):
  `Stream::failed` runs, `items` keeps the "dune" results for good, with no hint that they
  belong to another query.
- Fix: turn the client filter off only for results that belong to the text in the field.
  `Asked.query` already holds the query of the answer on screen:
  `filter = idle || asked.with(|a| a.as_ref().is_none_or(|a| a.query != query.get()))`.
  Stale rows are then filtered as typed (the behaviour of HEAD) until the answer of the new
  query arrives; answered results show as they came. Add a web or Playwright test: results
  for "aa", type on to a text the first row does not hold, Enter before the answer opens
  nothing / the list holds no stale row.

### OT1A-2 (medium) The OT-15 message follows the reader to another show and survives a refetch

- Where: `src/rust/crates/web/src/episode_list.rs:214`, `:396`; state lifetime in
  `src/rust/crates/web/src/item.rs:102` (`EpisodeUi::default()` once per `ItemPage`) and
  `:113-118` (the id-change effect clears only `inline`).
- Problem: `ui.note` is cleared by a mark that logs and by a season chip, nothing else.
  `ItemPage` keeps its `ItemUi` when only the route parameter changes (that is why the
  effect at `:113` exists), and across refetches by design.
- Failure scenario: on a finished show press "Mark show watched": "Every episode of this
  show is already watched. ..." appears. Open another, unwatched show through the palette
  (Ctrl-K, Enter): the Episodes tab of the new show states that every episode of this show
  is watched. Same within one show: the message is up, an episode is undone from the toast
  or History (or on another device); the page refetches and shows an unwatched row under a
  line that says all are watched. Not executed here; the first case rests on the router
  reusing `ItemPage` for `/items/:id`, which the existing effect at `item.rs:113` relies on.
- Fix: clear `ui.episodes.note` (and, while there, `error` and `ask`, which have the same
  lifetime on HEAD) in the id-change effect at `item.rs:113-118`, and clear the note when the
  rows change (for example in `EpisodeList` when it is built from new `progress`, or by
  deriving the visibility from `plan_bulk` still being `Err`). Extend the Playwright test
  "a bulk mark with nothing left to mark says so": navigate to a second show, expect the
  note empty.

### OT1A-3 (medium) Item page: two statements per play, in sequence, up to 100 per load

- Where: `src/rust/crates/app/src/activity.rs:691-697` (`item_plays`), called from
  `src/rust/crates/api/src/ops.rs` `item_page`; store side
  `src/rust/crates/store-pg/src/repos/sessions.rs:69-79, 143-145`.
- Judgement: `sessions.get(id)` is `sessions_where_ids(&[id])`, that is one `SELECT ... WHERE
  id = ANY($1)` plus the participants read of `load_sessions`. With the cap of 50 an item
  page of a much-played game runs up to 100 statements one after the other, plus
  `linked_to`, `users.get` and `companions.get_many`, on every load. The page refetches on
  every `entity.updated` of the item and after every log. The result is correct and bounded,
  so this does not block the commit, but the cost lands exactly on the items the owner's
  board game import creates (dozens of plays per game), and nothing measures it: the load
  run has no such item.
- Failure scenario: a game with 50 imported plays; each page view and each refetch after
  logging a play issues about 100 sequential round trips where HEAD issued none; on a
  database that is not on localhost (1 ms per round trip) that is 100 ms added to the item
  page.
- DEC-502 is wrong on one point: it lists the batched read as needing "a new sqlx query".
  The statement exists (`sessions_where_ids` takes a slice); only a port method is missing.
- Fix: add `SessionRepo::get_many(&[SessionId])` with a default body that loops over `get`
  (in-memory store) and a Postgres body that calls `sessions_where_ids`; `item_plays` then
  costs two statements for any number of plays. No new SQL, no `.sqlx` change. Keep the
  order by sorting the answer by the id list (the helper orders by `started_at DESC, id`).
  If deferred: correct the "alternatives" text of DEC-502 and add a play-heavy item to the
  load run.

### OT1A-11 (low) Events of other searches can fill the hold buffer

- Where: `src/rust/crates/web/src/palette.rs:336-345` (`Stream::arrived`, `MAX_HELD` 32).
- Problem: while a search is in flight every `search.results` event with another id is held,
  whichever search it belongs to, and the buffer stops taking events at 32.
- Failure scenario: the same account has the palette open in two tabs (events go to the
  user, not the tab) and both search; or one tab types fast with many sources: results of
  older searches arrive during the flight of the current one. If 32 of them come before the
  answer, the early batch of the current search is dropped, which is the defect item 5 was
  to remove. It needs more than 32 foreign events inside one round trip, so it is unlikely
  with today's handful of sources.
- Fix: when the buffer is full drop the oldest event instead of the new one, or keep only
  the newest event per `(search_id, connector)`.
