# Gate G2: independent review of the finished system

Date: 2026-11-06. Reviewer: a fresh session that did not produce any of the code. Scope:
`main` at `ca7b6de` (tag `m14` plus the M17 paging commit) against `docs/design/DESIGN.md`,
`docs/design/KICKOFF.md`, `docs/DECISIONS.md` (DEC-001..151), `docs/REPORT.adoc` and the
earlier reviews. Read-only: nothing was compiled or run; evidence is `path:line` relative to
the repository root (`src/rust/` prefix dropped for Rust paths).

## Summary verdict

The system is a solid, honestly reported partial build. What exists is well structured: the
hexagonal split is real and enforced (`xtask/src/arch.rs:11-56`), every REST handler and
server function resolves the caller before touching data, ownership checks live in the `app`
use-cases where both API surfaces share them, tokens are stored hashed, channel secrets are
redacted, Meilisearch filters are quoted and tenant-scoped with mutation tests. I could not
find an endpoint that returns another user's library, sessions, lists, channels, inbox,
deliveries or import reports.

Against KICKOFF, 12 of 18 milestones are complete (M00-M08, M13-M16), M09 and M12 are
partial, M10, M11 and M17 are not done, and G2 had not run. `REPORT.adoc` and DECISIONS say
so plainly; the gaps are reported, not hidden. The "known gaps" section is accurate but
incomplete (G2-5, G2-6, G2-13).

Real defects found: a login CSRF on the Leptos server functions (G2-1), cross-tenant catalog
poisoning through caller-supplied external ids (G2-2), a job lease that is never extended so
long imports run twice concurrently (G2-3), and no brute-force limit on sign-in (G2-4).
Nothing found is a data leak between accounts. Recommendation: fix G2-1..G2-4 before the
first multi-user deployment; the rest can follow with M17.

## Findings

### G2-1 (high) Login and logout CSRF on the server functions

Evidence: `crates/web/src/api.rs:81-131` (`sign_in`, `sign_up`, `sign_out` are `#[server]`
functions with the default URL encoding, so they accept `application/x-www-form-urlencoded`
POSTs); `crates/web/src/api.rs:56-68` sets the session cookie from the response;
`apps/server/src/lib.rs:516-522` mounts them under `/_fn/{*fn_name}` with no middleware.
`server_fn` 0.8.13 only reads `Referer` to redirect plain form posts; it has no `Origin` or
`Sec-Fetch-Site` check (registry source, `server_fn-0.8.13/src/lib.rs:295-344`).

A page on any origin can submit a hidden form to `/_fn/sign_in` with the attacker's
credentials. No cookie is needed for that request, so `SameSite=Lax` does not help. The
victim's browser is then signed in to the attacker's account; anything the victim imports,
rates or logs from then on lands in the attacker's library (readable through
`GET /api/v1/export`). `/_fn/sign_out` is a logout CSRF the same way. The REST handlers are
not affected (they take `Json<...>`, which a form cannot produce) and all other mutations are
covered by `SameSite=Lax` on the cookie (`crates/api/src/routes.rs:102-109`).

Recommendation: add one axum middleware on `/_fn/*` and `/api/v1/*` that rejects
state-changing requests whose `Origin` (or `Sec-Fetch-Site`) does not match
`server.public_url` when a session cookie is present or a session cookie would be set;
alternatively require a custom header (`X-Requested-With`) for server functions. Add a test
that posts a form to `/_fn/sign_in` with a foreign `Origin` and expects 403.

### G2-2 (medium) Any user can corrupt shared catalog items through external ids

Evidence: `crates/app/src/catalog.rs:218-239` (`ensure_catalog_item` finds an existing item
by the first matching id and then appends every other caller-supplied id to it);
`crates/integrations/src/lib.rs:277-289` and `crates/importers/src/lib.rs:433-445` pass ids
straight from the webhook body or import row; `crates/catalog-core/src/refresh.rs:35` picks,
per connector, the item's id in that connector's namespace; `crates/app/src/catalog.rs:167`
then overwrites the title (and attributes, description, cover) for everyone.
`crates/store-pg/src/repos/catalog.rs:91-94` only protects ids already claimed by another
item.

Attack: post `{"kind":"movie","title":"x","ids":{"imdb":"tt0133093","tmdb":"<id of another
film>"}}` to the webhook (or one import row). The shared "The Matrix" item gains a wrong TMDB
id, the queued refresh fetches the other film and rewrites title, year, description,
attributes and cover for every user on the instance. External ids are never removed, so the
damage repeats on every refresh. The same path lets a user pre-create items with arbitrary
titles for ids nobody searched yet (self-healing on refresh, but visible meanwhile).

Recommendation: in `ensure_catalog_item`, only attach caller ids when creating a new item;
for an existing item attach nothing (connectors add ids through `apply_catalog_refresh`).
Validate id namespaces against the connector registry plus a short allowlist (`imdb`). Add
an `app` test: a second `ensure_catalog_item` with a conflicting id leaves the item's ids
unchanged.

### G2-3 (medium) Job leases are never extended, so long jobs run twice at once

Evidence: `crates/jobs/src/worker.rs:40` (lease 300 s, not configurable), `worker.rs:88-115`
(claim, spawn, no heartbeat), `crates/jobs/src/queue.rs:118-119` (a running job with
`locked_until < now()` is claimable again). Imports process the whole file in one job
(`crates/importers/src/lib.rs:289-363`) with several queries per row (DEC-150 measures about
3 per entry); a 50 000-row import takes far longer than five minutes. After 300 s a second
worker slot claims the same job, both runs continue from the saved cursor, both push
`r.errors` and `r.imported`, and both overwrite the record (`lib.rs:349-357`). Library writes
stay idempotent, but the report is corrupt, the second run doubles the load, and the attempt
counter burns toward `dead` (`queue.rs:159`), after which the import record stays `Running`
forever: nothing sets `ImportState::Failed` when the job dies.

The M12 acceptance "kill the worker mid-import and restart finishes the import" is only
simulated in-process (`crates/importers/tests/generic.rs:119` calls `run_rows(id, Some(1))`
then `run`); no test exercises a lease expiry or a real worker restart.

Recommendation: extend the lease from `execute` while the handler runs (a ticker calling
`UPDATE jobs SET locked_until = ...`), or let handlers declare a lease per job kind. Mark the
import `Failed` from the job failure path when attempts are exhausted. Add a jobs test that a
job running longer than its lease is not claimed twice.

### G2-4 (medium) No brute-force protection on sign-in, TOTP or token endpoints

Evidence: `crates/api/src/routes.rs:145-163` and `crates/web/src/api.rs:81-98` call
`Auth::sign_in` with no limiter; `rg -i 'ratelimit|tower_governor'` over `apps/server` and
`crates/api` finds nothing; `crates/auth/src/lib.rs:243-271` has no failure counter. argon2
at the crate defaults costs tens of milliseconds, so a single client can try thousands of
passwords per minute; the 6-digit TOTP (`lib.rs:273-293`, skew 1) is brute-forceable once
the password is known. `/shared/lists/{token}`, `/invite/{token}` and `/hooks/watched`
accept unlimited guesses (tokens are 256-bit, so this is only a load concern).

Recommendation: a per-IP and per-username limiter on sign-in and TOTP (governor is already a
dependency), a lockout or growing delay after N failures stored in `credentials`, and a
generic per-IP limit on `/api/v1` and `/_fn`.

### G2-5 (medium) Sync pull hands out ids the client cannot resolve

Evidence: `crates/api/src/sync.rs:155-165` attaches state only for `library_entry` rows; the
feed also carries `progress_event`, `session`, `review`, `companion`, `list`, `link_request`
and `invite` rows (`crates/store-pg/src/tx.rs:58-72`, `rg 'record\(&mut tx, "'`). There is
no `GET` by id for progress events, sessions or reviews (`crates/api/src/routes.rs:29-83`),
and the change row does not carry the item id, so a client cannot fetch what changed.
DESIGN D-12 ("clients pull changes since cursor") and the M16 claim in `REPORT.adoc` ("M16
done") therefore hold only for library entries. Not listed under known gaps.

Recommendation: either embed the entity payload in `SyncChangeDto` for every entity, or add
`GET /api/v1/{progress-events,sessions,reviews}/{id}`; extend `crates/api/tests/sync.rs` to
replay a progress event and a session through the feed.

### G2-6 (low) Smaller coverage gaps not listed in REPORT.adoc

- KICKOFF M05/D-3 ask for `cli` user management and imports. `apps/cli/src/main.rs:1` claims
  both, but the parser (`main.rs:65-79`) has only `migrate`, `storage report|evict` and
  `reindex`. `App::delete_user` (`crates/app/src/users.rs:93-117`, the D-9 demotion on
  account deletion) is reachable from nowhere, and no admin can change roles.
- `web` lists `app` as an `ssr` dependency (`crates/web/Cargo.toml:32,44`) but never uses it
  (`rg 'app::' crates/web/src` finds only `crate::app`). DEC-092 made `Backend` the only
  path; the dependency and the `FEATURE_GATED_DEPS` rule for it are dead weight.
- M14 acceptance says "posting a Jellyfin playback-stop payload"; the test
  (`apps/server/tests/webhook.rs:15`) posts the project's own format. DEC-149 explains why;
  REPORT should say the acceptance was redefined.
- M09: `crates/connectors/tests/tvdb.rs:14` asserts no images; only TMDB's attribution is
  asserted end to end (`src/web/tests/slice.spec.ts:40`).
- Every Postgres and Meilisearch test is green when the service is absent
  (`crates/store-pg/src/testing.rs:14-37`, skip unless `REQUIRE_SERVICES`), so the KICKOFF
  per-crate acceptance commands pass with zero database tests run. CI and `cargo xtask ci`
  set `REQUIRE_SERVICES=1` (`xtask/src/main.rs:109`, `.gitlab-ci.yml:88`); REPORT should
  name `xtask ci` as the proving command.

Recommendation: add these to "Known gaps"; remove the unused `app` dependency from `web`;
add `cli user list|set-role|delete` or drop the claim from the CLI header.

### G2-7 (low) SSRF guard can be bypassed by DNS rebinding; test sends are unlimited

Evidence: `crates/notify/src/channels/http.rs:101-128` resolves the host and checks the
addresses, then `crates/catalog-core/src/plain.rs:35-44` lets reqwest resolve again (the
comment at `http.rs:96-97` admits the gap). Redirects are off and the body is not returned,
so the result is a blind POST with a user-controlled JSON body to any LAN address. Any user
can trigger it at will through `POST /notifications/channels/{id}/test`
(`crates/api/src/notifications.rs:228-235`) with no rate limit.

Recommendation: resolve once and pin with `reqwest::ClientBuilder::resolve_to_addrs` (or
connect to the checked IP and set `Host`), and limit test sends per user per minute.

### G2-8 (low) Webhook idempotency depends on the sender supplying `watched_at`

Evidence: `crates/integrations/src/lib.rs:304-317` builds the dedupe key from
`watched_at.unwrap_or(now)`. The Jellyfin webhook plugin retries without a stable timestamp
unless the user's template adds one; every retry then records a new play, which also
re-triggers `integration.play_recorded` with a new `play:{op}` key. The doc comment says
"the same play posted twice is recorded once", which is only true with `watched_at`.

Recommendation: require `watched_at` (422 without it) or dedupe on (item, season, episode)
within a short window; document it in `integrations.adoc`.

### G2-9 (low) Session updates reach linked users who were opted out

Evidence: `crates/app/src/sessions.rs:330-341` (`publish_session`) adds every linked
participant to the SSE audience regardless of the owner's `share_sessions`, while
`announce_session` (`sessions.rs:91-99`) and `shared_sessions` (`sessions.rs:251-268`)
honour it. Only the session id and `entity.updated` leak, but a client can learn that a
session with them exists.

Recommendation: check `shares_sessions(owner)` in `publish_session`.

### G2-10 (low) Missing input limits on catalog fields and one body limit for everything

Evidence: `crates/app/src/catalog.rs:38-42` only rejects an empty title; the webhook and
importer pass user text into `title`, `year` and id values with no length cap, and
`routes.rs:91` applies the 64 MiB import limit to every `/api/v1` route including the JSON
ones. Names elsewhere are capped (`crates/domain/src/companion.rs:35`, `list.rs:41`,
`review.rs:10`).

Recommendation: cap title and `original_title` (for example 500 chars), description (20 000),
external id namespace and value (64), and give the import route its own `DefaultBodyLimit`
while the rest get 1 MiB.

### G2-11 (low) Four hand-written pass-through layers per operation

Evidence: each UI operation exists as a REST handler (`crates/api/src/routes.rs`), an
`api::ops` function, a `Backend` trait method (`crates/web/src/backend.rs`), a `WebBackend`
method (`apps/server/src/web_backend.rs`, 332 lines of forwarding) and a `#[server]`
function (`crates/web/src/api.rs`, 401 lines of forwarding). Adding one operation touches
five files. The design is sound (DEC-092); the duplication is the maintenance cost.

Recommendation: allow `web -> api` under `ssr` (a DEC like DEC-006) and let the server
functions call `api::ops` directly, deleting `Backend` and `WebBackend`; or generate the
server functions from the trait with a macro.

## Architecture (D-3, D-4, D-15)

Dependency rule: real and transitive (`xtask/src/arch.rs:11-56`, run in CI by
`xtask/tests/architecture.rs`); `domain`/`app` depend on nothing forbidden; `ui` has no
workspace deps; connector-like crates cannot take an HTTP client directly (DEC-040). Ports
(`crates/app/src/ports.rs:39-421`): 20 traits, each with a real adapter and a memory fake;
none is ceremony. Both API surfaces share `api::ops` and authorization lives in `app`, so
REST and server functions cannot drift. The shared catalog is the one place where
multi-tenancy is by trust (G2-2); the pass-through layers are the DRY cost (G2-11).

## Security and correctness summary

Every route in `crates/api/src/routes.rs:29-83` and every `#[server]` function in
`crates/web/src/api.rs` requires a session except `sources`, `web_push_key`, `shared_list`,
`healthz`, `/assets` and the auth endpoints; `watched_hook` takes only integration tokens
(DEC-151, tested). Ownership is enforced in the use-cases for companions, link requests,
invites, lists, sessions, imports, channels, subscriptions, templates and integrations.
Progress events are unique per `(user_id, client_op_id)` (`migrations/0001_core.sql:107`).
Session, invite and integration tokens are stored hashed; channel secrets are redacted and
kept on update (`crates/notify/src/model.rs:71-120`); connectors send keys in headers, so
the HTTP cache key never holds credentials; OIDC checks state, PKCE and nonce
(`crates/auth/src/oidc.rs:179-197`). Jobs (dedupe, lane order, backoff, cron), outbox
atomicity, HLC merge with the 5-minute drift cap (`crates/app/src/lib.rs:66-78`), zero-stamp
defaults and notification dedupe (`migrations/0010_notifications.sql:36`,
`crates/notify/src/engine.rs:195-203`) are correct and tested. Open items: G2-1..G2-5,
G2-7..G2-10.
