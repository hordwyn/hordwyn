## Must fix before commit

### SEC0-1 (medium) The notifications REST routes still answer 500 with the store's text

- Where: `src/rust/crates/api/src/notifications.rs:33-35` (`fn port`), used as
  `.map_err(port)` on 22 call sites of that file (inbox, channels, subscriptions,
  deliveries, templates, instance defaults, ...).
- Problem: `port` builds `ApiError::new(INTERNAL_SERVER_ERROR, "internal", e.0)`. `e.0` is
  the text of `notify::pg` (`crates/notify/src/pg.rs:22`: `notifications db: {sqlx error}`).
  This is the same leak as SEC-9, one file away from the one that was fixed. DEC-648 says
  "the three places that answer the generic 500 ... share `ApiError::internal`"; this fourth
  one does not, and it does not log either.
- Failure scenario: the database is restarted or a migration is missing. Any signed-in
  member (session or API token) calls `GET /api/v1/notifications/channels` and reads
  `{"code":"internal","message":"notifications db: error returned from database: relation
  \"notify_channels\" does not exist"}`. Nothing is logged, so the operator has no line
  with the request id. Server functions are not affected (`server::code` passes the code
  only); REST is.
- Fix: replace the body of `port` with `e.into()` (`From<PortError> for ApiError`, which
  logs with the request id), or drop the helper and use `ApiError::from`. Add a test next
  to `a_storage_failure_behind_the_webhook_answers_with_the_generic_text` with a failing
  `NotifyStore`. Correct the count in DEC-648.
- Note: outside the letter of the plan (it names `hooks.rs`), inside the review question
  "no storage text reaches any client". One line; v1 is internet-facing (HANDOFF 4.8).

### SEC0-2 (medium) The in-place update is silent for assistive technology (WCAG 4.1.3)

- Where: `src/rust/crates/web/src/notify_channels.rs:284` (`StatusDot` with the live
  health), `:287-292` (the "failing" `Alert` with `role=AlertRole::None`, now shown and
  removed in place); `src/rust/crates/web/src/notifications.rs:480-485` (log rows).
- Problem: before this package the health text and the failing alert only changed with a
  page build that the person had asked for. Now they change on their own while the page is
  open, and none of the changed nodes is in a live region (`ui::StatusDot` is two plain
  spans, the alert has no role). HANDOFF 4: WCAG 2.2 AA everywhere; 4.1.3 Status Messages
  asks that such a change can be presented without moving focus.
- Failure scenario: a screen-reader user adds a webhook channel, turns on a rule and stays
  on the Channels tab. A delivery fails; the card changes from "Never used" to "Last
  delivery failed ..." and an error box appears. Nothing is announced; the user learns of
  the failure only by reading the card again.
- Fix: one polite live region for the page (`role="status"`, visually hidden, as
  `ui/src/toast.rs:151` does) that gets a sentence when a later read changes the health
  state of a channel ("Automation: last delivery failed"), written in `refresh_deliveries`
  only when the state differs from what is shown. Do not make the alert `role="alert"`:
  it is also rendered on a normal page build and would then be read on every load. Add an
  assertion to the first new browser test (`getByRole("status")` contains the sentence).
- Focus: the cards keep their nodes, so focus inside a card (Test, Edit, a half-typed
  form) is kept; that part is fine. For the log see SEC0-5.

### SEC0-3 (medium) "a channel is edited in place": the tab click closes half of the race

- Where: `src/web/tests/notifications.spec.ts:152-154` (new `tab(page, "Channels")`),
  cause in `src/rust/crates/web/src/notifications.rs:255-260` (`notification.new` ->
  `data.refetch()`, the whole page is built anew).
- Assessment of the change itself: legitimate. `first_tab` (`notifications.rs:109-115`)
  is a fixed, documented rule (inbox when something is unread, else channels); the test
  started an import and then assumed nothing was unread. The page does open on a stable
  tab for a given state; the test's precondition was not stable. No app problem is hidden
  by the click.
- Problem: the same import can also finish after the page has loaded. Its "Import
  finished" row is announced as `notification.new`, and the page is then built anew, which
  drops the "Add a channel" form and an open "Edit" form (stated by the package itself:
  progress log "Out of scope, noticed", second item; DEC-649 "a rebuild drops a
  half-filled form"). The window moved from "before `page.goto`" to "while lines 156-168
  type".
- Failure scenario: the import finishes while `addChannel` has chosen "ntfy" and filled
  "Name" but not yet "Topic". The page is rebuilt, the radio is back on its default and
  the name is empty; "Add and send a test" fails validation or the "Topic" label is not
  found, and the test fails at line 156 or 158. Same for the edit form (lines 159-168: the
  rebuild closes it, `name.fill("Pocket")` finds no field). The first side of this race was
  seen once in ten runs; this side is the same import a second later. A person filling the
  form while any notification arrives loses the input the same way.
- Fix (either; the first is the smaller one):
  1. Test precondition made deterministic: `await importDone(page, importId)` before
     `page.goto(PAGE)` (line 150), keep the tab click (the page then always opens on the
     inbox). Line 180 can stay. This is not a wait for the app to settle a race; it fixes
     what the test set up. Record the app defect as an open item of the next package.
  2. Fix the app: treat `notification.new` like `notification.delivery` (read, show the
     inbox rows and the unread count in place), so no event rebuilds the page under a form.
     Larger; fits v1-polish.
  Committing with only the tab click leaves a known flake in the gate.

### SEC0-4 (low) A delivery answer is dropped while the page is not built yet

- Where: `src/rust/crates/web/src/notifications.rs:217-223` (`found` is `None` while
  `state.built` is `None`, then `return`).
- Problem: `refresh_deliveries` needs the page it compares against. During the first read
  of a page reached inside the app (no read on opening, the stream is open already) there
  is none, and the fresh answer is thrown away instead of being kept.
- Failure scenario: Settings > Notifications is opened by a link inside the app. The page
  read is answered by the server, a delivery fails right after that read, the announcement
  arrives and its read is answered before the first page has rendered (the page read is
  the slower of the two answers, or the answer of the second read is handled between the
  resource resolving and `Page` running). The card then shows "Never used" / the log
  "Queued" until the next event or reload: the original symptom in a window of some
  milliseconds.
- Fix: do not require `built` for `live`. Compute `Live` from `fresh` always and set it
  with its read number; use `built` only to decide `page`. `Page` already drops a `live`
  that is older than the read it is built from (`:298-304`), and this one is newer.

### SEC0-5 (low) A log row that is retried is replaced: its error folds and focus is lost

- Where: `src/rust/crates/web/src/notifications.rs:481`
  (`key=|d| (d.id, d.state, d.attempts, d.last_error)`).
- Problem: the key holds everything that can change, so "in place" is true only for rows
  that did not change. A changed row is removed and built again.
- Failure scenario: a channel answers 503. The delivery stays "Queued" with an error and
  is retried. A keyboard user has unfolded "Show the error" on that row and has focus on
  the summary. The next attempt changes `attempts`: the row is removed, focus falls back to
  the document, the error is folded again. DEC-649 gives "an unfolded error stays" as the
  reason for the design; it does not hold for the row that is changing (WCAG 2.4.3, 3.2.x
  spirit: content the person is using is taken away without their action).
- Fix: key by `d.id` alone and let the state cell read the row from a signal
  (`Memo` per id over `rows`), so badge and error text change inside the same nodes.

### SEC0-6 (low) `body_limit` collects up to 2 MiB for every page path, with no time limit

- Where: `src/rust/apps/server/src/lib.rs:852-886`, placed at `:835`.
- Problem: the middleware reads the body into memory before anything else runs, for every
  method and every path of the pages router (pages, `/pkg`, the fallback), not only
  `/_fn/*`. A page handler never read its body before. There is no read timeout in the
  server (`grep timeout apps/server/src` finds none).
- Failure scenario: 1,000 connections each send `GET /` with a chunked body of 2 MiB minus
  one byte and then stall. The process holds about 2 GiB without a session and without a
  handler having run; on the 4 GB home instance of HANDOFF 4.8 that is an out-of-memory
  kill. Not a regression for `/_fn/*` (the library collected up to 2 MiB there before);
  new for the other paths.
- Fix: collect only where a body is used (`/_fn/`), and for the rest keep the
  `Content-Length` check and hand the body on wrapped in a length limit instead of
  collecting it; plus a body read timeout. The timeout belongs to sec2 (throttling); name
  it there.
- Also at `:877`: a body read error answers a bare `400` without the `ErrorDto` shape the
  413 next to it uses. The sender is gone in that case; cosmetic.

## Checked, no finding

Body limit (SEC-2)
- Placement: `request_meta` -> `csrf::guard` -> `body_limit` -> `resolve_shell_session` ->
  `sso_redirect` -> `pkg_no_cache` -> handler. Before the session is looked up; the 413
  carries `x-request-id`; a cross-site request is still refused first (403), without its
  body being read. The plan's "before `guarded`" is ambiguous; this order is the safe one.
- Coverage: `/_fn/{*fn_name}`, all Leptos routes and the fallback (which also serves
  unknown `/api/v1/...` paths after the merge) are under the layer. REST keeps
  `DefaultBodyLimit` 2 MiB, raw readers use `to_bytes(.., JSON_BODY_LIMIT)`
  (`oidc_routes.rs:443,491`), `Bytes` extractors honour the default. `/healthz`,
  `/assets`, `/brand/fonts`, `/api/v1/events` read no body.
- Chunked / no `Content-Length`: read piece by piece, stops at the first piece that
  crosses the limit, 413; tested with a counting stream. HEAD/GET with a body: same path,
  method is not looked at. A non-numeric or absent length falls to the streamed path.
  Request parts (headers, extensions) are kept; the handed-on body equals the read bytes.
- Import: `IMPORT_BODY_LIMIT` (64 MiB) layer on REST untouched; guard test with 3 MiB.
- Near 2 MiB: no new failure. The number is the one `server_fn` 0.8.13 applied before
  (`into_limited_body`, checked in the registry source); bulk undo see SEC0-8; imports,
  avatar and brand uploads do not go through server functions.
- 413 format: `ErrorDto` JSON, code `too_large`, as REST. The `server_fn` client cannot
  decode it and shows the generic text, as it did for the earlier 500; no legitimate
  client sends such a body.
- `body_limit` is 35 lines.

SEC-9
- Webhook: `IntegrationError::Port` -> `From<PortError>`: 500, `internal`, "internal
  error". `App` arm: `Repo` generic, the other texts are application sentences.
- Card and `integration.call` event: both `CallRecord` sites use `card_error`.
- Log line: store text plus request id, no request body, no token. `request_meta::current`
  is a task-local of the request, present for REST and server functions.
- Notification log and channel health show `SendError` text (what the channel answered),
  never a store error (`deliver.rs`: store errors go to the job's `Err`, not to
  `last_error`). Server functions pass error codes only.

Notifications fix
- Audience: `Delivery.user` is the user whose channels were read (`engine.rs:219-241`), so
  the event goes to the channel's owner only; `realtime::visible_to` filters by audience.
  Payload: one channel id of the owner. No other user's delivery can be learned.
- Digest: one event for the batch, also when suppressed; events are published after the
  write. Cross-process: the bus is `pg_notify` when web and worker are apart.
- `StreamOpens` / `read_at`: a loaded page reads once more when the stream opens, a page
  reached inside the app does not; a reconnect reads again; paced at one read per 2 s.
  One extra page read per full load of this one page is acceptable.
- Read numbering: followed the orders of answers (page read before/after a delivery read,
  queued refetch). A newer delivery state can be dropped for the moment between two page
  builds, never for good, apart from SEC0-4.
- `later`: no field of the page DTO changes by time alone, so an unchanged page is not
  rebuilt by a delivery event.
- `data-delivery` in the first test: legitimate. The locator `rows.filter("Failed")
  .first()` is resolved again on every use; with a log that follows deliveries the second
  failed row sorts above the first, so the test clicked one row and looked at another.
  Naming the row by its id is what a test of a live list has to do; no wait or retry.

- Function length: `ChannelCard` is 105 physical lines (`notify_channels.rs:232-336`),
  under 100 by clippy's count (comments not counted); the log reports clippy clean. The

- Scope: `refresh_on_updates` was rewritten onto the shared `Paced` (same behaviour,
