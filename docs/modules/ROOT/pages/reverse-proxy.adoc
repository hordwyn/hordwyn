= Behind a reverse proxy

The application speaks plain HTTP on port 3000 and expects a reverse proxy that terminates
TLS in front of it. Compose publishes the port on `127.0.0.1` only
(xref:install.adoc[Install and first run]).

== What the application needs

[cols="2,4"]
|===
|Setting |Value

|`APP__SERVER__PUBLIC_URL`
|The external address with its scheme, `https://tracker.example.org`, no path.

|`APP__SERVER__TRUSTED_PROXIES`
|The address the proxy connects from, as a list: `["127.0.0.1"]` does not fit a container
(the application sees the compose network's gateway); use the compose network, for example
`["172.16.0.0/12"]`, or the proxy host's address. Only then `X-Forwarded-For` is believed.
Not optional behind a proxy: the sign-in limits count per client address, and without this
setting every visitor has the proxy's address and shares one budget (<<limits>>).

|`APP__AUTH__SECURE_COOKIES`
|Stays `true` (the default) behind TLS.
|===

What the proxy must do:

* pass the `Host` header unchanged (the cross-site request check compares the browser's
  `Origin` with the public URL and with `Host`);
* set `X-Forwarded-For` (the visitor's address in the audit log) and `X-Forwarded-Proto`;
* not buffer the event stream `/api/v1/events` (server-sent events: live updates, search
  results as they arrive) and not cut it after a short idle time;
* allow request bodies of 64 MiB (import uploads; everything else stays under 2 MiB);
* close its idle connections to the application sooner than the application does (150
  seconds; the defaults of Caddy and nginx are below that, <<limits>>);
* compress responses if you want compression: the application sends none itself.

[#limits]
== Sign-in limits and time limits

The application slows down guesses at passwords and codes by itself
(xref:operations.adoc#sign-in-limits[Operations, Sign-in limits]): the pair of account and
client address waits longer after each failure, and a client address may fail 30 times in
15 minutes across all names before it is refused for a while. The client address is the
one `APP__SERVER__TRUSTED_PROXIES` yields. If the proxy is not listed there, the
application sees one address for everybody: thirty wrong passwords by anyone then close the
sign-in for all, the owner included, until the window is over. The owner must therefore set
`APP__SERVER__TRUSTED_PROXIES` behind a proxy. The server logs a warning (at most once an
hour) when a request with `X-Forwarded-For` arrives from an address that is not trusted,
and Admin > Overview shows a "Reverse proxy" warning row while such requests come from a
private address (the usual place of a proxy).
A limit of its own at the proxy (requests per address on `/api/v1/auth/` and `/_fn/`) is
not needed and can stay out.

Requests that stall are given up, by settings in seconds:

[cols="2,1,4"]
|===
|Setting |Default |What it limits

|`APP__SERVER__HEADER_READ_TIMEOUT_SECS` |150
|The head of a request (request line and headers); the connection is closed. It is also how
long an idle keep-alive connection is kept, and that is why the default is this long: the
proxy has to close its idle connections to the application first, or it can send a request
into a connection that is just being closed ("connection reset by peer"; Caddy's
documentation of `keepalive` warns of exactly this). Caddy keeps idle connections for 2
minutes by default (`keepalive` of the `http` transport: "Default: `2m`"), nginx for 60
seconds (`keepalive_timeout` in an `upstream` block: "Default: keepalive_timeout 60s";
"Since 1.29.7, keepalive connections are enabled by default"). Both
pages read 2026-11-13: https://caddyserver.com/docs/caddyfile/directives/reverse_proxy,
https://nginx.org/en/docs/http/ngx_http_upstream_module.html. If you lower this setting,
lower the proxy's time below it as well.

|`APP__SERVER__BODY_IDLE_TIMEOUT_SECS` |30
|The longest pause inside a request body; the request is answered `408`.

|`APP__SERVER__BODY_READ_TIMEOUT_SECS` |60
|A whole request body, for everything except the import upload; the request is answered
`408`.

|`APP__SERVER__IMPORT_READ_TIMEOUT_SECS` |1800
|The whole body of an import upload (up to 64 MiB: about 0.3 Mbit/s); the request is
answered `408`.
|===

The application speaks HTTP/1.1 only, which is what a proxy speaks to the application; a
client that opens a connection and sends nothing is cut off after the head limit too. A
proxy that buffers request bodies (nginx by default) sends them in one go, and its own limits
(`client_header_timeout`, `client_body_timeout`) are what a slow visitor meets first; the
application's limits then cover what reaches it directly.

== Security headers

The application sends them itself, on every answer (pages, the API, files, refusals). The
proxy passes them on and sets none of them: a second `Content-Security-Policy` from the
proxy would apply in addition to the application's, and a policy written at the proxy
cannot know the per-answer nonce of the inline scripts.

Not covered that way: what the proxy answers by itself, for example its `502` while the
application restarts during an upgrade. Such an answer has none of the headers. Its content
is the proxy's own short error text, so this is a small gap; <<proxy-defaults>> shows how to
close it with Caddy.

[cols="2,4"]
|===
|Header |Value

|`Content-Security-Policy`
|On pages: scripts and styles only from the instance and inline ones with the nonce of that
answer, WebAssembly may be compiled (`'wasm-unsafe-eval'`, no `eval`), pictures from the
instance, `data:` and any HTTPS host (covers come straight from the data sources and
podcast hosts), connections only to the instance, forms only to the instance and to the
end-session address of an enabled sign-in provider, no plugins, no `<base>`, no framing
(`frame-ancestors 'none'`). On everything that is not a page:
`default-src 'none'; frame-ancestors 'none'`.

|`X-Content-Type-Options` |`nosniff`
|`X-Frame-Options` |`DENY`
|`Referrer-Policy` |`same-origin`: other sites learn nothing about the instance from a link
or a picture, not even its name.
|`Permissions-Policy` |camera, microphone, location, payment, USB, MIDI, screen capture and
the motion sensors are switched off.
|`Strict-Transport-Security` |`max-age=31536000`, only when `APP__SERVER__PUBLIC_URL` starts
with `https://`. Without `includeSubDomains`: the application does not know the other names
of the domain.
|`Cache-Control` |`no-store` on pages, the API and server functions; pictures, fonts and
the application bundle are cacheable (the bundle's file names change with every build).
|===

Two settings:

`APP__SERVER__HSTS_MAX_AGE_SECS`:: The age in seconds; `0` sends no
`Strict-Transport-Security`. A browser that has seen the header refuses plain HTTP for that
host until the time is over, so set `0` (or a small number) while you are still trying an
address out, and `0` if the proxy sends its own header (for example with
`includeSubDomains`): of two such headers a browser reads only the first.
+
Taking it back: `0` only stops the application from sending the header; a browser that has
already seen it keeps refusing plain HTTP until its time is over. A browser forgets the rule
when it receives `Strict-Transport-Security: max-age=0` over HTTPS (RFC 6797, section 6.1.1:
https://www.rfc-editor.org/rfc/rfc6797#section-6.1.1), and the application has no value
that sends this. So before a host name goes back to plain HTTP (or to a service without
TLS): set `APP__SERVER__HSTS_MAX_AGE_SECS=0`, let the proxy send the header with
`max-age=0` while the name still answers over HTTPS (Caddy:
`header Strict-Transport-Security "max-age=0"`; nginx:
`add_header Strict-Transport-Security "max-age=0" always;`), and keep that up until every
browser that used the instance has opened it once. A browser that does not come by in that
time keeps the rule for the rest of the age it was given.

`APP__SERVER__CSP_REPORT_ONLY`:: `true` sends the policy as
`Content-Security-Policy-Report-Only`: the browser lists in its console what the policy
would refuse and refuses nothing. For finding out whether the policy is why something does
not load; not for normal operation.

Sign-out through a provider: the sign-out button posts a form to the application, which
redirects the browser to the provider's end-session address. A browser may hold each
redirect of a form against the policy (CSP Level 3, `form-action`:
https://www.w3.org/TR/CSP3/#directive-form-action), which is why the policy names the
origin of that address; the entry is needed and stays. It names that origin only: a
browser that checks stops a provider that redirects on to another host from there; the
session of the application is already ended at that point.

[#proxy-defaults]
=== Headers on the proxy's own answers (optional)

Caddy can set a header only when the answer has none yet (`?` in front of the field name:
"The field is only written if it doesn't yet exist", Caddy documentation, `header`, read
2026-11-13: https://caddyserver.com/docs/caddyfile/directives/header), so the
application's headers stay the only ones on its answers:

[source]
----
tracker.example.org {
    encode zstd gzip
    header ?X-Content-Type-Options nosniff
    header ?X-Frame-Options DENY
    header ?Strict-Transport-Security "max-age=31536000"
    reverse_proxy 127.0.0.1:3000
}
----

Never do this for `Content-Security-Policy` (see above), and leave the
`Strict-Transport-Security` line out while `APP__SERVER__HSTS_MAX_AGE_SECS` is `0`. nginx
has no such form: its `add_header` puts a second header next to the application's, so the
nginx snippet below stays without. Not tried on the project's build host; in particular it
was not checked whether Caddy puts these defaults on the error answer it writes when the
application is not reachable.

== Caddy

[source]
----
tracker.example.org {
    encode zstd gzip
    reverse_proxy 127.0.0.1:3000
}
----

Caddy passes `Host` through, sets `X-Forwarded-For`, `X-Forwarded-Proto` and
`X-Forwarded-Host`, and flushes `text/event-stream` responses immediately, so the event
stream needs no extra line (Caddy documentation, `reverse_proxy`, read 2026-11-12:
https://caddyserver.com/docs/caddyfile/directives/reverse_proxy). Its documentation names no
default limit for request bodies.

== nginx

[source]
----
server {
    listen 443 ssl;
    http2 on;                 # nginx 1.25.1 or newer. Older (Debian 12 ships 1.22): delete
                              # this line and write "listen 443 ssl http2;" above
    server_name tracker.example.org;
    # ssl_certificate and ssl_certificate_key as on your host

    client_max_body_size 64m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # live updates: no buffering, no short read timeout
    location /api/v1/events {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 1h;
    }
}
----

`$http_host` is the `Host` header as the browser sent it, with the port if there is one.
`$host` drops the port; for an instance reached on another port than 443 the cross-site
request check can then no longer fall back on comparing `Origin` with `Host`, and every
form answers 403 until `APP__SERVER__PUBLIC_URL` is exactly right. The `http2` directive
exists since nginx 1.25.1 (https://nginx.org/en/docs/http/ngx_http_v2_module.html#http2);
`nginx -t` of an older version refuses it as an unknown directive.

== Check

. `curl -sI https://tracker.example.org/healthz` answers `200` and shows
  `content-security-policy`, `x-content-type-options`, `x-frame-options`, `referrer-policy`,
  `permissions-policy` and `strict-transport-security`, each once. One of them twice means
  the proxy sets it too: remove it there.
. Sign in from another machine. A sign-in page that comes back without a message means the
  session cookie was dropped: the public URL is not HTTPS while secure cookies are on.
. A `403 cross-site request refused` on every form means the proxy rewrites `Host` or
  `APP__SERVER__PUBLIC_URL` is not the address in the browser.
. Open the same title in two browser windows and log it in one: the other updates without
  a reload. If it does not, the proxy buffers the event stream.
. Admin > Audit log shows your own address, not the proxy's.
. Type a wrong password for one account several times in quick succession. The first three
  failures cost nothing; from the fourth on, each one adds a wait that doubles (1, 2, 4, 8
  seconds, ...), so the first waits are over before a person has typed again. After about
  seven or eight quick failures the page says "Too many failed attempts. Try again in N
  seconds." (a loop with `curl` shows it faster: the answers turn from `401` to `429` with a
  `Retry-After`). Stay well below 30 failures: from the thirtieth in 15 minutes the whole
  address is refused. From another network (a phone without Wi-Fi) the same account signs
  in without a wait at that moment. If it has to wait too, the application sees the proxy's
  address for both: check `APP__SERVER__TRUSTED_PROXIES`.

The snippets were written from the Caddy and nginx documentation and were not run on the
project's build host.
