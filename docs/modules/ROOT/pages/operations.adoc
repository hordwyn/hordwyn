= Operations

The server binary runs as `server [--config <file>] [--role=all|web|worker]` and the admin
tool as `cli [--config <file>] <command>`; both read the same configuration (file plus
`APP__*` environment variables, see xref:configuration.adoc[configuration reference]).

== Roles

[cols="1,3"]
|===
|`--role=all` |Default. Web (pages, REST API, SSE, `/assets`) and worker in one process.
|`--role=web` |HTTP only. Events from workers arrive over Postgres `LISTEN/NOTIFY`.
|`--role=worker` |Job queue (catalog refresh, image fetch, eviction, cron) and the search
indexer. Run as many as you like; jobs are claimed with `FOR UPDATE SKIP LOCKED`.
|===

Every process applies pending database migrations at start-up (`cli migrate` does the same
on demand).

== Upgrade notes

Going back to an older build is done by restoring the database dump taken before the
upgrade (see Backup), not by starting the older binary on the migrated database.

[cols="1,4"]
|===
|Migration |What to know

|`0032_coop_no_result`
|One-way for the data written after it. The migration only widens a check: a co-op play can
be stored without a result (`sessions.coop_outcome = 'none'`); no existing row is changed.
Once such a play has been logged, a build from before this migration cannot read that
account's plays any more (History, People and the game's page fail with a corrupt-row
error). To go back without a restore, first set those rows to no outcome and put the old
check back: `UPDATE sessions SET coop_outcome = NULL WHERE coop_outcome = 'none';`, then
`ALTER TABLE sessions DROP CONSTRAINT sessions_coop_outcome_check, ADD CONSTRAINT
sessions_coop_outcome_check CHECK (coop_outcome IN ('won', 'lost'));`. Those plays then read
as competitive plays without a winner.
|===

== Backup

Postgres is the source of truth. Back up:

* the Postgres database (`pg_dump -Fc`), which includes the job queue, the outbox, the
  storage index and all user data;
* user uploads in the blob store: objects under `up/` (fs backend: `<fs_root>/up/`). Image
  variants (`img/`) and cached provider responses (`http/`) are derived data and are
  regenerated on demand after a restore;
* the brand directory if you changed it;
* the secrets key file (`secrets.key`, see below). The database dump and the key file are
  one backup unit: a dump restored without its key yields locked secrets.

Meilisearch does not need a backup: after a restore run `cli reindex --clear`.

== Secrets at rest

Data-source keys entered in the admin area, notification channel secrets and TOTP seeds are
stored encrypted (AES-256-GCM, envelope encryption: a random data key per value, wrapped by a
versioned key-encryption key). Each value is bound to its purpose, row and field, so a value
copied elsewhere does not decrypt. Passwords, session, invite and integration tokens and TOTP
recovery codes are hashed, not encrypted.

Where the key comes from, first match wins:

. the key file `secrets.key_file` (`APP__SECRETS__KEY_FILE`, default `data/secrets.key`; the
  container image uses `/data/secrets.key`): one key per line, `v<n>:<base64 of 32 bytes>`,
  newest first;
. `APP__SECRETS__KEYS`: the same lines joined with `,`. Environment variables can leak through
  process listings and crash dumps, so the file is the recommended path; docker and podman
  secrets mount as files.

On the first start without either, the server generates `v1`, writes the file with mode 0600
and logs one line. If the database already holds encrypted values but no key is found, the
server refuses to start and names the file and the variable: restore the key file. A value
whose key version is not loaded (or that fails to decrypt) is shown as locked; it is never
deleted, and it unlocks when the right key is back. With the in-memory storage backend (tests,
demos) and no key configured a temporary key is used.

=== Rotating the key

Rotate every two years or when staff changes (the admin overview reminds after two years):

. generate 32 random bytes, for example `head -c 32 /dev/urandom | base64`;
. add `v2:<base64>` as the first line of the key file (keep the `v1` line) and restart;
. Admin > Security: "Re-encrypt now" re-wraps every value with `v2` (a nightly job does the
  same while values are left on an old version); the page shows the rows per version;
. when no value uses `v1` any more, the page marks it removable: delete the line yourself once
  no backup you keep still needs it. The server never edits the key file.

== Search index

[source,shell]
----
cli reindex           # queue every catalog item, library entry and companion
cli reindex --clear   # empty the indexes first (removes documents of deleted rows)
----

The worker's indexer processes queued rows in batches of 200. If Meilisearch is unreachable
when a process starts, that process uses the Postgres fallback search (logged as an error);
restart it once Meilisearch is back.

The server talks to Meilisearch with the master key only at start-up, to configure the
indexes and to create (or reuse) a key limited to this deployment's indexes
(`search.index_prefix`) and to search and document actions. Browsers never receive any
Meilisearch key; every query goes through the server, which adds the owner filter for
per-user indexes.

== Storage report

[source,shell]
----
cli storage report --dry-run   # usage, limits, S3 counters, what eviction would remove
cli storage report --json
cli storage evict              # evict now instead of waiting for the background job
----

The report also shows the Postgres database size and, with the Meilisearch backend, its
document count and database size. Both are reported, not budgeted. See
xref:storage-budget.adoc[storage budget].

== S3 storage with compose

The compose file uses the `fs` storage backend by default. For an S3 backend it ships an
optional RustFS service (Apache-2.0) in the profile `s3`; a one-shot `s3-init` service
creates the bucket `assets`. Set `S3_ACCESS_KEY` and `S3_SECRET_KEY` in `config/.env`, point
the app at the service there and start with the profile:

[source,shell]
----
# config/.env
S3_ACCESS_KEY=...
S3_SECRET_KEY=...
APP__STORAGE__BACKEND=s3
APP__STORAGE__S3__ENDPOINT=http://s3:9000
APP__STORAGE__S3__BUCKET=assets
APP__STORAGE__S3__ACCESS_KEY_ID=...       # same as S3_ACCESS_KEY
APP__STORAGE__S3__SECRET_ACCESS_KEY=...   # same as S3_SECRET_KEY

docker compose -f src/docker/compose.yml --profile s3 up
----

With the podman override below the endpoint is `http://127.0.0.1:9000`. Any other
S3-compatible service works the same way through the `APP__STORAGE__S3__*` settings.

== API

The REST API is described by an OpenAPI document at `/api/v1/openapi.json` (titled with the
product name). Sign in with `POST /api/v1/auth/sign-in` and send the returned token as
`Authorization: Bearer <token>`. Browsers use the session cookie instead; state-changing
requests from other sites are refused (checked with `Origin` and `Sec-Fetch-Site`).
Sign-in is throttled after 10 failed attempts for a name within 15 minutes. JSON request
bodies are limited to 2 MiB, import uploads to 64 MiB.

== Behind a TLS-inspecting proxy

If a corporate proxy re-signs HTTPS traffic, the image build fails with certificate errors
(`curl: (60) unable to get local issuer certificate`). Copy the proxy's root CA certificates
(PEM, `.crt`) to `config/certs/` before building, e.g.
`cp /usr/local/share/ca-certificates/*.crt config/certs/`. They are trusted in the build and
in the running server, and are never committed.

== Rootless podman on Ubuntu

If the app logs `failed to lookup address information` for `postgres`, container DNS is not
working. On Ubuntu, AppArmor can stop podman from signalling `pasta`, which leaves stale
network namespaces (and a DNS server nobody reaches) behind after `down`; the kernel log then
shows `apparmor="DENIED" ... profile="pasta" ... signal=term`. Allow the signal in the local
override of the passt profile (`signal (receive) peer=podman,`), reload it with
`apparmor_parser -r`, stop stray `aardvark-dns`/`pasta` processes and start again.

If container DNS still does not work, start with the override that needs no DNS (the three
containers share one network namespace and talk over 127.0.0.1):
`docker compose -f src/docker/compose.yml -f src/docker/compose.podman.yml up`.
