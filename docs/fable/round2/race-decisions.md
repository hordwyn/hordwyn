# race decisions (lane R)

Format: `LR-N | question | choice | alternatives | how to reverse | source`. The orchestrator
renumbers them into `docs/DECISIONS.md` when merging.

LR-1 | The Library sent a page without its status tabs while the browser rendered them (hydration panic, `library.spec.ts:427` under load). What is the rule that keeps this from coming back? | On the server no memo reads a resource. A value derived from a resource comes from `pages::derived` (a `Memo` in the browser, a derived signal computed on every read on the server) or from a memo behind `#[cfg(feature = "hydrate")]`. The three header memos of the Library (`chips`, `all_count`, `tabs`) use `derived` and read both resources on every call (`Lib::header`, never one behind the other's `?`). `crates/web/tests/server_memos.rs` reads the sources and fails on a `Memo::new` outside such a `cfg` whose closure reads a resource; the server test `library_page::every_page_of_many_at_once_has_its_header_rows` is the detector (304 pages, 16 at a time, 4 worker threads). Earlier cases of the same rule: DEC-398 (`latest_page`), DEC-456 (`set_pending`). Seen (review RACE-1, 2026-11-13): the detector run on the code with F1 reverted (the three memos `Memo::new` over `kinds_now`/`counts_now` again), host under `stress -c 4`: 6 of 97 runs red ("the kind chips is missing" 4 times, "the status tabs is missing" twice; the 98th run was cut by a time limit); the fixed code under the same load (and a parallel `cargo leptos build`): 100 of 100 runs green. The stale memo is the cause the detector sees, and F1 removes it; C1 is closed as proven by these runs, with the console guard of the browser suite as the net for other causes. | Keep the memos and read the resources once more in the view (two paths to one value, the mismatch stays possible); a single-threaded page render (a change of the server's runtime for one defect) | Use `Memo::new` again in the three places and delete the source test | race-diagnosis.md 2.2, 2.4 F1; reactive_graph 0.2.16 `computed/inner.rs:106-189`, `computed/async_derived/arc_async_derived.rs:418-457`

LR-2 | A hydration panic left a page that looked complete, was marked `body[data-hydrated]` and did not react below the place of the panic. What does the page do? | (1) `body[data-hydrated]` is set by `web::hydrate` after `hydrate_body` returned, not by an effect (an effect queued before the panic still ran and set it). (2) A panic while hydrating marks `body[data-hydration-failed]` and reloads the page once per tab (`sessionStorage` key `app-hydration-retry`, removed by the next hydration that goes through); a second failure in a row stays marked and does not reload again. (3) The browser tests fail on any hydration error or panic on the console of a page, whatever the test was about (`tests/fixtures.ts`, `appFailures`); a test that provokes one on purpose reads the list and empties it. Without (3) the reload of (2) would hide a real defect from the suite. "Non-fatal error at ... renderer/dom.rs" is noted per test as an annotation with the page, not a failure (diagnosis 6.2: report first). | No reload, only the honest marker (a person keeps a dead page until they reload by hand); reload without a limit (a loop when the server's HTML is wrong every time); an error screen instead of a reload (more code for a case that one reload cures) | Remove `hydration::failed`'s reload; the marker and the guard stand on their own | race-diagnosis.md 2.3, 2.4 F2

LR-3 | `settings::loaded` rendered every answer of a refetch afresh, also an equal one: cards, menus, focus and typed text were rebuilt for the echo of an own action and for events about other things. | `loaded` keeps the render for an equal answer: it remembers the last `Ok` value and its key and gives the same key again when the new value is equal (`settings::render_key`); another value or an error gets a new key as before. This changes the sentence "each new value afresh" of `loaded`: each different value afresh. What must survive a different answer still comes from `kept` (LR-4). | Keyed shells for every card and row as in the Library (the complete cure, a larger change per page; not needed for the failure); compare in each page (27 call sites) | In `loaded`, take `fresh(renders)` for every answer again | race-diagnosis.md 3.2 F3

LR-4 | A menu inside a view that a refetch renders afresh closed under the pointer when an answer differed (`people.spec.ts:91` under load). | Every such menu gets an `open` signal that outlives the render and is handed to `DropdownMenu` (`open=`): `settings::kept` for the menus inside `loaded` (person card `pp-menu-<id>`, person page, game group `pp-group-menu-<id>`, integration `ig-menu-<id>`, admin user row `user-menu-<id>`), `ItemUi::menus` for the two menus of the item page (item actions, lists; closed when the route shows another item). The menu's own effect focuses its item again in the new render. | Keyed shells (see LR-3); closing the menu on purpose with a message (worse for the person) | Drop the `open=` props | race-diagnosis.md 3.2 F4, section 5

LR-5 | A page's own refresh did not tell its `Pace`: the event that announces the same action refetched a second time at once. | `events::refresh_on_updates` returns `OwnRefresh`; `OwnRefresh::wrap(refresh)` is the callback for the page's own refreshes: it notes the refetch in the pace (`Pace::own`) and runs `refresh` at once. People, the person page, Library, Home, History and the two list pages use it. The event of an own action is then answered once at the end of the quiet time (2 s), and with LR-3 that answer changes nothing on screen. When the event reaches the browser before the answer of the own request, the event refetches at once and the own refresh follows at once as before (two reads; the own action must show without a wait, and nothing tells the page that the event was about it). | Delay the own refresh inside the quiet time (an own action would show late); drop the event of an own action by its id (the REST answers do not carry the event's id) | Call the bare refetch in the pages again | race-diagnosis.md 3.2 F5; DEC-614

LR-6 | The Library header (count, kind chips, status tabs, tag filter, facet filters), the History side panel and the item page's lists cell sat in `<Suspense>` over a resource that is refetched: every refetch swapped them for their fallback until the answer came (focus lost, clicks into nothing). The held-answer tests were red on the unchanged code, so cause C5 of the diagnosis is confirmed. | `<Transition>` in the Library header and the History side panel: the first load shows the fallback, a refetch keeps what is on screen until the answer is there. The item page's lists cell has no boundary of its own and reads `lists` under the page's `Transition`: it sits inside the keyed render of the item, so a boundary there is a new one on every refetch and showed its fallback (empty) while `lists` was read again (seen in the test); the page's Transition is the same one across refetches and keeps the last lists. On the first load the page now waits for `lists` as well. The other `<Suspense>` places of the diagnosis' list were read and left alone, their resources are never refetched: `history.rs` group switcher and filter fields (`kinds`, `companions`), Stats (`home.rs`, `totals` and `kinds`), `stats_extras.rs` (`stats_compare`), `bulk.rs` (the list picker reads `lists` once per opening). The price (review RACE-8): the first load of the item page, on the server and after a client-side navigation, shows the item when `item_page`, `kinds` and `lists` are all there; a `lists` call that hangs keeps the skeleton (and the stream) for the whole page, an error leaves the cell out as before. Accepted: `lists` is one indexed read per user and the cell is above the fold; if it ever gets slow, read it into a signal by an effect in the browser instead. | Mirror signals filled by effects (more state for the same result) | `Suspense` again | race-diagnosis.md 4 F6, section 5

LR-7 | Review RACE-2: a menu kept open across a refetch (LR-4) is a new `DropdownMenu` in the new render, and its effect focused its item whenever it was open: every differing answer pulled the focus out of a field or a dialog the person had moved to, and put a keyboard user back on the first item. The menu had no close on a press outside either. | (1) An open menu takes the focus only when the focus is nowhere (`document.activeElement` is `body` or absent: the item that had it left with the old render) or already inside the dropdown (`ui::dropdown::may_take_focus`). (2) A press (`pointerdown`) outside the dropdown closes it without moving the focus (one window listener while open, removed on close and on cleanup); Escape and Tab close it as before. (3) The focused item is kept next to the open flag: `DropdownMenu` takes `active=` (an optional `RwSignal<usize>`), `settings::kept_menu(key)` gives both (`KeptMenu`), and the item page's two menus are `KeptMenu`s. | Close the menu on every differing answer (the failure LR-4 cured); close on focus leaving (also closes it when a dialog opens over it from a shortcut, which is not a reason) | Drop the `may_take_focus` check and `close_on_outside_press`; `active` back to a local signal | review 2026-11-13-race-review.md RACE-2; WCAG 3.2.1, 2.4.3

LR-9 | Review RACE-5: with LR-3 an equal answer keeps the render, so a save that the server stores other than typed (`045` stored as 45, a normalised value) left the typed text in the field next to "Saved." when the stored value had not changed. | `settings::render_again()` (a handle for the callback of a save) makes the next answer render afresh even when it equals the last one. The forms of the personal pages were not audited one by one; a form there that shows the stored value after a save calls `render_again` the same way. | Set the fields from the answer in every caller (more code per form); always render a save's answer afresh (loses the focus of an echo, the case of LR-3) | Remove the `render_again` calls | review RACE-5

LR-10 | Review RACE-4 and RACE-13: after the one reload (or without `sessionStorage`) a failed start left a dead page with nothing for the person; the reload itself dropped text typed into the server's page and was read out twice without a reason. | (1) The branch that does not reload puts a notice at the top of `body`: `role="alert"`, a sentence and a "Reload" link to the same address (`rel="external"`, a plain link: the app's code is not running).
