## Rules (binding)

- **No AI attribution** anywhere. ASCII in files. No GPL code (GPL API docs are fine, DEC-169).
- **The repository is public:** never write local or absolute paths, the owner's server or
  private domain, personal names or private e-mail addresses into any file, commit, issue or
  merge request. Placeholders: `<repo>`, `<scratchpad>`, `tracker.example.org`, test user
  `robin`. Commit identity is set: `Hordwyn maintainers <dev@hordwyn.com>`. Before each commit:
  `git grep -nE '/home/|/tmp/claude|punkt|passmail'` on what you add.
- **Production is personal:** never ask the owner to enter test or fake data there, never touch
  the server. Behaviour is proven in tests or on a throwaway local stack. The owner runs
  server commands; give them copy-paste ready (the owner has no `dc` helper defined, write it
  into the block).
- **The production host's hardening is another agent's work.** Do not touch it here.
- **Version rules (agreed 2026-11-18):** a patch has **no database migration**, no changed
  behaviour people rely on, no new required setting. Anything that needs a migration moves to
  1.1.0 (say so, do not squeeze it in).
- **Every fix comes with a test that reproduces the finding** (it fails before the fix).
- **Never accept a test workaround for an app race.** Retries never hide a failure: CI runs
  Playwright with `failOnFlakyTests`; a test that only passes on retry fails the run. Find the
  cause; if it is the app, fix the app. Timing budgets may differ between a dev host and the
  shared runner only when the test's point is kept (DEC-849).
- **Decisions are recorded** as one line in `docs/DECISIONS.md`
  (`DEC-n | topic | decision | alternatives | how to reverse | source`), next free number
  DEC-853. Every user-visible change gets its line under `## [Unreleased]` in `CHANGELOG.md`
  in the same commit. Conventional Commits; `sh src/sh/commit-lint.sh <range>` must pass.
- **Owner decisions** are asked with a question tool, one clear question with a recommended
  option; everything else is decided and recorded, not asked. New ideas from the owner go to
  `docs/handoff/v2-notes.md` and, when they are work, to a GitLab issue (milestone
  `Later 1.x` unless the owner says otherwise), never into 1.0.1 by themselves.
- **Build host:** 4 vCPU, 16 GB RAM. `CARGO_BUILD_JOBS=2` or 3, only one heavy build or test
  run at a time (one background agent that builds, never two). Dev shell: `nix develop`,
  then `cd src/rust`; local services `cargo xtask services up`.
- **Delegation:** a background agent per package is fine (brief it with these rules and the
  issue text); review its branch yourself before anything reaches main. Fable only for
  independent reviews (weekly limit).
- **Long waits:** background watchers stop at 2 h; restart them and say so. Never chain a
  merge and a branch delete in one command (2026-11-17: a failed merge plus a delete lost a
  branch for a moment).

## How to run 1.0.1

1. **Branch** `release/1.0.1` from main. One commit (or a few) per issue, the message names
   the issue (`fix(api): ... (#1)`); the merge request "Release 1.0.1" lists `Closes #1` ...
   `Closes #9`. Order: #1, #3, #9 first (priority), then #2, #4, #5, #6, #7, #8.
2. **Per issue:** read the code the issue names, write the reproducing test, fix, run the
   affected tests (Rust unit/integration, the e2e spec of the page). Record a DEC line when a
   choice was made.
3. **Issue notes:**
   - #1: the owner's production has a leftover session from before the fix. The cleanup must
     be something the owner can run (a `cli` command with a dry run, or a delete action in
     the app), never a SQL statement typed into production by hand.
   - #3: the stored TheTVDB shows need a refresh after the upgrade: name the command in the
     release notes ("Upgrade steps, release-specific").
   - #9: generate the notices at build time (cargo-about or equivalent for crates, the npm
     licences, `crates/ui/icons/vendor/*/LICENSE`, fonts); it goes into the image and CI fails
     when it cannot be generated. Check the tool's own licence.
   - If an issue turns out to need a migration, stop, tell the owner, move it to 1.1.0.
4. **Gate:** locally `cargo xtask ci` and `cargo xtask e2e` green (0 panics in the server
   log); then the full GitLab pipeline of the branch (`glab ci run -b release/1.0.1`) green
   including `docker-image`.
5. **Release** by `docs/HANDOFF.md` section 1, release checklist: CHANGELOG section
   `[1.0.1] - <date>`, release notes `docs/modules/ROOT/pages/releases/v1.0.1.adoc` from the
   template (+ index row + nav), version 1.0.1 in `src/rust/Cargo.toml` with `Cargo.lock`, no
   new migration, `upgrade-test` green (it now really runs from v1.0.0). Fast-forward main to
   the branch after the merge request pipeline is green (never squash away the issue
   references).
6. **Candidate and staging:** tag `v1.0.1-rc.1`, its pipeline publishes `:1.0.1-rc.1`. The
   owner upgrades a **staging copy** first (docs: Staging, published image), then confirms.
   Then `v1.0.1` on the same commit, its pipeline publishes `:1.0.1`, `:1.0`, `:latest`.
7. **Production (owner):** copy-paste steps: backup, `git fetch --tags --force origin`,
   `git checkout v1.0.1`, `APP_IMAGE=registry.gitlab.com/hordwyn/hordwyn:1.0.1`, `dc pull`,
   migrate dry run, `dc up -d --no-build`, the release-specific steps (#1 cleanup, #3 refresh),
   checks, and the way back.
8. **Close out:** issues closed by the merge request, milestone 1.0.1 closed, HANDOFF
   section 0 and this file updated, then the owner's next step (1.1.0 planning: episode names).

Production, copy-paste (in the production checkout; replace nothing but the date suffix if
you run it on another day):

```sh
dc() { docker compose --env-file config/.env -f src/docker/compose.yml "$@"; }
# 1. backup: database and secrets key
mkdir -p backup && chmod 700 backup
dc exec -T postgres pg_dump -Fc -U app app > backup/app-$(date +%F)-before-1.0.1.dump
dc exec -T app cat /data/secrets.key > backup/secrets.key && chmod 600 backup/secrets.key
# 2. the new version
git fetch --tags --force origin
git checkout v1.0.1
sed -i 's|^APP_IMAGE=.*|APP_IMAGE=registry.gitlab.com/hordwyn/hordwyn:1.0.1|' config/.env
grep '^APP_IMAGE=' config/.env
dc pull
# 3. dry run: must say "no pending migrations"
dc run --rm --no-deps --entrypoint cli app migrate --dry-run
# 4. start, watch for "listening" (Ctrl+C stops following)
dc up -d --no-build
dc logs -f app
# 5. release-specific steps
dc exec app cli sessions orphaned             # read the list (the OT-22 session)
dc exec app cli sessions orphaned --apply
dc exec app cli refresh-source tvdb           # only with a TheTVDB key; read the list
dc exec app cli refresh-source tvdb --apply
dc exec app cli refresh-source openlibrary --apply   # optional: book years now (#5)
# 6. checks
dc exec app curl -fsS http://127.0.0.1:3000/healthz; echo
dc exec app ls -l /usr/share/doc/app/THIRD-PARTY-NOTICES.txt
```
